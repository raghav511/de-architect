@@chapter
## C2.1 Why "fix the bug" is an expensive prompt

A coding agent fills every gap you leave with exploration. "Fix the bug" makes it read the whole project, guess which bug you mean, and pick its own definition of done. That costs turns and tokens, and the guess may be wrong. A good prompt removes guesses. Five parts, in this order:

| Part | Question it answers | Example for the practice project |
|---|---|---|
| **Goal** | What outcome? | EU amounts like `12,50` must parse as 12.5 |
| **Context** | Where to look, what is known? | `@pipeline/ingest.py` `parse_amount`; `@docs/vendor_notes.md` says DE and FR use a decimal comma |
| **Constraints** | What must not change? | Keep the US format `1,234.50` working; no new dependencies; do not touch load.py |
| **Verification** | How do we know it worked? | `test_eu_amount` and `test_us_amount` pass; add a test for `1.234,50` |
| **Output** | What do you want back? | A plan first; after the fix, a 3-line summary and the diff |

You do not need all five every time. For a quick question, goal and context are enough. For a change, never skip **verification**: an agent with a test to pass corrects itself; an agent without one stops when the code looks plausible.

## C2.2 Context beats cleverness

The model is capable; what it lacks is **your** knowledge. The highest-value sentences in a prompt are facts it cannot find:

- "The EU shop exports decimal commas; the US shop uses thousands commas." (business rule)
- "This runs daily on 50 million rows, so avoid per-row Python regex." (scale)
- "We tried rounding before; finance rejected it." (history)
- "The fix must work on Spark 3.3, our cluster version." (environment)

Point at files with `@` instead of describing them. Paste the exact error and the exact command that produced it. If a screenshot explains it better (a dashboard showing the wrong total), drag it into the terminal.

## C2.3 Ask for a plan, then steer early

For anything bigger than a one-line fix, ask for a plan first (plan mode). Reading a 10-line plan takes a minute and catches the wrong approach before 200 lines are written. Good follow-ups:

- "Option 2, but keep the function signature unchanged."
- "What would break if a value has no decimal part, like `1,234`?"
- "Do it in two commits: tests first, then the fix."

If Claude goes off track mid-edit, press `Esc` and correct it at once. A short correction now is cheaper than a long one later.

## C2.4 Patterns worth keeping

- **Test first:** "Write a failing test that shows the bug. Run it to prove it fails. Then fix the code until it passes. Do not change the test."
- **Interview me:** "Before you start, ask me up to 3 questions about anything ambiguous."
- **Explain like a reviewer:** "Explain this diff as if reviewing it for a teammate: risks, edge cases, what is not tested."
- **Bound the output:** "Answer in under 8 lines" or "only the changed function". Shorter answers cost less and are easier to check.
- **Name what you do not want:** "Do not refactor unrelated code. Do not add logging."

Anti-patterns: several unrelated tasks in one prompt; "make it better"; "fix everything"; letting a session wander across topics without `/clear`.

@@interview
Q: How do you write prompts for AI coding tools so the output is reliable?
TAG: ai
A: I give the agent what it cannot discover: the goal in one sentence, the files and business rules that matter, the constraints (what must not change, versions, scale), and how to verify, usually a test that must pass. For anything non-trivial I ask for a plan first and steer before code is written. I keep one task per session and bound the output. Reliability comes mostly from verification, not wording: an agent with a failing test to fix converges; one without just produces plausible code.
---
Q: Your team's AI-generated code keeps missing edge cases. What would you change?
TAG: ai
A: Make edge cases part of the definition of done. Ask for the failing tests first, including nulls, empty inputs, duplicates, late data and type edge cases, and review those tests before the fix. Put recurring rules in CLAUDE.md ("all parsers handle empty strings and None"). Add a review prompt: "list inputs this change does not handle". And track it: if a class of bug recurs, add a check that runs automatically, such as a hook or a CI test.
---
Q: How do you decide how much context to give an AI assistant?
TAG: ai
A: Enough to remove guesses, no more. Facts it cannot find (business rules, scale, history, environment) always go in. Files it can find, I point to with @ rather than paste. I avoid dumping whole logs; I give the error and the command. Too little context causes wrong guesses and exploration cost; too much dilutes attention and costs tokens. If I repeat the same context every session, it moves to CLAUDE.md.
---
Q: Give an example where asking for a plan first saved you time.
TAG: behavioral
A: (Use your own.) Example shape: we needed to deduplicate late-arriving events in a pipeline. The first plan proposed a full-table rewrite every run. Because I saw that in the plan, I steered it to a merge on the last three days of partitions, which matched our late-data window. That avoided a change that would have tripled compute cost. The plan took two minutes to read; the wrong implementation would have taken an hour to review and redo.
---
Q: What are anti-patterns when prompting coding agents?
TAG: ai
A: Vague goals ("make it better"), several unrelated tasks in one prompt, no verification step, letting a session drift across topics without clearing context, pasting secrets or production data, and accepting large diffs without reading them. Also over-specifying the how when the what is unclear: describe the outcome and constraints, and let the agent propose the approach for you to judge.
