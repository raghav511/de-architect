## C14.1 An LLM step is a transform that bills per row

Classify tickets, extract fields from emails, enrich products with a category: these are ordinary pipeline transforms whose function happens to be a model. AI 4 covered the same idea inside the warehouse ([A4.5 AI functions in SQL](#/learn/a04/chapter)) and AI 5 covered extraction as ETL ([A5.5](#/learn/a05/chapter)); here you build the step yourself with Claude, where the levers are yours.

Four properties make it safe to rerun and cheap to run:

1. **Idempotent by row.** Key every result by `(row_id, input_hash, prompt_version, model)`. A rerun skips rows already done with the same key, so a retry after a crash costs nothing and never duplicates. A new prompt version is a deliberate backfill, not an accident.
2. **Estimated before it runs.** Cost per row = input tokens x input price + output tokens x output price (thinking counts as output). Multiply by the rows. Run 1,000 rows first and compare with the estimate.
3. **Bounded.** A concurrency limit below your rate limit, retries with backoff for rate-limit (429) and overloaded (529) errors (the SDKs retry twice by default), a timeout, and a daily budget that stops the job.
4. **Checked.** The output schema and business rules from Claude Code 13, a dead-letter table for rows that fail twice, and a labelled sample scored on every prompt or model change.

Where the call lives: an Airflow or Dagster task that reads new rows, a dbt Python model, or Spark `mapPartitions` with one client per partition and a semaphore. Never call the model inside a per-row UDF with no concurrency limit: 200 executors times 8 cores is 1,600 parallel calls and a wall of 429s.

### Under the hood

A Messages call is a network request to a shared service: latency is seconds, not microseconds, and capacity is metered in requests and tokens per minute. Batch-style data work needs the same tools you use for any slow external API: bounded parallelism, retries that do not duplicate, and a record of what was already done.

### Common traps

- No input hash: an edited ticket keeps its old label forever, or every rerun pays again.
- Retrying a 400 error (a bad request) as if it were a 429.
- Logging full prompts with customer text into a shared log table (Claude Code 6).

## C14.2 The Message Batches API

When nobody is waiting for the answer (last night's tickets, a backfill, an evaluation run), send the requests as a **batch**. Every token costs **50% less**, and you trade latency: most batches finish within an hour, and every batch finishes or expires within 24 hours.

```python
import anthropic, hashlib
from anthropic.types.message_create_params import MessageCreateParamsNonStreaming
from anthropic.types.messages.batch_create_params import Request

client = anthropic.Anthropic()            # ANTHROPIC_API_KEY from the environment
reqs = [Request(custom_id=f"{t.id}-{hashlib.sha1(t.text.encode()).hexdigest()[:8]}",
                params=MessageCreateParamsNonStreaming(model="claude-haiku-5-5", max_tokens=200,
                    system=SYSTEM, messages=[{"role": "user", "content": t.text}]))
        for t in todo]
batch = client.messages.batches.create(requests=reqs)
# later: poll batches.retrieve(batch.id).processing_status until "ended", then
for r in client.messages.batches.results(batch.id):
    if r.result.type == "succeeded": save(r.custom_id, r.result.message)
    else: retry_later(r.custom_id, r.result.type)     # errored, canceled or expired
```

The rules that matter for pipelines:

- **Results come back in any order.** Join them by `custom_id` (1 to 64 letters, digits, `-` or `_`), never by position. Put the row key and the input hash in it.
- **Limits:** up to 100,000 requests or 256 MB per batch, whichever comes first. Split larger jobs.
- **Partial failure is normal.** Each result is `succeeded`, `errored`, `canceled` or `expired`. Resubmit only the failed ones in a new batch; expired requests are not billed.
- **Results stay downloadable for 29 days.** Store them in your table at once; the batch is not your storage.
- **Orchestrate it as two tasks:** submit (store the batch id), then a sensor or deferrable task that waits and collects. A worker that sleeps for an hour holding a slot wastes the cluster.

### Under the hood

A batch is many independent Messages requests that the service runs when it has spare capacity, which is why it can be cheaper. Each request is still single-shot: there is no tool loop inside a batch, so work that needs several turns must be flattened into one request or run in real time.

### Common traps

- Joining results by list index.
- One giant batch with no record of its id: a crashed orchestrator cannot find the results.
- Using batches for a dashboard someone opens at 9 a.m. with data from 8:55.

## C14.3 Prompt caching, and a worked cost example

Most pipeline prompts are a long, **identical** prefix (instructions, label definitions, five examples) and a short changing part (one ticket). **Prompt caching** stores the processed prefix so the next request with the same prefix reads it at a fraction of the price. Mark where the stable part ends:

```python
client.messages.create(model="claude-haiku-5-5", max_tokens=200,
    system=[{"type": "text", "text": RULES_AND_EXAMPLES, "cache_control": {"type": "ephemeral"}}],
    messages=[{"role": "user", "content": ticket_text}])
```

- **Order:** tools, then system, then messages. Anything that changes (a timestamp, a ticket id) must come **after** the marker, or every request misses.
- **Lifetime:** 5 minutes by default, refreshed on every hit; `"ttl": "1h"` keeps it an hour, useful for batches, which can take longer than 5 minutes.
- **Price:** a write costs 1.25x normal input (2x for the 1-hour TTL); a read costs about 0.1x (0.05x on Sonnet 5.5 and Opus 5.5). Two requests within 5 minutes already pay it back.
- **Minimum size:** about 512 tokens on current models; a shorter prefix silently does not cache.
- **Prove it:** `usage.cache_read_input_tokens` should be large on the second request. If it stays 0, something in the prefix changes.

**Worked example.** One million tickets a night; each request is a 2,000-token shared prefix, a 100-token ticket and about 40 output tokens at low effort. Prices from the pricing page in November 2026, per million tokens: Haiku 5.5 $0.10 in, $0.50 out, cache read $0.01; Sonnet 5.5 $2 in, $10 out, cache read $0.10.

| Setup | Input | Output | Per night |
|---|---|---|---|
| Sonnet 5.5, no caching | 2.1 B tokens x $2 = $4,200 | 40 M x $10 = $400 | about $4,600 |
| Haiku 5.5, no caching | 2.1 B x $0.10 = $210 | 40 M x $0.50 = $20 | about $230 |
| Haiku 5.5, prefix cached | 2 B x $0.01 + 0.1 B x $0.10 = $30 | $20 | about $50 |
| Haiku 5.5, batch, no caching | half of $230 | | about $115 |
| Haiku 5.5, batch and cache | discounts stack; cache hits in a batch are best effort | | $25 to $115 |

The model choice is worth 20x; caching is worth another 4x. Check quality before cost: the cheapest row is the one that is also right.

### Under the hood

The model turns the prefix into internal state (keys and values for every token) before it can read the next token. Caching stores that state for an identical prefix, so the work is done once. Any changed byte early in the prompt changes everything after it, which is why the rule is "stable first, changing last".

### Common traps

- `datetime.now()` or a run id at the top of the system prompt.
- Switching models mid-job: caches belong to one model.
- Assuming a hit: read the usage fields.

## C14.4 The right model: routing and fallbacks

| Model (API id) | Price in / out per M tokens | Use it for |
|---|---|---|
| Haiku 5.5 (`claude-haiku-5-5`) | $0.10 / $0.50 | High-volume classification, extraction, tagging |
| Sonnet 5.5 (`claude-sonnet-5-5`) | $2 / $10 | Harder extraction, summaries, most agent and coding work |
| Opus 5.5 (`claude-opus-5-5`) | $4 / $20 | Hard reasoning, long agentic tasks, design |

(Fable 5.2 is above Opus for the hardest long-horizon work, at a higher price. Haiku's price rises for prompts over 100,000 tokens.)

**Choose with your test set, not the leaderboard.** Anthropic's guide gives two starts: efficiency-first (start on Haiku, move up only for a measured gap) for high-volume pipelines, capability-first (start on Opus, then try lower effort or a smaller model) for hard tasks. Lowering **effort** on one model is often a better first lever than switching models, and it keeps one prompt cache.

**Routing** sends each row to the cheapest model that can do it: rules (short tickets with a known keyword go to Haiku) or a cascade (Haiku first; rows that fail the schema or business rules, or answer "unknown", go to Sonnet). A cascade pays when most rows stay small; escalated rows cost both calls. [A6.5](#/learn/a06/chapter) has the trade-offs of each lever.

**Fallbacks** keep a nightly job alive:

- **429 and 529:** retry with backoff and jitter, then slow the job down; do not hammer.
- **A longer outage:** fall back to another model or platform (Claude on Bedrock or Vertex) that has passed the same eval set, and record which model answered each row.
- **A refusal** (`stop_reason: "refusal"`): do not retry the same request in a loop; send the row to the dead-letter table.
- **Every row records** model, prompt version and cost, so a fallback night can be found and re-run.

With several teams this logic belongs in one LLM gateway ([A6.6](#/learn/a06/chapter)), not copied into every job.

### Under the hood

Larger models do more computation per token, so they cost more and answer more slowly; effort changes how many tokens a model spends on the same task. Both move quality, so every change is checked on the same labelled sample.

### Common traps

- A fallback model nobody evaluated: the job "succeeds" with worse labels.
- Routing on a guess instead of measured accuracy per route.
- Forgetting thinking tokens in the cost estimate: they bill as output.

@@interview
Q: You need to classify 50 million product descriptions with an LLM. How do you design it?
TAG: ai
A: Estimate first: tokens per row times rows times price, on a 1,000-row sample, at two models and two effort levels, scored against a labelled sample. Pick the smallest model that passes. Make the step idempotent: results keyed by product id, input hash, prompt version and model, so reruns skip done rows. Put the instructions and examples in a cached prefix and the description last. Nobody is waiting, so send it through the Message Batches API in chunks under 100,000 requests, with custom_id carrying the key and hash, a submit task and a collect task, and resubmission of errored or expired rows. Schema and business-rule checks, a dead-letter table, a daily budget and a record of model and prompt version on every row.
---
Q: When does prompt caching pay off, and how do you know it is working?
TAG: ai
A: When many requests share a long identical prefix within the cache lifetime: instructions, examples, tool definitions or a shared document, followed by a short changing part. A write costs about 1.25 times normal input and a read about a tenth or less, so two requests within five minutes already pay back. It fails silently when anything before the marker changes, such as a timestamp, or when the prefix is below the minimum size. I check usage.cache_read_input_tokens on repeated requests and alert when the hit rate drops.
---
Q: Batch API or real time?
TAG: ai
A: Batch when nobody waits for the answer: nightly enrichment, backfills, evaluation runs. It halves the token price, but most batches take up to an hour and any can take up to 24, results come back in any order, and there is no tool loop. Real time when a person or a downstream SLA waits, with caching to cut the cost. Many pipelines use both: real time for today's new rows, batch for the backfill.
---
Q: How do you choose between Haiku, Sonnet and Opus for a pipeline step?
TAG: ai
A: On my own labelled cases, not a leaderboard. For high-volume simple tasks I start with Haiku and move up only for a measured gap; for hard reasoning I start with Opus and try lower effort or a smaller model. I compare accuracy, cost per correct row and latency, read the misses, and often route: the cheap model for most rows, the stronger one for rows that fail checks or report low confidence. Every row records the model so a change can be backfilled deliberately.
---
Q: The LLM provider has an outage during your nightly job. What happens?
TAG: ai
A: The job backs off with jitter on 429 and 529 errors and slows its concurrency rather than hammering. If the outage lasts, it falls back to another model or cloud platform that passed the same evals, and each row records which model answered, so the night can be reviewed or re-run. Rows that still fail go to a dead-letter table and the job finishes the rest; the daily budget and an alert stop runaway retries. Because the step is idempotent, a rerun the next morning only processes what is missing.
