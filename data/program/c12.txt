## C12.1 Claude Code as a library

The **Claude Agent SDK** gives your own Python (or TypeScript) program the same agent harness that powers Claude Code: the loop, built-in tools (Read, Grep, Bash, Edit...), permissions, context management, MCP and subagents. You add your own tools and decide the rules. In AI 1 you built a loop by hand to understand it; for production you usually want this battle-tested harness and to spend your effort on tools, guardrails and evaluation.

```bash
pip install claude-agent-sdk
```

It needs credentials like Claude Code does: typically `ANTHROPIC_API_KEY` from the Anthropic Console in your environment (never in the code), or a cloud provider such as Bedrock or Vertex.

## C12.2 One call

```python
import anyio
from claude_agent_sdk import query, ClaudeAgentOptions

async def main():
    opts = ClaudeAgentOptions(
        cwd="/Users/me/cc-sandbox",
        allowed_tools=["Read", "Grep", "Glob"],   # read-only
        max_turns=8,
        model="sonnet",
        system_prompt="You are a careful data engineer. Answer with evidence: file:line.",
    )
    async for msg in query(prompt="Why are DE amounts too high?", options=opts):
        print(msg)          # assistant messages, tool use, and a final result with cost

anyio.run(main)
```

The stream ends with a result message that carries the total cost and usage: log it every run.

## C12.3 Custom tools

Tools are where your domain knowledge lives. Define them in-process and expose them as an SDK MCP server:

```python
from claude_agent_sdk import tool, create_sdk_mcp_server

@tool("revenue_by_country", "Revenue and order count per country from the warehouse", {})
async def revenue_by_country(args):
    con = sqlite3.connect("file:warehouse.db?mode=ro", uri=True)
    rows = con.execute("SELECT country, COUNT(*), ROUND(SUM(amount),2) FROM orders GROUP BY 1").fetchall()
    return {"content": [{"type": "text", "text": json.dumps(rows)}]}

dq = create_sdk_mcp_server(name="dq", version="1.0.0", tools=[revenue_by_country])
opts = ClaudeAgentOptions(mcp_servers={"dq": dq},
                          allowed_tools=["mcp__dq__revenue_by_country", "Read", "Grep"], max_turns=10)
```

Good tools are small, well described, read-only by default, return compact JSON, and fail with a helpful message.

## C12.4 From demo to production

What separates a demo from something you would run nightly:

- **Least privilege:** only the tools needed; no Bash unless essential; read-only data access.
- **Limits:** `max_turns`, a budget, timeouts; stop on no progress.
- **Structured output:** a schema the rest of your system validates (severity, findings, evidence), not prose.
- **Evaluation:** a small set of cases with known answers (for example "inject a duplicate order: does the agent find it?"), run on every change to the prompt, tools or model.
- **Observability:** log every run's prompt version, tool calls, cost and outcome.
- **Human in the loop** for actions: the agent recommends, a person or a pipeline with tests applies.

This is the same checklist as AI 1 to 3, now with a real harness. It is also a strong interview story: you built, constrained, evaluated and costed an agent.

## Lab: the data-quality investigator (40 minutes)

In ~/cc-sandbox (Python 3.10+, venv active, `pip install claude-agent-sdk`). Use Claude Code to help you write it. That is the point of the track.

1. Load the warehouse: `python3 -m pipeline.run 2026-10-01 2026-10-07`.
2. Write `agent/investigator.py` with two custom tools: `revenue_by_country` and `null_and_duplicate_counts` (both read-only, both compact JSON).
3. Options: your tools plus Read and Grep only, `max_turns=10`, model sonnet or haiku, and a system prompt that requires evidence.
4. Prompt: *"Investigate data quality in the warehouse. Return only JSON: {severity, findings: [{issue, evidence, suspected_cause_file_line}], recommended_fix}."* Parse the final result with `json.loads` and fail loudly if it is not valid.
5. Print the cost from the result message.
6. Eval: write `agent/eval.py` with 2 cases. First, on the buggy pipeline, a finding must mention DE or FR amounts. Second, after you fix the parser and reload, severity must not be fail. Run both.

@@interview
Q: Walk me through an AI agent you built. How did you make it reliable?
TAG: ai
A: (Use your investigator.) It investigates data quality in our warehouse with the Claude Agent SDK and two read-only custom tools: revenue by country and null and duplicate counts. Reliability came from the harness: read-only tools and a read-only connection, a turn limit and budget, a strict JSON output schema validated in code, and an eval set where I inject known problems (duplicates, a parsing bug) and check the agent finds them. It costs about X cents per run, logged every time. It recommends; humans or pipelines apply fixes.
---
Q: How do you evaluate an AI agent?
TAG: ai
A: A fixed set of realistic cases with known expected outcomes: some positive (an injected bug it must find), some negative (clean data where it must not raise false alarms), and edge cases. Score with checks in code where possible (it found the right table or field, valid JSON, severity correct), and with a rubric or LLM grader for free text, spot-checked by humans. Track pass rate, cost, turns and latency per version, and run the set on every change to the prompt, tools or model.
---
Q: Build or buy: when would you build a custom agent instead of using Claude Code directly?
TAG: ai
A: Use Claude Code directly for interactive engineering work. Build with the SDK when the task is a repeatable product or pipeline step with its own inputs and outputs (a nightly investigator, a triage bot, an internal assistant), when you need custom tools and strict permissions, structured output into other systems, evaluation and monitoring, or to embed it in your own app. If a scripted claude -p with a schema covers it, start there; move to the SDK when you need more control.
---
Q: What makes a good tool for an AI agent?
TAG: ai
A: A clear name and a description that says when to use it. A small, typed input schema. Compact, structured output (aggregates, capped rows). Read-only unless writing is the point, with writes idempotent and gated. Helpful errors the agent can recover from ("query must filter on order_date"). Enforcement inside the tool and the data layer, not in the description. Fast and deterministic.
---
Q: How do you control the cost of an agent in production?
TAG: ai
A: Turn and budget limits per run, the smallest model that passes the evals, compact tool outputs, stable prompt prefixes for caching, fewer and better tools (every tool description costs context), and logged cost per run with alerts. Review cost per useful outcome: per real issue found or ticket resolved, not per run.
