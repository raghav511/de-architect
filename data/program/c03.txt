@@chapter
## C3.1 What you actually pay for

Every turn of the agent loop sends the **whole conversation so far** to the model: your messages, Claude's replies, every file it read and every command output. You pay for:

- **Input tokens**: the context sent each turn. This is usually the biggest part, because it grows with every file and log.
- **Output tokens**: what Claude writes, including code. Output costs several times more per token than input.
- **Cache**: repeated context (the system prompt, CLAUDE.md, earlier turns) is cached automatically and read back at a fraction of the price. Changing early context breaks the cache.
- **Model**: Opus costs more per token than Sonnet, which costs more than Haiku. Effort and extended thinking add output tokens.

On a subscription plan you do not see dollars, but the same tokens count against your usage limits. Either way, fewer wasted tokens mean more work per day.

## C3.2 The four big drivers and the habit for each

| Driver | What it looks like | Habit |
|---|---|---|
| **Long conversations** | one session for the whole day; each turn re-sends hours of history | `/clear` between unrelated tasks; `/compact keep the failing test names and the plan` when one task runs long |
| **Exploration** | "fix the bug" makes it read ten files | point at files with `@`; give the error and the command; say where *not* to look |
| **Noisy output** | full test logs, `cat` of a 5 MB CSV, verbose builds | `python3 -m unittest -q`, `pytest -q -x`, `| tail -40`, `head -20 data.csv`; never let it print whole data files |
| **Wrong model** | Opus for renaming a variable | Haiku or Sonnet for routine work via `/model`; Opus for hard reasoning |

Check before you guess: `/context` shows what fills the window (system prompt, CLAUDE.md, MCP tools, files, conversation). `/cost` (API billing) or `/usage` (subscription) shows spend.

## C3.3 Structural savings

- **Keep CLAUDE.md short.** It is loaded in every session. 40 precise lines beat 400 vague ones.
- **Turn off what you do not use.** Every MCP server adds its tool descriptions to the context. Disable unused ones with `/mcp`.
- **Delegate searches to a subagent** (lesson C11). The subagent reads twenty files in its own context and returns a 10-line summary; your main context stays small.
- **Headless with limits** (lesson C9). Scripts can set `--max-turns` and `--max-budget-usd`, and restrict tools so a run cannot wander. The app's own grader does exactly this: no tools, a small model and a JSON schema, so a grade costs about a tenth of a cent instead of 25 cents.
- **Ask for less.** "Answer in 5 lines", "only show the changed function", "no explanation, just the command".

## C3.4 Do not save in the wrong place

Cheap is not the goal; **cost per correct result** is. Skipping the test run saves tokens and ships a bug. A prompt that asks for a plan and a test costs more than "fix it", and is worth it. Cut waste: repeated history, aimless exploration, giant outputs and the wrong model. Do not cut verification.

1. **Baseline.** Run: *"Look through the project and tell me everything that could be wrong with it."* Note turns, tokens in, tokens out and cost.

3. **Model.** Run prompt 2 again with Haiku, then with Sonnet. Is the answer as good? What did each cost?
4. **CLAUDE.md effect.** Open *Add a CLAUDE.md to this run* and paste 5 lines of project facts (what the project is, how to run tests, where the docs are). Re-run prompt 1. Did it explore less?
5. In your terminal, start `claude` in ~/cc-sandbox, read two files, run the tests, then type `/context`. Which part of the window is biggest? Run `/compact keep only the test results` and check `/context` again.

Keep the numbers. Task 1 asks for them.

@@interview
Q: How would you control the cost of AI coding tools across a data engineering team?
TAG: ai
A: Measure first: usage by person and repo, and which kinds of sessions are expensive. Then cut waste without cutting verification. Habits: one task per session, @ references instead of open exploration, quiet test output. Structure: short CLAUDE.md files, only the MCP servers people use, subagents for broad searches. Model policy: a mid-tier model by default, the top model for hard reasoning, a small model for automated jobs. Automation runs headless with a turn and budget cap. I report cost per merged change rather than raw spend, so we do not push people into skipping tests.
---
Q: Explain prompt caching and when it fails to save money.
TAG: ai
A: The provider caches the unchanged beginning of a prompt, such as the system prompt, tool definitions and earlier conversation, so repeated reads cost a fraction of normal input. It fails when the start of the prompt changes every call, for example a timestamp or request ID at the top, or a reordered tool list, because the cache matches on an exact prefix. Fix: stable content first, variable content last.
---
Q: A scheduled AI job costs 10 times more than expected. How do you debug it?
TAG: ai
A: Look at the usage per run: turns, input and output tokens, cache reads. Usual causes: the agent explores because the prompt is vague; tool outputs are huge (full logs or tables); it retries in a loop with no stop condition; the cache is broken by a changing prefix; or the model is bigger than needed. Fixes: a precise prompt, trimmed tool output, max turns and a budget, stable prefixes, a smaller model, and an alert when cost per run passes a threshold.
---
Q: When is it worth paying for the most capable model?
TAG: ai
A: When the task needs deep reasoning across a lot of context and mistakes are costly: debugging a subtle concurrency or data-correctness issue, designing a migration, or reviewing a complex change. For routine edits, renames, boilerplate and summaries, a smaller model gives the same result for less. I sometimes plan with the strong model and implement with a cheaper one.
---
Q: What does "cost per correct result" mean, and why use it?
TAG: ai
A: Total spend divided by the number of changes that were correct and merged, including the cost of rework. It stops the wrong optimisation: a cheap session that produces a bug costs more after the incident and the rework. It rewards good prompts, verification and smaller tasks, which make each correct result cheaper.
