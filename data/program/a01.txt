## A1.1 What an agent really is

A language model on its own does one thing: it reads text and writes text. It cannot run code, open a file, query a table or remember yesterday. Everything that makes an "agent" feel capable is built **around** the model by ordinary software. A short formula captures it:

> **Agent = model + harness**

The **harness** is your code: it sends the model a task, offers it tools, runs the tools the model asks for, feeds results back, keeps memory, enforces limits and records what happened. The same model inside a careless harness wastes money and makes things up. Inside a good one it fixes pipelines on its own.

A **workflow** is a fixed sequence you design (call A, then B, then C). An **agent** decides its own next step in a loop. Start with workflows; use an agent only when the steps cannot be known in advance, because every loop iteration costs time and tokens.

## A1.2 The loop

Every agent, from a 20-line script to a coding assistant that runs for hours, is this loop:

```
messages = [task]
while True:
    reply = model(messages, tools)          # think
    if reply asks for tools:
        results = run(reply.tool_calls)     # act
        messages += [reply, results]        # observe
    else:
        return reply.text                   # done
```

The model never executes anything. It returns a structured request such as `{"tool": "run_sql", "input": {"query": "..."}}`. Your code runs it and sends back the output. That separation is what lets you add safety: you can refuse, sandbox or ask a human before running anything.

**Three stop conditions you always need:**

1. **Done:** the model answers without asking for a tool.
2. **Budget:** a step limit and a token or money limit. Without them a confused agent loops forever.
3. **No progress:** the same tool with the same input twice in a row, or the same error three times. Stop and report instead of retrying blindly.

**Self-improving loops** are the same loop with a second judge in it: produce something, check it (run tests, score it against examples, ask a reviewer model), and feed the verdict back as the next observation. Module A2 is about these.

## A1.3 Harness engineering

"Harness engineering" became a common term in 2026, after prompt engineering (2022–23) and context engineering (2024–25). The idea is simple: when an agent makes a mistake, do not just reword the prompt; **change the environment so that mistake cannot happen again**. A production harness has five layers:

| Layer | What it does | Failure it prevents |
|---|---|---|
| Tools and orchestration | Small, well-named tools with clear inputs; retries with backoff; timeouts | Agent invents a tool or passes garbage; one slow call hangs everything |
| Verification | Run tests, linters, schema checks, row counts after each step | "Done" when nothing works |
| Context and memory | Give only what the step needs; keep a notes file of decisions and lessons | Context overflow, repeating old mistakes |
| Guardrails | Budgets, read-only roles, sandboxes, human approval for irreversible actions | Dropped tables, runaway bills, prompt injection doing damage |
| Observability | A trace of every call: input, output, tokens, cost, time | Not knowing why it failed or what it cost |

Known failure modes that harnesses fix: stopping early and declaring success, rushing when the context fills up, and trying to do too much in one pass. The fixes are structural: a checklist the agent must tick with evidence, a fresh context per sub-task, and one change per iteration.

## A1.4 Context engineering

What the model sees is the only thing it knows. Good context is **small and relevant**:

- Put stable material first (instructions, tool descriptions, schema) and changing material last (the current question). This also makes caching work.
- Give **examples of the output you want**, two or three, including an edge case.
- Summarise long histories instead of resending them. Keep a short "state" block: goal, done so far, next step.
- For data work, give table and column descriptions, a few sample rows, and the business definitions (what "active rider" means). This is the semantic layer you will build in the text-to-SQL project.

## A1.5 Prompts that work

A reliable prompt has six parts. Use XML-style tags so the model can tell them apart:

```
<role>You are a data reliability engineer.</role>
<task>Explain why this Airflow task failed and propose one fix.</task>
<context>{log tail, DAG code, last good run}</context>
<constraints>Quote the log line that proves the cause. If unsure, say so. Max 120 words.</constraints>
<output_format>JSON: {"cause": str, "evidence": str, "fix": str, "confidence": "low|medium|high"}</output_format>
<examples>{one good example}</examples>
```

Rules that change results the most:

1. **Say what "good" looks like.** Success criteria beat adjectives. "Quote the log line" beats "be accurate".
2. **Ask for structured output** when code will read the answer. Validate it; on failure, send the validation error back once.
3. **Let it think when the task is hard, and not when it is easy.** Reasoning costs tokens. Use it for diagnosis and design, not for formatting.
4. **One job per prompt.** Split "classify, then summarise, then draft a fix" into steps you can test separately.
5. **Test prompts like code.** Keep 20 inputs with expected answers and score every prompt change against them (lab 3).

## A1.6 Spending fewer credits for the same result

Cost is input tokens + output tokens × the price of the model. Levers, roughly in order of impact:

- **Pick the smallest model that passes your eval.** Route easy steps (classification, extraction) to a small model and hard ones (diagnosis, design) to a large one.
- **Prompt caching.** On the Claude API, a cache read costs a small fraction of normal input (0.1× by default, less on some current models). A 5-minute cache write costs 1.25× and a 1-hour write 2×. It only works on an **identical prefix**, so put tools, system prompt and long documents first, and never put timestamps or IDs before the cache breakpoint. Check `cache_read_input_tokens` in the response to prove it worked.
- **Cap output.** Set `max_tokens`, ask for short structured answers, and do not ask the model to repeat the input.
- **Send less.** Retrieve the 5 relevant rows, not the table; the log tail, not the whole log.
- **Batch** non-urgent work (batch APIs are discounted) and **stop loops early** with the stop conditions above.
- **Measure.** Log tokens and cost per task in the trace; you cannot cut what you do not count.

## A1.7 Automating tasks and prompts

A prompt you run by hand every day is a script waiting to be written. The ladder:

1. **Script:** the prompt plus code that gathers its inputs, in a file in git.
2. **Schedule:** cron, a GitHub Actions `schedule:` workflow, or Airflow. GitHub Actions is free for public repos and has a free monthly allowance for private ones.
3. **Idempotent output:** the job writes to a dated file or upserts a row, so reruns do not duplicate.
4. **Alerting:** on failure, send a message (Slack webhook, email) with the trace link.
5. **Review:** a weekly look at cost and accuracy; turn repeated corrections into prompt or tool changes.

Secrets (API keys) live in the CI secret store, never in the repo.

## Prompt drills (30 minutes)

Rewrite each prompt using the six-part structure. Then compare with the model answers below.

1. "Fix my SQL."
2. "Summarise this incident."
3. "Is this data good?"
4. "Write a DAG for this."
5. "Explain Kafka."

**Model answer for 1:** `<role>` senior analytics engineer; `<task>` find why this query returns duplicate rows and give a corrected query; `<context>` the query, table DDL, expected row count; `<constraints>` keep the same output columns, explain the cause in one sentence, do not change filters; `<output_format>` corrected SQL in a code block, then the one-sentence cause. The key additions are the **symptom**, the **expected result**, and **what must not change**.

**Model answer for 3:** ask for checks, not an opinion: "Run these 5 checks on the attached profile (nulls in keys, duplicates on trip_id, row count vs yesterday ±20%, negative fares, future timestamps). Return a table: check, value, pass/fail." A yes/no question invites a confident guess.

**Model answers for 2, 4, 5:** each needs the **audience** (on-call engineer, interviewer, new hire), the **length**, and the **format** (timeline table, a DAG file plus test, a 5-bullet explanation with one diagram).

@@interview
Q: What is the difference between an AI workflow and an AI agent, and when would you choose each?
TAG: ai
A: A **workflow** is a fixed sequence of model and tool calls that I design: extract, then classify, then summarise. An **agent** chooses its next step in a loop based on what it observes. I choose a workflow when the steps are known, because it is cheaper, faster and testable step by step. I choose an agent when the path depends on what it finds, such as diagnosing a failed pipeline. Even then I constrain it: few tools, budgets, and a verifier that must pass before it can say done.
---
Q: Walk me through the agent loop and where you would add safety.
TAG: ai
A: The harness sends the task and tool definitions; the model either answers or returns tool calls; the harness runs the tools and sends results back; repeat. Safety goes in the harness because that is where execution happens: allow-listed tools only, read-only credentials for data, a human approval gate for anything irreversible (drops, deletes, sends), step and cost budgets, a no-progress stop, and a full trace for audit.
---
Q: What is harness engineering?
TAG: ai
A: Treating the code around the model as the product. When the agent makes a mistake, I change its environment so the mistake cannot recur: a better tool, a verification step, tighter context, a guardrail. The five layers are tools and orchestration, verification, context and memory, guardrails, and observability. Example: an agent kept reporting success on broken SQL, so I made "done" require a passing row-count check.
---
Q: How do you reduce LLM cost in production without losing quality?
TAG: ai
A: Measure first with an eval set and a trace of tokens per task. Then: route each step to the smallest model that passes its eval; use prompt caching with stable content first; send only relevant context (retrieve rows, tail logs); cap output with structured short answers; batch non-urgent work; stop loops early. I report cost per successful task, not per call.
---
Q: How would you know a prompt change made things better?
TAG: ai
A: A fixed eval set of representative inputs with expected outputs, scored automatically (exact match, schema validation, or a rubric), plus cost and latency. I compare old vs new on the same set, look at the failures, and keep a held-out set to avoid tuning to the test.
---
Q: What goes into the context for a text-to-SQL assistant?
TAG: ai
A: Table and column descriptions, keys and joins, business definitions (what counts as an active rider), a few sample rows, two or three example questions with correct SQL, and rules (read-only, always filter on the partition column). Stable parts go first for caching; the user question goes last.
---
Q: Your scheduled AI job produced a wrong report and nobody noticed for a week. What do you change?
TAG: ai
A: Add verification and alerting: the job checks its own output (row counts, required sections, numbers reconcile to source) and fails loudly; failures page or post to Slack with the trace. Add a weekly human review of a sample, and turn every correction into an eval case so it cannot regress.
---
Q: When do you let the model "think" before answering?
TAG: ai
A: For multi-step reasoning: diagnosis, planning, design trade-offs, tricky SQL. Not for formatting, extraction or simple classification, where it only adds cost and latency. I decide per step using the eval: if accuracy does not improve, I turn it off.
