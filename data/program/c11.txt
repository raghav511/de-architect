## C11.1 What a subagent is

A **subagent** is a separate Claude with its own context window, its own instructions and its own tool list. The main session hands it a task; it works (reading files, searching, running tests) and returns only a summary. Two benefits:

1. **Context stays small.** The subagent reads twenty files; your main conversation receives ten lines. That saves tokens in every later turn and keeps the main agent focused.
2. **Focus.** A reviewer with a review checklist and read-only tools reviews better than a generalist halfway through implementing.

The cost: the subagent's own tokens, and some latency. Use subagents for broad searches, reviews and independent sub-tasks, not for one-line questions.

## C11.2 Defining one

Run `/agents` to create one interactively, or write a file in `.claude/agents/` (project, shared) or `~/.claude/agents/` (personal):

```markdown
---
name: pipeline-reviewer
description: Reviews pipeline code changes for correctness, idempotency, late data, security and privacy. Use after any change under pipeline/.
tools: Read, Grep, Glob, Bash
model: sonnet
---
You are a senior data engineer reviewing a change. Do not edit files.
Run `git diff` to see the change and `python3 -m unittest -q` to check tests.
Report at most 8 findings ranked by impact, each with file:line and a concrete failing input.
End with APPROVE or REQUEST CHANGES.
```

Claude delegates automatically when the task matches the description, or you ask: *"Use the pipeline-reviewer subagent on my changes."* Keep tools minimal: a reviewer does not need Edit.

## C11.3 Parallel work with worktrees

Two independent tasks in the same folder will collide. Git **worktrees** give each task its own folder on its own branch, sharing one repository:

```bash
git worktree add ../cc-amounts -b fix/amounts
git worktree add ../cc-loader  -b fix/loader
# terminal 1: cd ../cc-amounts && claude     terminal 2: cd ../cc-loader && claude
git merge fix/amounts fix/loader            # back in the main folder, after review
git worktree remove ../cc-amounts
```

Rules: only parallelise tasks that touch different files and do not need each other's results. One person still reviews each branch.

## C11.4 Choosing a pattern

| Pattern | Shape | Good for | Watch out |
|---|---|---|---|
| **Single agent** | one loop | most tasks | context growth on long tasks |
| **Explore with subagents** | main agent fans out searches | big codebases, research | summaries can drop details |
| **Writer and reviewer** | one writes, a fresh one reviews | quality on important changes | review needs a real checklist |
| **Orchestrator and workers** | a planner splits work, workers do parts in parallel | many independent pieces (migrating 40 models) | coordination cost; merge conflicts; several times the tokens |

Multi-agent systems can use several times the tokens of a single agent. Use them when the work is genuinely parallel or needs separate expertise, and measure whether quality or speed actually improved.

## Lab: a reviewer and two parallel fixes (40 minutes)

Fresh copy, `cd ~/cc-sandbox`.

1. Create `.claude/agents/pipeline-reviewer.md` from the lesson (or with `/agents`).
2. Make a small change yourself (for example, rename a variable in `ingest.py`), then ask: *"Use the pipeline-reviewer subagent on my changes."* Check its verdict and findings. Then `git checkout .` to undo your change.
3. Create two worktrees: `fix/amounts` (the EU amount bug) and `fix/loader` (SQL injection and the transaction in load.py).
4. Open two terminals and run `claude` in each worktree with a precise prompt. Let both work at the same time.
5. In each worktree, ask the reviewer subagent to review before you commit.
6. Merge both branches in the main folder, run the tests, and remove the worktrees.
7. Note: did the reviewer catch anything real? How long did the parallel work take compared with doing them one after another?

Q: Your manager wants a 5-agent system to migrate 40 SQL models to dbt. When is that worth it, and what would you measure?
MODEL: Worth it when the models are mostly independent and the per-model work is similar, so an orchestrator can split the work and workers run in parallel, each with tests to pass. Otherwise a single agent working model by model is cheaper and simpler. Measure correctness (row-count and checksum comparisons between old and new outputs per model), human review time, total tokens and cost compared with a single-agent baseline on a sample, wall-clock time, and merge conflicts. Start with a pilot of 5 models.

@@interview
Q: When would you use a multi-agent architecture instead of a single agent?
TAG: ai
A: When the work is genuinely parallel (many independent pieces), when sub-tasks need separate context or expertise (researcher, implementer, reviewer), or when one context would overflow. Otherwise a single agent is cheaper, simpler and easier to debug. Multi-agent systems can use several times the tokens and add coordination failures, so I prove the gain on a pilot with measured quality, cost and time.
---
Q: How do you keep an AI agent effective on a large codebase?
TAG: ai
A: Manage context. A short CLAUDE.md with a map of the repo, subfolder CLAUDE.md files for local rules, subagents for broad exploration so the main context stays small, precise @ references, one task per session, and good tests the agent can run in that area. For big changes, a plan first, then work split into independent chunks, possibly in parallel worktrees.
---
Q: Explain the writer and reviewer pattern and why it works.
TAG: ai
A: One agent implements; a second agent with a fresh context and a review checklist reviews the diff and runs the tests. The reviewer is not anchored to the writer's reasoning, so it catches different mistakes, much like human code review. It works best when the reviewer has a concrete checklist and must give evidence (a failing input) for each finding. A human still approves.
---
Q: What failure modes do you see in multi-agent systems?
TAG: ai
A: Duplicated or conflicting work when the split is unclear. Workers losing context the orchestrator had. Summaries that drop critical details. Merge conflicts. Runaway token cost. Agents agreeing with each other's mistakes. Mitigations: clear task boundaries and interfaces, shared tests as the source of truth, budgets per worker, structured handoffs, and a final verification step independent of the agents.
---
Q: How would you organise AI-assisted work across a team of engineers?
TAG: behavioral
A: Shared repo configuration (CLAUDE.md, settings, commands, reviewer subagents) so everyone gets the same baseline. Small, reviewable tasks. Parallelism through branches and worktrees, not shared folders. Clear ownership: each AI-assisted change has a human author accountable for it. A short weekly exchange of what worked and what did not, feeding back into the shared configuration.
