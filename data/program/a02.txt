## A2.1 Evals first

You cannot improve what you cannot score. An **eval** is a set of inputs with a way to judge outputs. Build it before you build the agent, the same way you write a test before fixing a bug.

**Three kinds of grader**, cheapest first:

| Grader | Use for | Example |
|---|---|---|
| Code (exact, regex, schema, run it) | Anything with a checkable answer | SQL returns the expected rows; JSON matches the schema; tests pass |
| Rubric with a model judge | Open-ended text with clear criteria | "Names the cause, quotes evidence, under 120 words" scored 0–3 |
| Human review | Taste, high stakes, calibrating the judge | Weekly sample of 20 outputs |

Rules of thumb:

- **20–50 cases** is enough to start. Include the boring common case, the edge cases, and every bug you have ever seen.
- Keep a **held-out** set you never tune on.
- For agents, grade the **final state** (did the table end up correct?) and look at the **transcript** (did it take a dangerous path to get there?).
- Run evals several times: models are not deterministic. Report pass@1 (single try) and pass^k (all k tries pass) for reliability.

## A2.2 Graders that do not lie

A model judge is itself a model. Make it reliable:

- Give it a **rubric with concrete criteria**, not "is this good?".
- Ask for the **criterion-by-criterion verdict before the score**.
- Use a **different model or prompt** from the one being judged where possible, and never show the judge the expected score.
- **Calibrate**: label 20 outputs yourself and check the judge agrees. If agreement is below about 80%, fix the rubric before trusting it.
- Prefer code graders whenever the answer can be executed. A passing test is evidence; a confident paragraph is not.

## A2.3 Reflection and self-critique

**Reflection** = generate, critique, revise. It helps when the critic can see something the generator missed: a failing test, a schema error, a rubric item. It often **does not** help when the same model re-reads its own answer with no new information; it may just become more confident or change correct answers.

So the strongest self-review loops bring in **external signal**:

```
draft  = model(task)
for i in range(3):
    feedback = verify(draft)          # tests, linters, SQL dry-run, rubric judge
    if feedback.ok: break
    draft = model(task, draft, feedback.errors)   # revise with evidence
```

The **Reflexion** idea adds memory: after a failure, the agent writes a short lesson in plain words ("Always check for NULL keys before joining") and reads its lessons at the start of the next attempt.

## A2.4 Self-fixing code agents

The pattern every coding agent uses:

1. Read the task and the failing test output.
2. Make **one small change**.
3. Run the tests.
4. If they fail, read the new error and go to 2. If they pass, run the full suite, then stop.

Guardrails that make it safe and honest:

- The agent may edit source files but **not tests** (check file paths in the tool).
- A budget on iterations and tokens.
- Run code in a **sandbox** (a container or temp dir) with no network and no secrets.
- Keep a diff of every change for review.

The same pattern fixes data: run `checks/check.py`, read failures, change the SQL, rerun.

## A2.5 Self-improving prompts

A prompt can be optimised like a model's weights, by search against a metric:

1. Start with a prompt and an eval set split into **train** and **held-out**.
2. Run on train; collect failures.
3. Ask a model to propose a better prompt given the failures (or add the best few-shot examples).
4. Keep the new prompt only if train accuracy goes up; report held-out accuracy.

Tools like DSPy automate this. The danger is **overfitting**: the prompt memorises the train cases. If held-out accuracy does not rise, you have not improved anything.

## A2.6 Memory: agents that learn from mistakes

Long-lived agents keep **files** as memory, because the model forgets everything between runs:

- **Instructions file** (like `CLAUDE.md` or `AGENTS.md`): how this repo works, commands, rules.
- **Lessons file**: one line per mistake and its fix, read at start.
- **Progress file** for long tasks: goal, done, next, open questions; lets a fresh context resume.
- **Skills**: reusable instructions plus scripts for a task type, loaded only when needed.

Prune memory: old or wrong lessons cost tokens and mislead.

## A2.7 Guardrails for agents that act on their own

The more autonomous the agent, the stronger these must be:

1. **Least privilege**: read-only credentials by default; write access only to a staging area.
2. **Approval gates** for irreversible actions: deletes, drops, sends, payments, merges to main.
3. **Budgets**: steps, tokens, money, wall-clock time.
4. **Prompt injection defence**: treat every document, web page and tool output as data, never as instructions; never let fetched text widen permissions.

An autonomous agent without these is not autonomous, it is unsupervised.

## Grader design drills (30 minutes)

Choose the grader for each task, then check the model answers.

1. An agent writes SQL for "daily active riders by city".
2. A summary of an incident for the on-call channel.
3. A JSON classification of log lines.
4. An agent that fixes a failing dbt test.
5. A design doc for a streaming pipeline.

**Model answers:** 1, run the SQL on a fixture database and compare rows with the reference (code grader). 2, rubric judge (cause, impact, timeline, next step, under 150 words) calibrated on 20 human-labelled examples. 3, schema validation plus exact match on the label. 4, final state: the dbt test passes and no test file changed; plus transcript check for forbidden commands. 5, human review with a rubric; a model judge can pre-screen for missing sections.

@@interview
Q: How do you evaluate an LLM feature before shipping it?
TAG: ai
A: I build an eval set first: 30–50 representative inputs, edge cases and past bugs, with a held-out split. Graders in order of preference: code (execute and compare), rubric-based model judge calibrated on human labels, then human review for a sample. I track accuracy, cost and latency, run several trials for reliability, and gate releases on not regressing.
---
Q: Does asking a model to review its own answer improve it?
TAG: ai
A: Only reliably when the review brings new information: test failures, schema errors, a rubric, retrieved facts. Same-model re-reading without evidence often just raises confidence. So my self-review loops are verify-then-revise: run the checks, feed the errors back, cap iterations.
---
Q: Design a self-fixing agent for failing dbt tests.
TAG: ai
A: Tools: read model files, write model files (not tests or sources), run `dbt build --select model+`, query a staging schema read-only. Loop: run the failing test, read the compiled SQL and failure rows, make one change, rerun; stop on pass, on budget, or on repeated failure. Guardrails: runs against a dev target, never prod; diff captured for a pull request; human approval to merge. Eval: a set of broken models with known fixes, graded on tests passing and no test files changed.
---
Q: What is the risk of automatic prompt optimisation and how do you control it?
TAG: ai
A: Overfitting to the train cases and silently breaking unseen ones. I split train and held-out, only accept changes that improve held-out, keep the prompt in version control with its scores, and re-run the full eval when the model version changes.
---
Q: How do agents remember things between runs?
TAG: ai
A: Through files the harness loads: an instructions file for the repo, a lessons file of past mistakes, a progress file for long tasks, and skills loaded on demand. Memory is pruned and reviewed like code, because stale memory misleads.
---
Q: What guardrails would you require before letting an agent run unattended against your data platform?
TAG: ai
A: Read-only by default, writes only to a staging schema; approval for drops, deletes, merges to main and anything external; budgets on steps, tokens, money and time; content treated as data to block prompt injection; full traces and alerts; and an eval suite that must pass before each version is deployed.
---
Q: How do you make an LLM judge reliable?
TAG: ai
A: Concrete rubric, verdict per criterion before a score, a different model or prompt from the generator, and calibration: I label 20 outputs myself and require high agreement before trusting it. I re-check calibration when models change.
---
Q: An agent's success rate dropped after a model upgrade. How do you find out why?
TAG: ai
A: Re-run the eval on both versions, diff failures by category, and read transcripts of newly failing cases. Common causes: changed tool-calling behaviour, stricter refusals, different default verbosity breaking parsers. Fix with prompt or tool changes, pin the model version until the eval passes again.
