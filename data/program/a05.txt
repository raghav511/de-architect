## A5.1 RAG is a data pipeline

Retrieval-augmented generation answers a question using your documents: find the most relevant passages, put them in the prompt, ask the model to answer from them and cite them. Two paths:

- **Ingest path (batch or streaming):** read sources (runbooks, tickets, wiki pages, contracts), clean, split into chunks, redact personal data, embed, and write chunks with metadata to an index.
- **Query path (online):** embed the question, filter by metadata the user may see, search for the top k chunks, optionally re-rank, build the prompt, answer with citations.

Everything you learned about pipelines applies to the ingest path: idempotent runs, incremental loads, lineage from chunk back to source document and version, quality checks, backfills when the embedding model changes. The query path is a service: latency, access control, caching and logs.

**Say it:** "RAG is an ingest pipeline that builds an index and a query service that reads it. Most of the work is the pipeline."

## A5.2 Chunking and embeddings

An **embedding** is a list of numbers that places text in space so that similar meanings land close together. Similarity is usually cosine: the angle between two normalised vectors.

**Chunking** decides what can be found:

- Too big, and one chunk mixes topics, so its vector is blurry and the prompt fills with noise.
- Too small, and an answer split across a boundary is never retrieved whole.
- A sensible start: 200 to 400 words with 10 to 20% overlap, split on headings and paragraphs where possible. Keep the heading path ("Runbook > Kafka > Consumer lag") in the chunk metadata and often in the text.

Store with each chunk: `doc_id`, `chunk_no`, text, `content_hash`, `embedding_model`, `embedded_at`, and access labels. A new embedding model means a full re-embed into a new index, compared on your eval set before you switch.

**Say it:** "Chunk on structure with overlap, store lineage and the model name with every vector, and re-embed into a new index when the model changes."

## A5.3 Where vectors live

You do not need a new database on day one.

- **Postgres with pgvector:** vectors next to the application data, with transactions and the access rules you already have. Enough for most teams up to tens of millions of vectors with an approximate index (HNSW or IVF).
- **The warehouse or lakehouse:** vector types and similarity functions in SQL (DuckDB, Snowflake, Databricks, BigQuery). Good for analytics and batch retrieval, and the data never leaves.
- **A dedicated vector database:** very large scale, very low latency, heavy filtering at high query rates.

Exact search compares the query with every vector; approximate indexes trade a little recall for a lot of speed. Measure recall at k with and without the index before you trust it.

**Hybrid search** combines keyword ranking (good for exact names, error codes, ticket ids) with vector ranking (good for meaning). Most production systems use both, plus metadata filters such as team and date.

**Say it:** "Start where the data lives, pgvector or the warehouse; move to a vector database only for scale or latency; use hybrid search with filters."

## A5.4 Keeping the index fresh

A stale index gives confident wrong answers from deleted or outdated documents. Treat it like any derived table:

- **Change detection.** Hash each document's text. Re-embed only new or changed documents; delete chunks of documents that disappeared. Full re-embeds every night are the most common cost leak.
- **CDC.** If documents live in a database, stream changes (inserts, updates, deletes) from the log, as in module 6, and apply them to the index. Deletes matter most: "right to be forgotten" applies to vectors too.
- **Idempotent upserts.** Key chunks by `(doc_id, chunk_no, content_hash)` so a retry does not duplicate.
- **Freshness metrics.** Lag between a source change and the index, and the count of chunks whose source no longer exists.

**Say it:** "Hash or CDC to embed only what changed, delete what was removed, upsert idempotently, and alert on index lag."

## A5.5 LLM extraction as ETL, and privacy

Models can turn unstructured text into rows: the city, fare and date from a complaint email; the parties and dates from a contract. That is an ingestion job with an unreliable source, so give it the same contract:

- **A schema** for the output, checked in code (types, formats, allowed values).
- **One bounded retry** with the validation error, then a **dead-letter table** for rows that still fail, reviewed by a person.
- **Version columns:** model, prompt version, extracted_at, so you can backfill deliberately.
- **A labelled sample** to measure field accuracy.

**Privacy.** Prompts, logs, caches and vector indexes are new copies of your data. Redact personal data (emails, phone numbers, names where possible) at ingestion, before text reaches a model or an index. Keep access labels on every chunk and filter by them at query time, so a person only retrieves what they may read.

**Say it:** "Extraction is ingestion with a schema, a bounded retry and a dead-letter table. Redact before the model and the index, and filter by access at query time."

## A5.6 Measuring RAG

Measure the two halves separately.

- **Retrieval:** a set of questions, each labelled with the chunks that answer it. **Recall at k** is the share of those chunks in the top k. If recall is low, fix chunking, filters and hybrid search before touching the prompt.
- **Generation:** is the answer supported by the retrieved chunks (faithfulness), does it answer the question, does it cite correctly? Use code checks where possible (citation ids exist) and a rubric judge calibrated on human labels for the rest.
- **Operations:** latency per stage, cost per answer, cache hit rate, index lag.

Run the eval on every change of chunking, embedding model, index settings or prompt.

**Say it:** "Recall at k for retrieval, faithfulness for generation, both on a labelled set, rerun on every pipeline change."

## A5.7 Retrieval at scale: rewrite, fuse, rerank, filter by permission

A demo searches one index with the user's raw question. A production system at 10 million documents runs a short pipeline on every query, each step cheap enough to fit the latency budget:

1. **Rewrite the query.** Users type "why is it slow again?" in the middle of a conversation. A small, fast model rewrites it into a standalone search query ("Kafka consumer lag on the payments topic"), expands acronyms, and for a question with two parts writes one query per part. Two other tricks: several phrasings of the same question (multi-query), and searching with a short hypothetical answer instead of the question (HyDE), because an answer looks more like the documents than a question does. Each costs one extra model call, so cache rewrites by conversation state and skip them for short keyword queries.
2. **Search two ways and fuse.** Keyword search (BM25) finds exact names, error codes and ticket ids; vector search finds meaning. Their scores are on different scales, so do not average them. **Reciprocal rank fusion (RRF)** uses only positions: each document scores `sum over lists of 1 / (60 + rank)`, so a document near the top of both lists wins. It needs no tuning and no score normalisation.
3. **Rerank the top 50 to 100.** First-stage search embeds the question and each chunk separately, so it cannot see how they relate. A **cross-encoder reranker** reads the question and one passage together and scores how well that passage answers it, which is much more accurate and much slower: run it only on the fused candidates, then keep the best 5 to 10 for the prompt. Typical cost: 50 to 150 ms for 50 passages on a GPU, or a per-call price from a hosted rerank API.
4. **Filter by what this user may read, before ranking.** Every chunk carries the access labels of its source document (groups, tenant, classification). The query path looks up the user's groups and passes them as a filter into the search itself (pre-filtering). Filtering after ranking (post-filtering) can leave too few results, and anything filtered after the model sees it has already leaked. Never ask the prompt to enforce permissions.

**Permissions stay in sync with the source.** A document shared or unshared in the wiki must change its chunks' labels within minutes: carry permission changes through the same CDC or change detection as content (A5.4), and include deletes. Tenants who must never mix (customers of a SaaS product) get separate indexes or partitions, not just a filter. Caches of answers are keyed by the permission set, or they serve one user's answer to another.

**A latency budget** for a 2-second answer, roughly: rewrite 100 to 200 ms (often skipped), embed the query 10 to 30 ms, keyword and vector search in parallel 20 to 50 ms, rerank 50 to 150 ms, and the rest for the model to start and stream its answer. Measure each stage separately (A5.6).

**Say it:** "Rewrite the question, search keywords and vectors in parallel, fuse with RRF, rerank the top 50 with a cross-encoder, and filter by the user's permissions inside the search, with labels kept in sync by CDC."

## A5.8 Answers you can trust: conflicts, citations, abstaining, long context, GraphRAG

**Conflicting and stale sources.** Two runbooks give different timeouts; last year's pricing page is still indexed. Retrieval cannot tell which is right unless you tell it. Store `effective_date`, `version`, `source` and an authority tier (policy over wiki over chat) with every chunk, prefer the newest authoritative chunk when two disagree, collapse near-duplicate chunks before the prompt, and tell the model what to do with a conflict: answer from the most authoritative source and say that another source disagrees, with both citations. Old versions that must stay searchable are filtered by date, not deleted.

**Citations you can check.** Ask for an answer in which every claim names the chunk ids it comes from, in structured output. Then check in code: every cited id was in the prompt, and any quoted text appears in that chunk. A citation that fails the check is removed, and the claim with it. Show citations as links to the source document and version, so a reader can verify in one tap.

**Hallucination** means a claim the sources do not support. Reduce it in three places:

- **Before:** retrieve better (A5.7). Most made-up answers start as a retrieval miss the model fills from memory.
- **During:** tell the model to answer only from the sources and to reply "I could not find this in the documents" otherwise, and give it a way to do that in the output schema.
- **After:** a **groundedness check** splits the answer into claims and asks a small judge model (or a natural-language-inference model) whether each claim is supported by the cited chunk. Unsupported claims are removed or the whole answer is replaced by an abstention.

**Abstaining is a feature.** If the best reranker score is below a threshold you tuned on labelled data, do not call the model at all: say what you searched and offer the closest documents. Put unanswerable questions in the eval set and track two numbers: the share of answerable questions answered, and the share of unanswerable ones correctly refused. A system that never says "I don't know" is guessing.

**Long context instead of RAG.** Models now read hundreds of thousands to a million tokens, so for a small, stable corpus (a few contracts, one codebase, a policy manual) the simplest system puts the whole thing in the prompt, with prompt caching to cut the repeated cost. RAG still wins when the corpus is large or changes, when users may see different subsets (permissions), when you need citations to exact passages, and on cost and latency at high query rates: every long-context query pays for every token, and quality drops for facts buried in the middle of a very long prompt. A common middle way: retrieve the best few documents, then give the model those documents whole.

**GraphRAG in one page.** Vector search answers "what does this passage say" well and "what are the main themes across 50,000 tickets" or "which suppliers of our top customers had incidents" badly, because the answer is spread over many documents. GraphRAG (published by Microsoft Research in 2024) uses a model to extract entities and relations from every document into a knowledge graph, groups the graph into communities, and writes a summary of each; a global question is answered from the community summaries, a multi-hop question by walking the graph. The costs: indexing calls a model over the whole corpus (often 10 to 100 times the cost of embedding it), the extracted graph has its own errors, and keeping it fresh is hard. Use it for exploratory and multi-hop questions over a stable corpus; if you already have the relations in tables (customers, suppliers, incidents), a SQL join or a graph you already own is cheaper and exact.

**Say it:** "Store dates and authority with each chunk and say when sources conflict; check citations in code; abstain below a tuned score and measure refusals; use long context for small stable corpora and RAG for large, changing or permissioned ones; GraphRAG only for global or multi-hop questions worth its indexing cost."

## A5.9 Architect's lens: RAG and vector stores

The questions an architect is asked about retrieval-augmented generation: when it is the right tool, where the vectors live, and what breaks at 10 million documents and 1,000 queries a second.

| Question | Short answer for RAG and vector stores |
|---|---|
| **What problem does it solve?** | Answering questions from your own documents, which change daily and differ by user, with citations, without retraining a model. Retrieval picks the few passages that matter; the model writes the answer from them. |
| **Why it over the alternatives?** | Fine-tuning teaches style and format, not fresh facts, and cannot forget a deleted document or respect permissions. Long context works for a small, stable corpus but pays for every token on every query. Plain keyword search finds documents but does not answer. For vectors, pgvector or the warehouse keeps them next to the data and its access rules; a dedicated vector database (Pinecone, Weaviate, Qdrant, Milvus, or OpenSearch and Elasticsearch vectors) earns its place at hundreds of millions of vectors, high query rates or heavy filtering. |
| **When not to use it?** | The corpus fits in the context window and rarely changes (use long context with prompt caching); the answer is a number in a table (use SQL or a semantic layer, not text search); the question needs reasoning across the whole corpus (themes, multi-hop: GraphRAG or analytics); nobody will build an eval set, so nobody will know whether it works. |
| **Who owns and pays for it?** | The data platform team owns the ingest pipeline (chunking, embeddings, freshness, deletes, permission labels) like any derived table; the product team owns prompts, the eval set and answer quality; security owns the permission model. Cost: embedding the corpus (and again on every model change), the index's memory, rerank calls, and model tokens per answer, usually the largest line. |
| **Where does it sit?** | Between the document sources (wiki, tickets, drives, databases) and the assistant: an ingest pipeline that writes chunks, vectors and labels to an index, and a query service that rewrites, searches, fuses, reranks, filters and calls the model, behind an API with logs and per-stage latency. |
| **How does it fail and scale?** | It fails quietly: stale or deleted documents still answered from, a permission change not yet in the index, a new embedding model mixed with old vectors, recall dropping after an index setting change, and confident answers when nothing relevant was found. It scales by sharding the index (memory), adding replicas (query rate), quantizing vectors, caching rewrites and answers by permission set, and keeping the reranker on a small candidate set. |
| **When do you move off it?** | When long context becomes cheap enough for your corpus and query rate; when most questions turn out to be structured (move them to SQL); when you outgrow pgvector (shard, or move to a dedicated store); or when a managed search service with built-in permissions and connectors does the same job for less. |

### Under the hood

**1. How does an HNSW index find neighbours quickly, and what do its settings trade?**
<details><summary>Model answer</summary>

HNSW (hierarchical navigable small world) links every vector to its nearest neighbours in a graph with a few sparse layers on top. A search enters at the top layer, walks greedily towards the query, drops a layer, and repeats, so it visits a few thousand vectors instead of millions. `M` is the number of links per vector (more links: better recall, more memory), `ef_construction` is how hard the build searches for good links (slower builds, better graph), and `ef_search` is how many candidates a query keeps (higher: better recall, slower queries). Filters are the trap: if a filter removes most vectors, the graph walk runs out of matches and returns too few results. pgvector 0.8 added iterative index scans that keep searching until enough rows pass the filter; dedicated stores build filters into the walk. Always measure recall at k with the filter on, against exact search, before trusting the index (A5.3, A5.6).

</details>

**2. Why does a cross-encoder rerank better than the embedding search, and what does it cost?**
<details><summary>Model answer</summary>

An embedding model (a bi-encoder) turns the question and each chunk into vectors separately, so the chunks can be embedded once, ahead of time, and compared with a cheap dot product. It never sees the question and passage together, so it misses how they relate ("does this passage answer this question?" versus "is it about the same topic?"). A cross-encoder reads the question and one passage in a single pass and outputs a relevance score, which is much more accurate but cannot be precomputed: it costs one model pass per candidate per query. So you use both: the bi-encoder (with keyword search) narrows millions of chunks to 50 to 100 in milliseconds, and the cross-encoder reorders those in 50 to 150 ms. Using a large language model as the reranker is more accurate again and far more expensive; keep it for small, high-value queries.

</details>

**3. How does reciprocal rank fusion combine keyword and vector results, and why not average the scores?**
<details><summary>Model answer</summary>

BM25 scores are unbounded and depend on the query's words; cosine similarities sit between -1 and 1 and bunch together. Averaging them lets one scale dominate, and normalising them per query is fragile. RRF ignores scores and uses ranks: a document's fused score is the sum, over each result list, of 1 / (k + rank), with k = 60 by convention. A document ranked 1st by keywords and 3rd by vectors scores 1/61 + 1/63; one ranked 1st by vectors only scores 1/61. Documents both methods like rise to the top, and nothing needs tuning. Weighted fusion (more weight to one list) is a later step, chosen on the eval set. Many engines (OpenSearch, Elasticsearch, Weaviate, and Postgres with a few lines of SQL) do it for you.

</details>

**4. How do you make sure retrieval never shows a user a document they cannot open?**
<details><summary>Model answer</summary>

Copy the source's permissions onto every chunk as labels (user and group ids, tenant, classification) at ingest, and look up the user's groups from the identity provider at query time. Pass them as a filter into the search itself, so a forbidden chunk is never ranked, never sent to a reranker or model, and never counted. Keep labels fresh: permission changes and deletes flow through CDC or change detection like content, with an alert on how far the index lags the source. Separate tenants physically (an index or partition each) when a leak would be a breach. Key every cache (rewrites, retrieved chunks, answers) by the permission set. Test it: an eval with users from different groups, asserting that answers cite only documents each one may read. The prompt is never the control: a model told "do not reveal X" can still reveal it.

</details>

**5. Size a RAG service for 10 million documents and 1,000 queries a second with a 2-second answer budget.**
<details><summary>Model answer</summary>

Chunks: 10 million documents at about 5 chunks each is 50 million vectors. At 1,024 dimensions in 32-bit floats, that is 50M × 1,024 × 4 bytes, about 205 GB, plus the HNSW graph (roughly 100 to 200 bytes per vector, about 5 to 10 GB). Shrink it: 8-bit quantization is about 51 GB; binary quantization about 6.4 GB, re-scoring the top few hundred with full vectors. Spread the index over shards for memory and add replicas for the query rate; at roughly 100 to 300 queries a second per replica, 1,000 QPS needs about 4 to 10 replicas of each shard, plus headroom for a zone failure. Budget per query: embed 20 ms, keyword and vector search in parallel 50 ms, rerank 50 candidates 100 ms, and about 1.5 seconds for the model to stream the answer. Cache rewrites and frequent answers by permission set, which also keeps the service up when the model provider cuts your rate limit: the simulator's [RAG challenge](#/sim/sc/rag) breaks a service without a cache in front of the model. Cost is mostly model tokens: 1,000 QPS is 86 million answers a day, so the prompt size (5 chunks of 300 words, not 20) is the biggest lever. Re-embedding all 50 million chunks on a model change is a planned backfill into a new index, compared on the eval set before switching.

</details>

**6. How do you make an assistant say "I don't know" instead of making something up, and prove it works?**
<details><summary>Model answer</summary>

Three layers. Before the model: if the best reranker score is below a threshold tuned on labelled data, return "not found" with the closest documents and skip the model call. In the model: the instructions say to answer only from the numbered sources and give an explicit "not found" field in the output schema. After the model: check citations in code (every id was in the prompt, quoted text is in the chunk), then run a groundedness check that asks a small judge model whether each claim is supported by its cited chunk, removing unsupported claims or abstaining. Prove it with an eval set that includes unanswerable questions and questions whose answer changed: track the answer rate on answerable questions, the correct-refusal rate on unanswerable ones, and the share of claims that pass the groundedness check, and calibrate the judge against human labels before trusting it. Watch the same numbers on a sample of live traffic.

</details>

**Model answers:** 1, deletes are not applied to the index: handle deletes through hashing or CDC and alert on chunks whose source is gone. 2, hybrid search: keyword ranking finds exact codes that vectors blur; also keep the code in the chunk text. 3, embed everything into a new index, run the retrieval eval on both, switch when recall at k is equal or better, keep the old index until rollback is no longer needed. 4, it re-embeds every document every night; hash content and embed only new or changed documents. 5, access labels were not stored on chunks or not applied as a filter at query time; filter before ranking, by the user's permissions.

Q: Design a RAG assistant over 10 million documents at 1,000 queries a second, with a 2-second answer budget.
TAG: arch
A: Ingest: documents chunked on structure (about 50 million chunks), redacted, embedded, written with access labels, dates and source to a sharded index; changes, deletes and permission changes by CDC or hashing, with index lag alerts. Memory: 50M vectors at 1,024 floats is about 205 GB, so quantize (8-bit about 51 GB) and shard, with replicas for the query rate (roughly 4 to 10 per shard) and a zone of headroom. Query path: rewrite with a small model (cached), keyword and vector search in parallel with the user's permission filter inside the search, fuse with RRF, rerank the top 50 with a cross-encoder, answer from the top 5 with checked citations, abstain below a tuned score. Budget: about 200 ms to retrieve and rerank, the rest to stream the answer. Cost is mostly tokens, so keep prompts small and cache by permission set. Eval: labelled and unanswerable questions, recall at k, groundedness, refusal rate, per-stage latency.

Q: Two indexed sources give different answers to the same question. What should the assistant do?
TAG: arch
A: Never pick silently. Store effective date, version, source and an authority tier with every chunk; collapse near-duplicates; prefer the newest authoritative source; and have the model say that another source disagrees, citing both. Old versions stay searchable only when asked for by date. Fix the cause too: a stale document still indexed is a freshness bug (deletes and versions should flow through change detection), so report conflicts to the document owners.

Q: How do you stop a RAG assistant from showing someone a document they are not allowed to open?
TAG: arch
A: Permissions are data in the index: every chunk carries its source document's groups, tenant and classification, kept in sync by CDC or change detection, deletes included. At query time look up the user's groups and filter inside the search (pre-filter), so a forbidden chunk never reaches ranking, the reranker or the model; separate tenants physically when a leak would be a breach; key every cache by the permission set. Test it with users from different groups and assert answers cite only what each may read. Never rely on the prompt to enforce access.

Q: Design a runbook assistant for on-call engineers.
TAG: ai
A: Ingest: runbooks and past incident notes from the wiki and the ticket system, cleaned, split on headings into 300-word chunks with overlap, personal data redacted, embedded, stored in Postgres with pgvector with doc id, heading path, hash, model and team labels. Changes flow in by hash comparison or CDC, including deletes. Query: hybrid search filtered by team, re-rank the top 20, answer from the top 5 with citations, and say "not found" when nothing scores well. Eval: 50 real on-call questions labelled with the right chunks, recall at 5 and faithfulness, rerun on every change. Ops: latency per stage, cost per answer, index lag.

Q: When do you need a dedicated vector database?
TAG: ai
A: When the data is very large (hundreds of millions of vectors), query rates and latency targets are strict, or filtering at that scale is heavy. Before that, pgvector or the warehouse's vector functions keep vectors next to the data, under the same access rules and backups, with one less system to run.

Q: How do you keep a RAG index consistent with its sources?
TAG: ai
A: Treat it as a derived table. Hash each document; embed only new or changed ones; delete chunks for removed documents; upsert by doc id, chunk number and hash so retries are safe. For database sources, use CDC so deletes arrive too. Track lag from source change to index and the count of orphan chunks, and alert on both.

Q: How do you turn 5 million support emails into a table of structured fields?
TAG: ai
A: A batch extraction job: a JSON schema for the fields, a prompt with a few labelled examples, temperature 0 and a pinned model. Validate every reply in code; retry once with the error; dead-letter the rest for review. Cache by email hash and store model and prompt version with each row. Trial on 1,000 emails for cost and field accuracy against labels, then run incrementally.

Q: A RAG assistant's answers are wrong. How do you debug it?
TAG: ai
A: Split retrieval from generation. Check recall at k on labelled questions: if the right chunk is not retrieved, fix chunking, filters, hybrid search or re-ranking. If it is retrieved but the answer is wrong, check faithfulness: the prompt, the number of chunks, and whether the model is told to answer only from the sources. Also check freshness: stale or deleted documents in the index.
---
Q: How do you protect personal data in an AI pipeline?
TAG: ai
A: Redact at ingestion before text reaches a model, cache or index; keep access labels on every chunk and filter by the user's permissions before ranking; log prompts with the same retention and access rules as the source data; send data only to approved model endpoints with no training on our data; and make deletes flow through to the index.
