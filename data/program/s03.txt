## 3.1 From your code to tasks

Spark questions appear in 98% of the interview files you bought, and the internals come up in nearly half. Uber opens its senior loop with them. The goal of this chapter is that you can explain what Spark does with a query, find a problem in the Spark UI, and fix it in the right order.

Start with the vocabulary, because the UI is organised by it.

- An **application** is one driver and its executors.
- Every **action** starts a **job**.
- A job is cut into **stages** at each shuffle.
- A stage runs one **task** per partition.

A **narrow** transformation, such as `filter`, `select` or `withColumn`, computes each output partition from one input partition. Narrow steps are chained inside a stage. A **wide** transformation, such as `groupBy`, `join`, `distinct` or `repartition`, needs rows from many input partitions, so data must be redistributed. That redistribution is a **shuffle**, and it ends the stage.

```python
(trips.filter("event_type = 'completed'")      # narrow
      .groupBy("city").count()                 # wide: shuffle by city
      .show())                                 # action: starts the job
```

This runs as two stages. Stage 1 reads files, filters, and counts within each partition. Its tasks write their partial counts into shuffle files, grouped by the hash of `city`. Stage 2 reads those files, so each task receives every row for its set of cities, and finishes the count.

If an executor dies, Spark recomputes the lost partitions from the plan. This recomputation from **lineage** is how Spark tolerates failure without replicating intermediate data.

## 3.2 Catalyst, Tungsten and reading a plan

A DataFrame query passes through the **Catalyst** optimizer before anything runs. Catalyst resolves column names, applies rules to the logical plan, generates physical plans and picks one. The rules that matter most are the ones from sprint 2: filters are pushed toward the scan, unused columns are dropped, and constant expressions are folded.

**Tungsten** is the execution side. Rows are held in a compact binary format outside normal Java objects, and whole stages of the plan are compiled into a single generated function. This is why DataFrames outperform RDDs: Spark understands the operations, and it does not have to treat them as opaque functions.

A Python UDF breaks both. Catalyst cannot see inside it, and every row is serialised to a Python process and back. Prefer built-in functions. When you need Python, a vectorised pandas UDF moves data in batches and is far cheaper.

Read plans with `df.explain("formatted")`. These are the operators to recognise.

| In the plan | What it means |
|---|---|
| `FileScan` with `PartitionFilters` and `PushedFilters` | What was pruned and pushed down. Empty lists mean a full scan. |
| `Exchange hashpartitioning(city, 200)` | A shuffle by `city` into 200 partitions |
| `BroadcastExchange` | A small table being sent to every executor |
| `SortMergeJoin`, `BroadcastHashJoin`, `ShuffledHashJoin` | The join strategy chosen |
| `HashAggregate` appearing twice | Partial aggregation before the shuffle, final after it |
| `AdaptiveSparkPlan` | Adaptive execution is on, and the plan may change at run time |

Count the `Exchange` operators. Each one is a shuffle, and shuffles are where most Spark time and most Spark failures are found.

## 3.3 The shuffle

In a shuffle, every map task sorts its output by target partition and writes it to local disk. Every reduce task then fetches its share from every map task over the network. The cost is disk, network and serialisation, multiplied by the volume of data.

Two settings govern its shape. `spark.sql.shuffle.partitions` sets the number of partitions after a shuffle and defaults to 200. That number is right only by accident. Too few gives huge partitions that spill or run out of memory. Too many gives thousands of tiny tasks and small files. A reasonable target is 100 to 200 MB per partition, and adaptive execution will now merge small ones for you.

`repartition(n)` does a full shuffle and produces evenly sized partitions. It can increase or decrease the count. `coalesce(n)` only merges existing partitions and does not shuffle. It can only decrease the count, and the results can be uneven. Use `coalesce` to reduce file count before a write, and `repartition` when you need balance or a different key.

Reduce shuffle work by filtering and selecting before a join, aggregating before a join where the logic allows, broadcasting small tables, and reusing a partitioning across consecutive operations on the same key.

## 3.4 Join strategies

| Strategy | How it works | When Spark uses it |
|---|---|---|
| **Broadcast hash join** | The small table is sent to every executor and held in a hash map. The large table is never shuffled. | One side is under `spark.sql.autoBroadcastJoinThreshold`, 10 MB by default, or you add a `broadcast()` hint |
| **Sort-merge join** | Both sides are shuffled by the key and sorted, then merged | The default for two large tables with an equality condition |
| **Shuffled hash join** | Both sides are shuffled; a hash map is built per partition from the smaller side | One side is much smaller but too big to broadcast |
| **Broadcast nested loop, cartesian** | Every row is compared with every row | No equality condition. Avoid on large data. |

```python
from pyspark.sql import functions as F
enriched = trips.join(F.broadcast(zones), "zone_id")
```

The broadcast table must fit in the driver's memory and in each executor's. Broadcasting something large is a common way to run the driver out of memory.

## 3.5 Skew

Skew means a few keys hold most of the rows. After a shuffle, all rows for one key land in one partition, so one task receives most of the data. In the Spark UI's stage page the signature is unmistakable: the median task takes seconds, and the maximum takes most of an hour. Shuffle read size shows the same pattern.

At Meridian, Bengaluru has 80% of trips. A join or aggregation keyed by `city` sends 80% of the data to a single task. NULL keys cause the same thing, because every NULL hashes to the same partition.

There are five fixes. Apply them in this order.

1. **Check adaptive skew handling is on.** With adaptive execution, a partition counts as skewed if it is larger than five times the median and larger than 256 MB. Spark then splits it into several tasks and duplicates the matching rows from the other side. This costs nothing to enable and handles most sort-merge joins.
2. **Broadcast the other side** if it is small. With no shuffle, there is no skewed partition.
3. **Filter out NULL and junk keys** before the join if they cannot match anyway.
4. **Treat the hot key separately.** Join the hot key's rows with a broadcast of its one matching row, join the rest normally, and union the two.
5. **Salt the key.** Add a random number to the key on the large side, and replicate each row of the small side once per salt value.

```python
N = 16
salted_trips = trips.withColumn("salt", (F.rand() * N).cast("int"))
salted_cities = cities.withColumn("salt", F.explode(F.array([F.lit(i) for i in range(N)])))
joined = salted_trips.join(salted_cities, ["city", "salt"]).drop("salt")
```

Bengaluru's rows are now spread over 16 partitions. The cost is that the small side is 16 times larger. For an aggregation, salting takes two steps: aggregate by key and salt, then aggregate again by key alone.

## 3.6 Adaptive query execution

Before Spark 3, the plan was fixed before the job ran, using estimates that were often wrong. **Adaptive query execution** re-plans between stages using the real sizes of the shuffle output. It is on by default from Spark 3.2. It does three things.

- **Coalesces shuffle partitions.** Start with a high partition count, and small neighbours are merged toward a target size.
- **Switches join strategy.** If one side turns out to be small after filtering, a planned sort-merge join becomes a broadcast join.
- **Splits skewed partitions**, as described above.

Intuit's loop in your bank asks about moving from Spark 2 to Spark 3. Adaptive execution is the headline. The other changes worth naming are dynamic partition pruning, where a filter on a dimension table prunes partitions of the fact table at run time, better join hints, and stricter ANSI SQL and date parsing behaviour, which is where migrations usually break.

## 3.7 Memory, spill and out-of-memory errors

An executor's memory has three parts you need to know.

```
executor container
 ├─ JVM heap  (spark.executor.memory)
 │    ├─ unified memory, about 60% of heap
 │    │     ├─ execution: shuffles, joins, sorts, aggregations
 │    │     └─ storage: cached data          (the two borrow from each other)
 │    └─ user memory: your objects and UDF data
 └─ overhead  (spark.executor.memoryOverhead, at least 384 MB or 10% of heap)
       off-heap buffers, and the Python worker processes
```

When execution memory runs short, Spark **spills** to disk and continues, slowly. Spill columns in the UI are your early warning. When a single structure cannot spill, such as one enormous row group or a hash map for a skewed key, the executor fails with an out-of-memory error.

Match the error to the cause.

| Symptom | Likely cause | First response |
|---|---|---|
| `java.lang.OutOfMemoryError` on an executor | A partition too large: skew, too few partitions, or an exploding join | Fix the data shape: more partitions, handle skew, filter earlier |
| Container killed for exceeding memory limits | Overhead exhausted, often by Python UDFs or large off-heap buffers | Raise `memoryOverhead`; replace row UDFs with built-ins |
| Driver out of memory | `collect()` on a large result, or a broadcast that is too big | Remove the `collect`; write results out; lower the broadcast threshold |
| Job gets slower every day, then fails | Data grew and the partition count did not | Size partitions from data volume |

Walmart's loop asks: a job fails at 40%, how do you raise memory without adding executors? Raise `spark.executor.memory` or the overhead, or lower `spark.executor.cores`, because fewer tasks running at once in an executor means more memory for each. Say that, and then say that you would look for skew first, because adding memory to a skewed job only moves the failure to next month.

`cache()` stores a DataFrame after its first computation, in memory and spilling to disk. `persist()` is the same with a storage level you choose. Cache only what is reused by more than one action and is expensive to recompute, and call `unpersist()` afterwards. `checkpoint()` writes the data to reliable storage and discards the lineage. Use it to cut a very long plan, as in iterative jobs, and in streaming state.

## 3.8 Sizing a job

A method you can state in an interview:

1. **Partitions from data volume.** One terabyte at about 128 MB per partition is roughly 8,000 partitions for the widest stage.
2. **Cores from partitions and time.** Tasks per core depend on how long each takes. Measure one.
3. **Four or five cores per executor.** More than that and executors contend on I/O and garbage collection.
4. **Memory per executor from partition size.** Each task needs several times its partition size while joining or sorting, and the executor runs one task per core.
5. **Dynamic allocation** adds executors when tasks queue and releases them when idle. It needs shuffle data to survive executor removal, through an external shuffle service or shuffle tracking.

On YARN, executors are containers on a Hadoop cluster. On Kubernetes, the driver and each executor are pods. In **cluster** mode the driver runs inside the cluster; in **client** mode it runs where you launched the job. Production jobs use cluster mode, so the job does not depend on a laptop or an edge node staying up.

## 3.9 Tools that read evidence

Your agent has only read log files so far. This sprint it gets tools that return *computed facts* about a Spark job.

The design rule: **code does the counting, and the model does the reasoning.** A Spark event log is tens of megabytes of JSON. Handing it to a model is expensive and unreliable. Models are poor at arithmetic over thousands of lines and good at interpreting a twelve-row summary.

```python
import json, statistics
from collections import defaultdict

def stage_summary(event_log_path: str, top: int = 5) -> list[dict]:
    """Slowest stages with the numbers that reveal skew and memory pressure."""
    tasks = defaultdict(list)
    with open(event_log_path) as f:
        for line in f:
            e = json.loads(line)
            if e.get("Event") != "SparkListenerTaskEnd":
                continue
            info, m = e.get("Task Info", {}), e.get("Task Metrics") or {}
            read = m.get("Shuffle Read Metrics", {})
            tasks[e.get("Stage ID")].append({
                "secs": (info.get("Finish Time", 0) - info.get("Launch Time", 0)) / 1000,
                "shuffle_mb": (read.get("Remote Bytes Read", 0) + read.get("Local Bytes Read", 0)) / 1e6,
                "spill_mb": m.get("Disk Bytes Spilled", 0) / 1e6,
            })
    rows = []
    for stage, ts in tasks.items():
        secs = [t["secs"] for t in ts]
        rows.append({"stage": stage, "tasks": len(ts),
                     "median_task_s": round(statistics.median(secs), 1), "max_task_s": round(max(secs), 1),
                     "max_shuffle_read_mb": round(max(t["shuffle_mb"] for t in ts), 1),
                     "total_spill_mb": round(sum(t["spill_mb"] for t in ts), 1)})
    return sorted(rows, key=lambda r: -r["max_task_s"])[:top]
```

Field names in event logs vary a little between Spark versions, so check them against one of your own logs.

Three principles of tool design are visible here, and you can state them in an interview.

- **Small, shaped output.** Five rows with named fields, not raw log lines.
- **The diagnostic ratio is precomputed.** Median and maximum task time side by side is the skew signature. The model does not have to derive it.
- **A description that says when to use it.** The docstring is what the model reads to decide.

Add a second tool that returns `explain("formatted")` for a named query, and the agent can connect a slow stage to the operator that caused it.

Then do the part that matters most. Diagnose the job yourself first, and write your answer down. Only after that, run the agent and compare. An agent's diagnosis is a hypothesis. The UI is the evidence.

## 3.10 Architect's lens: Spark in a data platform

The questions an architect is asked about Spark, beyond how to write a DataFrame job.

| Question | Short answer for Spark |
|---|---|
| **What problem does it solve?** | Large batch transformations that do not fit on one machine: joins, aggregations and rewrites over terabytes of files in the lake, in SQL or Python, with the work split across many machines and retried when one fails. The same engine also runs micro-batch streaming and feature preparation for machine learning. |
| **Why it over the alternatives?** | Against Flink: Spark is batch first and simpler for large rewrites and backfills; Flink wins for low-latency, stateful streaming. Against DuckDB or Polars: those are faster and far cheaper while data fits on one machine (up to a few hundred gigabytes). Against warehouse SQL (Snowflake, BigQuery): no data copy, open table formats, Python and libraries next to SQL, and control of the compute bill, at the cost of tuning it yourself. Against Dask or Ray: a mature query optimizer and SQL for ETL; Ray is the better fit for GPU training and general Python tasks. |
| **When not to use it?** | Small data (a single-node engine finishes before a cluster starts); millisecond serving or lookups (use a database or cache); per-event stateful streaming with tight latency (Flink); transforms that are plain SQL over warehouse tables (dbt in the warehouse); when nobody will own cluster versions, sizing and cost. |
| **Who owns and pays for it?** | A platform team owns the runtime (Databricks, EMR, or the Spark operator on Kubernetes), cluster policies, versions, default configs and cost guardrails such as auto-termination and spot use. Pipeline teams own their jobs, their sizing and their data's skew; cost is tagged per job and shown back per team. |
| **Where does it sit?** | The compute layer over the lakehouse: it reads Parquet, Iceberg or Delta tables (and Kafka for streaming), is scheduled by Airflow or a job service, and writes tables that Trino, the warehouse or BI tools read. It is not a serving layer and not a database. |
| **How does it fail and scale?** | It scales by partitions and executors: more cores run more tasks at once, until a shuffle, the driver or one partition becomes the limit. It fails as a straggler task from skew, executor out-of-memory or container kills, heavy spill, shuffle fetch failures when executors (often spot) disappear, a driver that collects too much or plans millions of small files, and a bill that grows faster than the data. |
| **When do you move off it?** | When data shrinks to one machine (DuckDB, Polars), when the workload becomes low-latency streaming (Flink), when transforms are SQL that the warehouse runs cheaper (dbt), or when the work is GPU training and Python tasks (Ray). |

### What changed in Spark 4

Spark 4.0 (May 2025) is the current major line; 4.x releases build on it. Interviewers ask "what changed recently", and three answers matter.

- **Spark Connect** splits the client from the server. Your program is a thin client that sends unresolved query plans over gRPC to a long-running Spark server, which holds the driver, and gets results back as Arrow batches. For operations: a client crash or out-of-memory no longer kills the driver, clients and server can be upgraded separately, many users share one server, and clients exist beyond the JVM (Python without Java, plus Go, Swift and Rust clients). The catch: no RDD API or `SparkContext` on a Connect client, and UDFs still run on the server, so Python versions and libraries must match there. It arrived in 3.4; in 4.0 the Python and Scala DataFrame APIs work over it almost fully, and `spark.api.mode=connect` runs an existing app over it.
- **ANSI SQL mode is on by default** (`spark.sql.ansi.enabled=true`). Before 4.0, bad data was quietly turned into NULLs or wrong numbers. Now a cast of `'abc'` to INT, an integer overflow, division by zero or an array index out of range raises an error and fails the job. Upgrades break where jobs relied on the old silence: fix the data, or use `try_cast`, `try_divide` and `try_element_at` where NULL really is the right answer. Turning ANSI off is a temporary escape, not a fix.
- **The VARIANT type** stores semi-structured data such as JSON in a binary form: `parse_json` once, then read fields with `variant_get(v, '$.path', 'type')` without parsing text again on every query, and without fixing a schema up front as a STRUCT would. It is the middle ground between a JSON string (flexible, slow) and STRUCT columns (fast, rigid). Table formats are adding it too (Delta, Iceberg v3); shredding, which stores common fields as real columns, is newer, so check what your engine and format version support.

The internals below have held since Spark 3.x and still hold in 4.x; each answer says where a part was introduced.

### Under the hood

**1. What do the driver, the DAG, stages and tasks each do when you call an action?**
<details><summary>Model answer</summary>

Transformations only build a plan; nothing runs until an action such as `write` or `count`. The driver is the one process that holds the plan: it optimizes the query, builds a graph of the work (the DAG), and cuts it into stages wherever data must be shuffled between machines. Inside a stage, the narrow steps (filter, select, map) are chained and run as one task per partition. The driver's scheduler sends tasks to executors, preferring ones that already hold the data, retries a failed task (four times by default), and reruns a parent stage if its shuffle output is lost. So a job is one action, a stage is the work between two shuffles, and a task is one partition of one stage on one core. This has been the model since Spark 1.x; with Spark Connect the driver lives on the server rather than in your program.

</details>

**2. Why is a shuffle expensive, and how do broadcast joins and adaptive query execution avoid it?**
<details><summary>Model answer</summary>

A shuffle moves every row to the partition that owns its key. Each map task sorts and writes its output to local disk split by target partition; each reduce task then fetches its piece from every map task over the network. That costs serialization, disk writes and reads, network transfer, and a barrier: the next stage cannot start until the whole map side is done. A broadcast join avoids it by sending the small table to every executor as a hash map, so the large side is read in place and never moved. Adaptive query execution (added in Spark 3.0, on by default since 3.2) re-plans at each stage boundary from the real shuffle sizes: it switches a sort-merge join to a broadcast join when one side turns out small, merges many tiny shuffle partitions into fewer, and splits oversized ones.

</details>

**3. What is data skew, how do you spot it, and how does salting fix it?**
<details><summary>Model answer</summary>

Skew is one key holding far more rows than the rest, so after a shuffle one partition, and the one task that reads it, is many times larger. The stage page shows it: median task 10 seconds, maximum 30 minutes, and one task with most of the shuffle read. Try adaptive skew join first (Spark 3.0 and later), which splits a partition larger than five times the median and 256 MB. If that is not enough, salt: add a random number from 0 to N-1 to the hot key on the large side, and copy each row of the small side N times, once per salt value, so the join still matches. The hot key's rows now spread over N tasks. The cost is a small side N times larger, so salt only the hot keys and pick N from the measured skew. For aggregations, aggregate by key and salt first, then by key alone.

</details>

**4. How is executor memory divided, what is spill, and what usually causes out-of-memory errors?**
<details><summary>Model answer</summary>

Since Spark 1.6 (unified memory management), the heap (`spark.executor.memory`) keeps 300 MB reserved, then splits the rest: 60% (`spark.memory.fraction`) is unified memory shared by execution (shuffles, joins, sorts, aggregations) and storage (cached data), and the remaining 40% is user memory for your objects and Spark's metadata. Execution can evict cached blocks above the protected storage half, but not the reverse. Outside the heap, `memoryOverhead` (at least 384 MB or 10%) holds JVM internals, network buffers and Python workers. When a task's execution memory runs out, Spark spills sorted runs to disk and merges them later: slower, but the job survives. Out-of-memory comes from what cannot spill: a skewed partition or huge rows built by `explode`, a broadcast table larger than expected, `collect()` on the driver, too many cores sharing one executor, or Python and Arrow buffers that blow past the overhead so YARN or Kubernetes kills the container.

</details>

**5. What do Catalyst and Tungsten's whole-stage code generation actually do?**
<details><summary>Model answer</summary>

Catalyst is the optimizer. It resolves names against the catalog (analysis), rewrites the logical plan with rules such as predicate pushdown, column pruning and constant folding, then picks a physical plan, for example broadcast or sort-merge, from size statistics. Tungsten is the execution layer: rows live in a compact binary format, often off the Java heap, so there are fewer objects and less garbage collection. Catalyst dates from Spark SQL's first release (1.0) and Tungsten from 1.5; whole-stage code generation (Spark 2.0 and later) fuses a chain of operators, such as scan, filter, project and partial aggregate, into one generated Java function with a tight loop, instead of calling each operator once per row; operators marked with `*(n)` in `explain` run this way. A Python UDF is a black box to both: Catalyst cannot push filters through it, and rows must leave the binary format for a Python process. Built-in functions, or pandas UDFs over Arrow, keep the speed.

</details>

## Incident: one city has 80% of the rows (45 minutes)

The nightly job has gone from 20 minutes to 3 hours, and last night it failed at 40%.

1. **Reproduce it.** Regenerate data with the skew option, so Bengaluru has 80% of trips and 5% of events have a NULL `driver_id`. Turn adaptive execution off, set `spark.sql.autoBroadcastJoinThreshold` to `-1`, and give Spark 1 GB. Run the job. It will fail with a memory error or spill heavily. Either one is the symptom.
2. **Find it in the UI.** Open the failing stage and sort tasks by duration. Record the median, the maximum, and the shuffle read of the largest task. Then find the key: `trips.groupBy("city").count().orderBy(F.desc("count")).show()`.
3. **Fix one: remove what cannot match.** Filter out NULL `driver_id` before the driver join. Measure.
4. **Fix two: let Spark handle it.** Turn adaptive execution back on. Check the plan for the skew join marker. Measure.
5. **Fix three: salt.** With adaptive execution off again, salt the city join by hand as in section 3.5. Measure.
6. **Decide** which fix you would ship, and write one sentence on why.

TITLE: Evaluate a postfix expression
KIND: dsa
MIN: 13
TAG: dsa
SRC: Expedia, 5 YOE
PROBLEM:
Given a postfix expression of single-digit operands and the operators `+ - * /`, return its value. Division truncates toward zero.

`"231*+9-"` returns `-4`: 3 × 1 = 3, 2 + 3 = 5, 5 − 9 = −4.
SOLUTION:
```python
def eval_postfix(expr: str) -> int:
    stack = []
    for ch in expr:
        if ch.isdigit():
            stack.append(int(ch))
            continue
        b = stack.pop()          # right operand is on top
        a = stack.pop()
        if ch == "+":
            stack.append(a + b)
        elif ch == "-":
            stack.append(a - b)
        elif ch == "*":
            stack.append(a * b)
        else:
            stack.append(int(a / b))
    return stack.pop()
```

Operands wait on a stack until their operator arrives. The order of the two pops is the usual mistake: the first value popped is the right-hand operand, which matters for subtraction and division. Time and space are O(n). If asked about multi-digit numbers, split on spaces and treat each token as a number or an operator.

KIND: pyspark
MIN: 20
TAG: spark
PROBLEM:
`big` is a large DataFrame, heavily skewed on the column named by `key`. `small` has one row per key value.

Write `salted_join(big, small, key, n=8)` that returns the same rows as `big.join(small, key)` but spreads each key over `n` partitions by salting. The salt column must not appear in the output.
SOLUTION:
```python
from pyspark.sql import functions as F

def salted_join(big, small, key, n=8):
    salted_big = big.withColumn("_salt", (F.rand() * n).cast("int"))
    salted_small = small.withColumn(
        "_salt", F.explode(F.array([F.lit(i) for i in range(n)])))
    return salted_big.join(salted_small, [key, "_salt"]).drop("_salt")
```

Each row on the big side gets a random salt from 0 to n−1. Each row on the small side is copied n times, once for every salt, so whichever salt a big row drew, its match exists. The join key is now the pair, and a hot key's rows hash to n different partitions.

Be ready for three follow-ups. The cost is that the small side grows n times. For a skewed **aggregation**, salt, aggregate by key and salt, then aggregate again by key. And on Spark 3, try adaptive skew join first, because it does this for you without code.

@@interview
Q: Explain how jobs, stages and tasks are executed in Spark. How do you analyse them?
SRC: Microsoft, 4 YOE
TAG: spark
A: Each action submits a job. The scheduler turns the job's plan into a graph of stages, cutting wherever a shuffle is needed, and runs a stage once the stages it depends on are complete. Within a stage, narrow transformations are pipelined and one task runs per partition, on executors chosen for data locality where possible. Failed tasks are retried; lost shuffle output causes the parent stage to rerun. I analyse this in the Spark UI: the SQL tab shows the physical plan with time and rows per operator, the stage page shows task duration distribution, shuffle read and write, spill and garbage collection. That is where skew and memory pressure show up.
---
Q: Differentiate narrow and wide transformations, with examples and their performance impact.
SRC: Microsoft, 4 YOE
TAG: spark
A: In a narrow transformation each output partition depends on a single input partition: `map`, `filter`, `select`, `withColumn`, `union`. No data moves between executors, and consecutive narrow steps run as one pipeline. In a wide transformation an output partition needs rows from many input partitions: `groupBy`, `join` without broadcast, `distinct`, `orderBy`, `repartition`. That needs a shuffle, which writes to disk, transfers over the network and starts a new stage. Performance work in Spark is largely about having fewer and smaller shuffles: filter early, broadcast small tables, and avoid repartitioning on a key you are about to change.
---
Q: Explain the Catalyst optimizer and Tungsten. How do they help performance?
SRC: LinkedIn, 5 YOE
TAG: spark
A: Catalyst is the query optimizer. It parses a DataFrame or SQL query into a logical plan, applies rules such as predicate pushdown, column pruning and join reordering, generates physical plans and selects one using size estimates. Tungsten is the execution engine: it stores rows in a compact binary format off the Java object heap, which cuts memory use and garbage collection, and compiles whole stages into single generated functions so the CPU runs tight loops. Together they explain why DataFrame code beats hand-written RDD code, and why Python UDFs are slow: they are opaque to Catalyst and force rows out of Tungsten's format.
---
Q: Compare broadcast joins and shuffle joins. When do you use each, and what are the cost trade-offs?
SRC: LinkedIn, 5 YOE
TAG: spark
A: A broadcast join sends the small table to every executor, where it is held as a hash map; the large table is scanned once and never shuffled. It is the fastest join when one side is small, and it is immune to skew. Its costs are driver and executor memory, and the time to collect and ship the table. A shuffle join, usually sort-merge, repartitions both sides by the key. It scales to any size because it can spill, but pays for two shuffles and two sorts, and suffers from skew. I broadcast when one side comfortably fits in memory, raise the threshold or hint when statistics are wrong, and otherwise accept the shuffle.
---
Q: Shuffle join, broadcast join, sort-merge join: when do you use each?
SRC: Flipkart, 4 YOE
TAG: spark
A: Broadcast hash join when one side is small enough to hold in memory, roughly tens to a few hundred megabytes. Sort-merge join for two large tables on an equality key; it is the default because it handles any size by spilling. Shuffled hash join when both sides are too large to broadcast but one is much smaller, so building a per-partition hash map is cheaper than sorting both sides. Without an equality condition, Spark falls back to nested loop or cartesian joins, which I avoid on large data by rewriting the condition, for example bucketing a range join into equal-width bands first.
---
Q: How do you detect and fix data skew in a Spark job? Give at least three mitigation strategies.
SRC: LinkedIn, 5 YOE
TAG: spark
A: Detect it in the stage page: a large gap between median and maximum task time, and one task with far more shuffle read than the rest. Confirm by counting rows per key.

Q: How do you handle out-of-memory errors in Spark?
SRC: Google, 5 YOE
TAG: spark
A: First identify where: driver or executor, and which stage. Driver errors come from `collect`, large broadcasts or huge task counts; the fix is to stop pulling data to the driver. Executor errors come from oversized partitions: skew, too few shuffle partitions, exploding joins, or caching too much. I fix the data shape before the configuration: more partitions, skew handling, earlier filters, narrower rows. If the container is killed for exceeding limits, the overhead region is too small, typically with Python UDFs. Only then do I raise executor memory or reduce cores per executor. I also check spill and garbage collection time as early signs.

Q: What is the difference between `repartition()` and `coalesce()`? Give a use case for each.
SRC: LinkedIn, 5 YOE
TAG: spark
A: `repartition(n)` or `repartition(col)` performs a full shuffle and produces evenly distributed partitions, optionally by key. It can raise or lower the count. `coalesce(n)` merges existing partitions without a full shuffle and can only lower the count; the result may be uneven.

I use `repartition` before a write partitioned by date, so each date's rows come from one task and produce few files, or to rebalance after a heavy filter. I use `coalesce` to cut the number of output files at the end of a job cheaply. One caution: `coalesce(1)` can pull upstream work into a single task.

Q: When would you use `cache()`, `persist()` and `checkpoint()`?
SRC: Flipkart, 4 YOE
TAG: spark
A: `cache()` when a DataFrame is expensive to compute and reused by several actions in the same job, such as a cleaned dataset feeding three aggregations. `persist()` when I need a specific storage level, for example disk only for a large intermediate that should not compete with execution memory. I unpersist once the reuse ends. `checkpoint()` when lineage has become long enough to slow planning or make recovery costly, as in iterative jobs, or when I want the result to survive executor loss without recomputation. Caching a DataFrame used once, or caching before a filter that removes most rows, wastes memory.

Q: What is dynamic allocation in Spark, and how does it help?
SRC: Flipkart, 4 YOE
TAG: spark
A: With dynamic allocation, Spark requests executors when tasks are waiting and releases them after they have been idle for a set time, within configured minimum and maximum bounds. A job gets capacity during its heavy stages and gives it back otherwise, which improves utilisation on shared clusters and lowers cost. Because executors hold shuffle files, removing one could lose data, so it needs an external shuffle service or shuffle tracking. It suits batch jobs with varying stages. For streaming or very short jobs, fixed sizing is often more predictable, because acquiring executors takes time.

Q: Explain Adaptive Query Execution and its benefits for skew joins.
SRC: Intuit, 3 YOE
TAG: spark
A: Adaptive query execution re-optimises a query during execution, using actual statistics from completed shuffle stages. It coalesces small shuffle partitions toward a target size, converts a sort-merge join to a broadcast join when one side turns out to be small, and handles skew. For skew joins, it detects a shuffle partition much larger than the median and above a size threshold, splits it into several sub-partitions, and reads the matching partition of the other side once for each. The hot key is then processed by several tasks in parallel, with no salting code. It is on by default from Spark 3.2.

Q: How does Spark decide the number of partitions?
SRC: Databricks, 5 YOE
TAG: spark
A: It depends on the source of the DataFrame. When reading files, Spark splits them by `spark.sql.files.maxPartitionBytes`, 128 MB by default, so the count follows total size and file layout. After a shuffle, the count is `spark.sql.shuffle.partitions`, 200 by default, unless adaptive execution coalesces them. For RDDs created in memory, it follows default parallelism, usually the total cores. Explicit `repartition` or `coalesce` overrides these. Reading from Kafka gives one partition per topic partition. I size shuffle partitions from data volume, aiming for partitions of one to two hundred megabytes.

Q: Which metrics tell you whether a Spark job is running efficiently?

TAG: spark

Q: How do you estimate resources for a pipeline that ingests 1 TB a day?

Q: Why is a shuffle the most expensive thing in a Spark job, and how do you avoid one?
TAG: spark
A: Every row moves to the partition that owns its key: map tasks sort and write their output to local disk, reduce tasks fetch it over the network, and the next stage waits for the whole map side. That is serialization, disk, network and a barrier. Avoid it by broadcasting the small side of a join, filtering and pruning columns before wide steps, not repartitioning on a key you then change, bucketing tables that are joined often, and letting adaptive execution switch to broadcast and merge small partitions at run time.

Q: Explain how executor memory is divided, and the difference between spill and an out-of-memory error.
TAG: spark
A: After 300 MB reserved, 60% of the heap is unified memory shared by execution (shuffles, joins, sorts) and storage (cache), where execution can evict cache down to a protected half; the rest is user memory. memoryOverhead outside the heap holds JVM internals, network buffers and Python workers. Spill is when execution memory runs out and Spark writes sorted runs to disk to merge later: slow but safe. Out-of-memory is what cannot spill: a skewed or exploded partition, an oversized broadcast, collect() on the driver, too many cores per executor, or Python memory past the overhead, which gets the container killed.
---
Q: What changed in Spark 4 that matters for a platform, and what breaks when you upgrade?
TAG: spark
A: Three things. Spark Connect splits client and server: thin clients send query plans over gRPC to a long-running server that holds the driver, so a client crash cannot kill the driver, clients and server upgrade separately, and Python clients need no JVM; but there is no RDD API or SparkContext on a client, and UDF libraries must be installed on the server. ANSI mode is on by default: bad casts, overflow and division by zero now fail the job instead of producing NULLs or wrong numbers, so upgrades surface hidden data problems; fix the data or use try_cast and try_divide deliberately. And the VARIANT type stores JSON in a binary form that is queried without reparsing, between a slow JSON string and a rigid STRUCT.
