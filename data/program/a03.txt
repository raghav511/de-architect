## A3.1 Long-running agents

A task that takes hours (migrating 40 dbt models, backfilling a month) does not fit in one context window. Long-running harnesses split work into **sessions** that each start fresh and pick up from files:

- **Plan file**: the full list of sub-tasks with a status each. The first session writes it; later ones only update it.
- **Progress file**: what was done, what is next, open questions, links to evidence.
- **Checkpoints**: commit after each sub-task, so a bad step can be reverted and a crash loses at most one step.
- **One change per step**, verified before moving on. Agents that try to do everything at once leave half-finished work.
- **Initialiser + worker**: one agent sets up the environment and plan; workers each take the next open item.

Resumability is the test: kill the agent mid-task, start a new session, and it should continue from the files without redoing work.

## A3.2 Planning, budgets and honesty

Autonomous agents need explicit rules for when to stop:

- **Definition of done** per sub-task, checked by code (tests, row counts, checks).
- **Escalate instead of guessing**: if the same error appears three times, write the question to the progress file and stop.
- **Budget per sub-task and overall**; report cost per completed item.
- **Report with evidence**: every claim links to a log line, query result or test output.

## A3.3 Multi-agent systems

An **orchestrator** splits a task and gives parts to **subagents**, each with its own fresh context, then merges the results. It helps when parts are **independent and parallel** (research 6 sources, review 10 files). It hurts when parts are tightly coupled (one SQL model), because handoffs lose context and cost multiplies; multi-agent runs can use several times the tokens of a single agent.

Good patterns: **reviewer** agent with a different prompt checking the worker's output; **cheap small-model subagents** for search and summarising, a **large model** only for decisions.

## A3.4 MCP: tools as a standard

The **Model Context Protocol** is an open standard for giving agents tools and data. An **MCP server** exposes:

- **Tools**: functions the model can call (`run_sql`, `list_dag_runs`).
- **Resources**: read-only data (a table schema, a runbook).
- **Prompts**: reusable templates.

Any MCP-capable client (coding assistants, desktop apps, your own harness) can then use them. For data platforms: wrap your warehouse with a **read-only** role, limit rows returned, log every query, and never expose credentials to the model.

## A3.5 The on-call data agent

A complete design you will build in lab 10:

```
Airflow failure ──► trigger ──► agent
   tools: get_task_log(tail), get_dag_code, run_sql (read-only), get_recent_changes(git log),
          propose_patch (writes a branch + diff, cannot merge)
   loop:  read log tail → form hypothesis → gather evidence → verify with a query → propose fix
   stop:  confident with evidence → post report + diff, ask for approval
          budget hit or no progress → post what it knows and the open question
```

Evaluation: inject 10 known failures (schema change, OOM, late upstream, bad credentials, duplicate rerun). Score: correct cause, cited evidence, no unsafe action, minutes and cost per incident.

## A3.6 What is new in agents (October 2026)

The field moves weekly, so this section is refreshed by the program's weekly research update. Concepts worth knowing now, with reports to read:

- **Skills as an open standard.** Anthropic donated Agent Skills (instructions plus scripts an agent loads only when a task needs them) to the Agentic AI Foundation, MCP's home under the Linux Foundation. Treat skills as versioned team runbooks that keep the base prompt small and cacheable. (Anthropic)
- **Guardrails moving into the platform.** Databricks Unity Gateway now screens MCP tool calls and results for prompt injection (beta). Tool results are the main injection path into data agents, so this is the A3.4 guardrail layer as a managed service. (Databricks release notes)
- **Agents as ordinary pipeline steps.** Genie Code tasks in Lakeflow Jobs (GA) run an agent prompt as a job step. Apply the usual job rules: idempotency, retries, budgets and a queryable audit trail. (Databricks release notes)
- **Portable request shapes in the warehouse.** Snowflake added a Responses API to the Cortex REST API (preview), which makes a harness easier to move between providers while data stays governed in place. (Snowflake)
- **Incremental agents.** Claude Security now runs a deep baseline scan, then rescans only changed code weighted by risk, and closes or reopens findings as fixes ship: the incremental-processing pattern applied to agent cost. (Claude blog)
- **Always-on agents with approval gates.** Claude Duet (research preview) works on its own cloud computer, checks in on a schedule and asks before sensitive actions. The same design an always-on data agent needs before it touches production (A3.2). (Claude)

How to judge any new development: what problem does it remove, what does it cost per successful task, can you evaluate it on your own eval set within a day, and what new risk does it add?

## Agent design drills (30 minutes)

Critique each design, then check the model answers.

1. "An agent with admin credentials that fixes any failed DAG and reruns it."
2. "Ten subagents, each writes one part of the same SQL model."
3. "A nightly agent that summarises Slack and posts a digest."

**Model answers:** 1, excessive agency: give read-only tools, let it propose a patch on a branch, require approval to merge and rerun, add budgets and evidence. 2, tightly coupled parts: use one agent with a plan file, or one writer and one reviewer. 3, fine as a workflow, not an agent: fetch, summarise, post; treat message content as data (injection), cap length, idempotent per date.

@@interview
Q: Tell me about an agent you built that runs without a human.
TAG: ai
A: Use the on-call agent: trigger on Airflow failure; tools for log tail, DAG code, read-only SQL and git history; loop of hypothesis and evidence; output is a report and a proposed diff that waits for approval. Numbers: cause found in 8 of 10 injected incidents, zero unsafe actions, about N cents and M minutes per incident. One failure: it blamed the wrong table when two had similar names; fix was a describe_table tool and a rule to verify with a query before concluding.
---
Q: How do you design an agent for a task that takes many hours?
TAG: ai
A: Initialiser writes a plan file and sets up the environment; workers take one sub-task at a time in a fresh context, verify it with code, commit, and update a progress file. Budgets per item and overall; escalate on repeated failure; resumable from files at any point.
---
Q: When would you use multiple agents?
TAG: ai
A: When parts are independent and parallel, such as researching many sources or reviewing many files, and a reviewer agent with a different prompt for quality. Not for tightly coupled work, where one agent with a plan is cheaper and more coherent.
---
Q: What is MCP and why does it matter for data teams?
TAG: ai
A: An open protocol for exposing tools, resources and prompts to any agent client. A data team writes one governed MCP server for the warehouse and pipelines (read-only, limited, logged) and every assistant uses it, instead of each tool getting its own credentials and ad-hoc integration.
---
Q: How do you stop an autonomous agent from doing damage?
TAG: ai
A: Least privilege, approval gates for irreversible actions, budgets, sandboxed execution, content treated as data to prevent injection, traces and alerts, and an eval suite that includes attack cases.
---
Q: How do you keep up with AI developments without chasing hype?
TAG: ai
A: A weekly review of a few primary sources; for anything promising, I ask what problem it removes, its cost per successful task and its risks, and I test it on my own eval set within a day before adopting it.
---
Q: What would you measure to decide if agents are worth it for your team?
TAG: ai
A: Cost and time per resolved task compared with the human baseline, quality (rework rate, defects), and risk incidents. For coding agents, cost per merged PR and review time; for on-call, time to diagnosis and false-cause rate.
---
Q: How do you route work between small and large models?
TAG: ai
A: Per step, using the eval: classification, extraction and search on small models; diagnosis and design on large ones; escalate to the large model when the small one's confidence or a verifier fails. Track cost per successful task to confirm the routing saves money.
