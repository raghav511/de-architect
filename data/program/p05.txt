## P5.1 Exceptions: catch narrowly, fail loudly

```python
try:
    amount = int(row["amount"])
except KeyError:
    log.warning("row %s has no amount", row.get("id"))
    amount = None
except ValueError as e:
    raise BadRow(f"row {row['id']}: bad amount {row['amount']!r}") from e
else:
    pass          # runs only if no exception: keep the try block small
finally:
    pass          # always runs: cleanup
```

Rules that separate senior code from junior code:

1. **Catch the specific exceptions you expect and can handle.** `except Exception:` around a whole job, or a bare `except:`, also swallows typos (`NameError`), bugs and Ctrl+C, and turns a crash into silent wrong data.
2. **Keep the `try` block small**, around the one line that can fail, so you know what failed.
3. **Add context when you re-raise.** `raise NewError("...") from e` keeps the original traceback attached as `__cause__`.
4. **Never swallow silently.** If you decide to skip a row, count it and log it (or send it to a dead-letter store). Exercise 4 does this.
5. **Custom exceptions** (`class BadRow(ValueError): pass`) let callers handle your failures specifically, while still being caught by `except ValueError`.

```
Exception hierarchy (part)
BaseException
 ├── KeyboardInterrupt, SystemExit      <- a bare except: catches these too
 └── Exception
      ├── ValueError ── your BadRow
      ├── KeyError, IndexError (LookupError)
      ├── TypeError
      └── OSError ── ConnectionError, FileNotFoundError, TimeoutError
```

## P5.2 Retries belong to transient errors only

Some failures fix themselves (network blips, rate limits, a database failover): retry them with **exponential backoff**, waiting 1, 2, 4, 8 seconds, plus random **jitter** so a thousand clients do not retry in the same instant. Other failures are bugs or bad data (a `KeyError`, a schema mismatch): retrying just repeats the failure, so raise immediately.

```python
def retry_call(fn, attempts, base_delay, sleep, retry_on=(ConnectionError, TimeoutError)):
    ...
```

Passing `sleep` in as an argument (**dependency injection**) is what makes this testable: tests pass `slept.append` and finish instantly, production passes `time.sleep`. The same trick applies to clocks, HTTP clients and database connections. Exercise 5 is exactly this function.

## P5.3 Context managers: cleanup you cannot forget

A `with` block guarantees setup and teardown, even when the body raises:

```python
with open(path) as f:              # file closed afterwards, always
with lock:                         # lock released
with conn.transaction():           # commit on success, rollback on error
```

Under the hood, `with` calls `__enter__` at the start and `__exit__(exc_type, exc, tb)` at the end. `exc_type` is `None` on a clean exit. If `__exit__` returns `True`, the exception is **swallowed**; return `False` (or nothing) to let it continue.

```python
class Transaction:
    def __init__(self, conn): self.conn = conn
    def __enter__(self):
        self.conn.execute("BEGIN"); return self
    def __exit__(self, exc_type, exc, tb):
        self.conn.execute("COMMIT" if exc_type is None else "ROLLBACK")
        return False                     # do not hide the error
```

For simple cases, a generator with `@contextmanager` is shorter: code before `yield` is setup, after it is teardown, and `try/finally` makes the teardown run on errors.

```python
from contextlib import contextmanager
import time

@contextmanager
def timer(stats, name):
    t0 = time.perf_counter()
    try:
        yield
    finally:
        stats[name] = time.perf_counter() - t0
```

## P5.4 Logging instead of print

`print` goes to stdout with no time, level or source. `logging` gives you all three, and lets operators turn detail up or down without code changes.

```python
import logging
log = logging.getLogger(__name__)          # one logger per module

logging.basicConfig(level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s %(message)s")

log.info("loaded %d rows into %s", n, table)      # lazy formatting: args, not f-string
log.warning("skipped %d bad rows", bad)
log.exception("load failed for %s", table)        # inside except: adds the traceback
```

| Level | Use for |
|---|---|
| DEBUG | detail you only want while investigating |
| INFO | normal milestones: started, loaded n rows, finished |
| WARNING | something odd but handled: skipped rows, a retry |
| ERROR | an operation failed |
| CRITICAL | the process cannot continue |

In production, log **structured** fields (JSON with `run_id`, `table`, `rows`) so you can search and aggregate. Your on-call agent in DE 9 reads these logs: the better they are, the better its diagnosis. Never log secrets or personal data.

## P5.5 Testing with pytest

pytest finds files named `test_*.py` and functions named `test_*`, and uses plain `assert`:

```python
# test_cleaning.py
import pytest
from cleaning import parse_amount, BadAmount

def test_parses_rupees():
    assert parse_amount(" ₹12.50 ") == 12.5

@pytest.mark.parametrize("text", ["", "12,5x", "abc"])
def test_rejects_bad_amounts(text):
    with pytest.raises(BadAmount):
        parse_amount(text)

@pytest.fixture
def sample_rows():
    return [{"id": 1, "amount": "10"}, {"id": 2, "amount": "x"}]

def test_bad_rows_go_to_dead_letter(sample_rows):
    result = load_batch(sample_rows)
    assert result["failed"][0][0] == 2
```

- **parametrize** runs one test over many inputs.
- **fixtures** build reusable test data or resources; built-ins include `tmp_path` (a temporary folder) and `monkeypatch` (replace an environment variable or function).
- Test the edges: empty input, None, duplicates, the boundary values, and the failure path.
- A data pipeline's tests usually come in three layers: unit tests of pure functions (fast, many), a few integration tests against a real local database or DuckDB, and data quality checks on real tables (DE 9).

## P5.6 Project layout, environments and config

```
meridian-ingest/
├── pyproject.toml          # name, version, dependencies, tool settings
├── src/meridian_ingest/
│   ├── __init__.py
│   ├── __main__.py         # python -m meridian_ingest
│   ├── extract.py
│   └── transform.py
└── tests/
    └── test_transform.py
```

- One **virtual environment** per project: `python3 -m venv .venv && source .venv/bin/activate`, or a tool such as uv. Never install into the system Python.
- **Pin** dependencies for deployable jobs (a lock file) so a new library release cannot break Tuesday's run.
- `if __name__ == "__main__":` guards code that should run only when the file is executed, not when imported.
- **Config and secrets come from the environment**, not the code: `os.environ["WAREHOUSE_URL"]`. Commit a `.env.example` with placeholder values and keep the real `.env` out of Git (Git lesson 8 shows how to remove a secret that was committed).

```python
class Quiet:
    def __enter__(self): return self
    def __exit__(self, *a): return True
with Quiet():
    1 / 0
print("after")
```
<details><summary>Answer</summary>

`after`. Returning `True` from `__exit__` swallows the `ZeroDivisionError`. That is almost always a bug outside of something like `contextlib.suppress`.

Q: Explain what a context manager guarantees and give two data engineering examples.
MODEL: It guarantees that setup and teardown happen around a block, and that teardown runs even if the block raises: `__exit__` (or the code after `yield` in a `finally`) always runs. Examples: a database transaction that commits on success and rolls back on error; a file or object-store writer that is closed and flushed; a lock or lease released; a timer that records how long a step took even when it failed.

@@interview
Q: How do you handle bad records in a batch pipeline?
TAG: py
A: Decide per error type. Bad rows are expected, so I catch the specific conversion and validation errors per row, write the row with the error message, source file and run id to a dead-letter table, count them, and continue. I set a threshold: if more than, say, 1% of rows fail, the job fails, because that signals an upstream change rather than a few bad rows. Unexpected exceptions are not caught; they fail the task loudly. A dashboard on the dead-letter table and an alert on the threshold close the loop.
---
Q: Write a context manager for a database transaction.
TAG: py
A: A class whose `__enter__` begins a transaction and returns the connection or a cursor, and whose `__exit__(exc_type, exc, tb)` commits when `exc_type` is None and rolls back otherwise, returning False so errors propagate. The generator version uses `@contextmanager`: begin, `try: yield conn` then commit, `except: rollback; raise`. I would also make sure the connection is returned to the pool in a `finally`.
---
Q: What makes code testable, and how do you test code that calls external services?
TAG: py
A: Pure logic separated from I/O, and dependencies passed in rather than created inside: a client, a clock, a sleep function. Then unit tests pass fakes or use pytest's `monkeypatch`, and run in milliseconds. For the integration layer I run a real local dependency (DuckDB, a Postgres container, a local object store) in a few slower tests, and use recorded responses for third-party APIs. Data quality checks on real tables cover what unit tests cannot.
---
Q: How do you structure logging in a production data job?
TAG: py
A: One logger per module with `logging.getLogger(__name__)`, configured once at the entry point. INFO for milestones with counts (rows read, written, rejected), WARNING for handled oddities, `log.exception` on failures. Structured JSON logs with a run id, task, table and partition so they can be searched and joined to metrics. No secrets or personal data. The goal is that someone, or an on-call agent, can diagnose a failure from the logs without rerunning the job.
---
Q: When should a pipeline retry, and how?
TAG: py
A: Only for transient failures: timeouts, connection resets, throttling (429), server errors (5xx), a database failover. Use exponential backoff with jitter and a cap on attempts and total time, and make the operation idempotent so a retry after a partial write cannot duplicate data (MERGE on a key, overwrite a partition, or an idempotency key). Permanent failures such as validation errors or a 400 should fail fast with a clear message.
---
Q: How do you lay out and package a Python data project?
TAG: py
A: A src layout with a package under `src/`, tests in `tests/`, and a `pyproject.toml` declaring dependencies and tool settings (pytest, ruff, mypy). A virtual environment per project and a lock file for deployable jobs. Configuration from environment variables, validated at start-up, with a `.env.example` committed and real secrets in a secret manager. A `__main__.py` or console script as the entry point so orchestrators run it the same way everywhere, and CI that runs lint, type checks and tests on every pull request.
