## P1.2 Names point at objects

A Python variable is a **name tag on an object**, not a box holding a value. Assignment moves the tag; it never copies the object.

```
a = [1, 2, 3]          a ──┐
b = a                  b ──┴──> [1, 2, 3]     one list, two names

b.append(4)            a and b both see [1, 2, 3, 4]

c = a.copy()           c ─────> [1, 2, 3, 4]  a new list
```

This explains most "my data changed by itself" bugs. If a function receives a list and calls `.append` on it, the caller's list changes, because there is only one list.

Objects are either **mutable** (can change in place: `list`, `dict`, `set`, most objects you create) or **immutable** (cannot: `int`, `float`, `str`, `tuple`, `frozenset`). `x += 1` on an int does not change the int; it makes a new int and moves the name `x` to it.

Two comparisons:

- `a == b` asks: do they hold equal values?
- `a is b` asks: are they the same object? Use `is` only for `None` (`if x is None`).

```python
a = [1, 2]; b = [1, 2]
a == b   # True: equal values
a is b   # False: two different lists
```

**Copies.** `list(a)`, `a.copy()` and `a[:]` make a *shallow* copy: a new outer list, but the items inside are shared. For a list of dicts that matters: changing `copy[0]["fare"]` changes the original dict too. `copy.deepcopy` copies everything, slowly.

## P1.3 Lists and tuples, and what they cost

A **list** is a resizable array of references. Fast at the end, slow at the front.

| Operation | Cost | Why |
|---|---|---|
| `xs[i]`, `xs[i] = v` | O(1) | jump straight to slot i |
| `xs.append(v)`, `xs.pop()` | O(1) amortised | the end has spare room; occasionally it grows |
| `xs.insert(0, v)`, `xs.pop(0)` | O(n) | every other item shifts one place |
| `v in xs`, `xs.index(v)` | O(n) | scans from the start |
| `xs[a:b]` | O(b − a) | slicing **copies** |
| `xs.sort()`, `sorted(xs)` | O(n log n) | Timsort, stable |
| `len(xs)` | O(1) | stored, not counted |

"Amortised O(1)" means: most appends are instant, and the occasional resize (copying everything to a bigger array) is rare enough that the average stays constant.

A **tuple** is an immutable list: `point = (12.97, 77.59)`. Use it for fixed-size records and as a dict key (a list cannot be a key, because it can change). Unpacking is everywhere in good Python:

```python
lat, lon = point
for i, trip in enumerate(trips):      # index and item
for city, n in counts.items():        # key and value
first, *rest = [1, 2, 3]              # first = 1, rest = [2, 3]
```

## P1.4 Dicts and sets: the hash table you use every day

A **dict** maps keys to values using a hash table. Python computes `hash(key)`, which points to a slot, so a lookup does not scan anything.

```
hash("Pune")  ──> slot 5 ──> ("Pune", 120)
hash("Goa")   ──> slot 2 ──> ("Goa", 40)

d["Pune"]  : hash, jump to slot 5, compare key, done.  O(1) on average
```

| Operation | Cost |
|---|---|
| `d[k]`, `d[k] = v`, `k in d`, `del d[k]` | O(1) average |
| iterate `d`, `d.items()` | O(n) |
| `s.add(x)`, `x in s` (set) | O(1) average |
| `a & b`, `a \| b` (set intersection, union) | O(len(a) + len(b)) |

Keys must be **hashable**: immutable things like `str`, `int`, `tuple`. Since Python 3.7, dicts keep **insertion order**.

Useful methods:

```python
d.get("Delhi", 0)                  # default instead of KeyError
d.setdefault("Delhi", []).append(t)  # create the list the first time
{**defaults, **overrides}          # merge; right side wins
```

A **set** is a dict with only keys: membership and deduplication. The single most important performance habit in Python interviews is this: **if you are checking `x in something` inside a loop, `something` should be a set or dict.** A list there turns O(n) into O(n²). Exercise 1 makes you feel the difference.

## P1.5 Big-O in ten minutes

Big-O describes how the work grows with the input size n, ignoring constants. You need five classes:

```
O(1)        dict lookup, list append          flat
O(log n)    binary search, heap push          barely grows
O(n)        one pass over the data            grows with the data
O(n log n)  sorting                           a bit faster than linear
O(n²)       a loop inside a loop over n       explodes: 100k rows = 10 billion steps
```

How to count: walk the code from the inside out and multiply nested loops.

```python
for t in trips:                 # n times
    if t["driver_id"] in ids:   #   ids is a list: O(m) each  -> O(n·m)
        ...                     #   ids is a set:  O(1) each  -> O(n)
```

Also say the **space** cost: how much extra memory you use. A set of seen ids is O(n) space; reading a file line by line is O(1).

In an interview, state the time and space of your first idea, then improve it. "This is O(n²) because of the nested scan; a set makes it O(n) time and O(n) space" is exactly the sentence interviewers listen for.

## P1.6 The collections module

Four types that replace ten lines of code each:

```python
from collections import Counter, defaultdict, deque, namedtuple

Counter(["a", "b", "a"])            # Counter({'a': 2, 'b': 1})
Counter(words).most_common(3)       # top 3 [(word, n), ...]

groups = defaultdict(list)          # missing key -> new empty list
for t in trips:
    groups[t["city"]].append(t)

window = deque(maxlen=3)            # keeps only the newest 3
for x in stream:
    window.append(x)                # O(1) at both ends

q = deque(); q.append(x); q.popleft()   # a queue: O(1), unlike list.pop(0)

Trip = namedtuple("Trip", "id city fare")   # a tuple with field names
```

Map them to SQL in your head: `Counter` is `GROUP BY ... COUNT(*)`, `defaultdict(list)` is grouping rows, `deque(maxlen=n)` is a sliding window.

## P1.7 Strings and files

Strings are immutable, so building one in a loop with `+=` creates a new string each time. Collect parts in a list and `"".join(parts)` once.

```python
line.strip().split(",")        # remove whitespace at the ends, split on commas
line.split(maxsplit=2)         # at most 3 parts: keeps the message intact
f"{city}: {fare:.2f}"          # f-strings for formatting
",".join(["a", "b"])           # 'a,b'
```

Reading a file **line by line** keeps memory flat, whatever the file size:

```python
with open("trips.log", encoding="utf-8") as f:
    for line in f:             # one line at a time, never the whole file
        ...
```

`f.read()` or `f.readlines()` loads everything into memory: fine for a config file, wrong for a 20 GB log. The `with` block closes the file even if an error happens (module P5 shows how that works).

## On your Mac (optional, 20 minutes)

Feel the O(n²) difference at real scale. Save this as `dedupe_speed.py` and run `python3 dedupe_speed.py`:

```python
import time

def with_list(xs):
    out = []
    for x in xs:
        if x not in out:
            out.append(x)
    return out

def with_set(xs):
    seen, out = set(), []
    for x in xs:
        if x not in seen:
            seen.add(x)
            out.append(x)
    return out

for n in (1_000, 10_000, 40_000):
    xs = list(range(n)) * 2
    for f in (with_list, with_set):
        t0 = time.perf_counter(); f(xs)
        print(f"{f.__name__:10} n={n:>6}: {time.perf_counter() - t0:.3f}s")
```

Each time n grows 4x, the list version gets about 16x slower. That is O(n²).

@@interview
Q: What is the time complexity of looking up a key in a Python dict, and how does it work?
TAG: py
A: O(1) on average. A dict is a hash table: Python computes `hash(key)`, uses it to pick a slot, and compares the key stored there. Collisions are resolved by probing other slots, so the worst case is O(n), but with a good hash and the automatic resizing that keeps the table partly empty, lookups stay constant on average. That is why keys must be hashable (immutable): if a key changed after insertion, its slot would be wrong.
---
Q: You have two lists of 10 million ids each. How do you find ids in both, and what does it cost?
TAG: py
A: Convert one list to a set (O(n) time, O(n) memory), then keep the items of the other that are in the set: O(n + m) overall. `set(a) & set(b)` does the same if order and duplicates do not matter. The nested-loop version is O(n·m), 10^14 comparisons, which never finishes. If the data does not fit in memory, sort both and merge, or push the work into a database or Spark join.
---
Q: Your pipeline's memory keeps growing while reading a large file. What do you look for?
TAG: py
A: Anything that holds the whole file: `read()`, `readlines()`, `list(...)` around an iterator, or appending every row to a list "for later". I iterate the file object line by line, process and write in batches, and keep only what is needed (counts, a set of keys with a time limit). Then I measure with `tracemalloc` or by watching resident memory while it runs.
---
Q: When would you use a tuple instead of a list?
TAG: py
A: For fixed-size records whose fields mean different things, like `(lat, lon)` or `(city, day)`, and whenever I need it as a dict key or set member, which requires immutability. Lists are for variable-length collections of the same kind of thing. Tuples also signal intent: this should not change.
---
Q: What is the difference between `Counter`, `defaultdict` and a plain dict, and when do you reach for each?
TAG: py
A: A plain dict raises `KeyError` on a missing key, so you use `get` or `setdefault`. `defaultdict(factory)` creates the value on first access, which is ideal for grouping (`defaultdict(list)`) or summing (`defaultdict(int)`). `Counter` is a dict of counts with extras: `most_common(k)`, adding and subtracting counters. I use Counter for frequency questions, defaultdict for grouping, and a plain dict when a missing key should be an error.
---
Q: Explain amortised O(1) for `list.append`.
TAG: py
A: A list is an array with spare capacity. Most appends write into the spare slot in constant time. When it fills, Python allocates a larger array (roughly 1.125x plus a little) and copies everything: an O(n) step. Because each resize grows the capacity in proportion to the size, those expensive copies are rare, and averaged over all appends the cost per append is constant.
