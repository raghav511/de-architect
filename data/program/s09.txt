## 9.1 The failures that do not fail

A job that crashes is the easy case. Someone is paged, and the dashboard shows yesterday's numbers with a warning. The dangerous failures finish successfully and publish wrong data.

Last month, Meridian had three:

- The app team renamed `fare_amount` to `fare`. The ingest job's permissive schema handling filled the old column with NULLs, and a filter on `fare_amount > 0` dropped 12% of trips. Every task was green.
- A source sent the same day's file twice. Revenue doubled for one day.
- A source stopped sending one city's data. Totals dipped by 4%, within normal variation, and nobody noticed for a week.

Data can go wrong in five ways, and each needs its own check.

| Dimension | Question | Example check |
|---|---|---|
| **Freshness** | Did the data arrive on time? | Newest `event_ts` is less than two hours old |
| **Volume** | Is the amount plausible? | Row count is within the band expected for this weekday |
| **Schema** | Is the shape what consumers expect? | Columns, types and nullability match the contract |
| **Distribution** | Are the values plausible? | Null rate of `driver_id` under 1%; no city's share moved by more than 20% |
| **Lineage** | What is affected if this breaks? | The list of downstream tables and dashboards, and their owners |

A pipeline is reliable when each of these is checked automatically, at the right place, with an alert that reaches someone who can act.

## 9.2 Testing data pipelines

Testing has three layers, and each runs in a different place.

**Unit tests** check transformation logic with small, hand-written inputs. They run in CI on every change, in seconds, with no cloud access.

```python
import pytest
from pyspark.sql import SparkSession
from jobs.enrich import completed_per_city

@pytest.fixture(scope="session")
def spark():
    return SparkSession.builder.master("local[1]").getOrCreate()

def test_counts_only_completed_trips(spark):
    df = spark.createDataFrame(
        [("t1", "BLR", "completed"), ("t2", "BLR", "cancelled"), ("t3", "HYD", "completed")],
        "trip_id string, city string, status string")
    result = {r.city: r.trips for r in completed_per_city(df).collect()}
    assert result == {"BLR": 1, "HYD": 1}
```

This only works if transformations are written as functions that take and return DataFrames, with reading and writing kept at the edges of the job. That design choice makes code testable, and it is worth stating in interviews. External sources are replaced by DataFrames built in the test. External services are replaced with mocks.

**Data tests** check the data itself, every time it is produced: keys unique and not null, values in an allowed set, foreign keys present in the dimension, counts within a band. dbt tests and expectation libraries such as Great Expectations are both this layer. They run in production, as part of the pipeline.

**Integration tests** run the whole pipeline on a small fixed dataset, often with real services in containers, and compare the output with a known answer. They run in CI before a release.

## 9.3 Data contracts

Most bad data starts upstream, in a change made by a team that did not know who depended on its output. A **data contract** makes that dependency explicit.

```yaml
contract: trip_events
version: 2.1.0
owner: rides-app-team
consumers: [data-platform, pricing]
schema:
  event_id:    {type: string, nullable: false, unique: true}
  event_type:  {type: string, nullable: false, allowed: [requested, accepted, started, completed, cancelled]}
  trip_id:     {type: string, nullable: false}
  fare_amount: {type: decimal, nullable: true, description: "Rupees, excluding tip. Set on completed only."}
  event_ts:    {type: timestamp, nullable: false, description: "UTC, from the device"}
quality:
  - freshness: event_ts within 15 minutes of arrival
  - volume: between 60% and 160% of the same hour last week
changes:
  non_breaking: add nullable field
  breaking: rename, remove, change type or meaning; needs a new major version and 30 days' notice
```

A contract is useful only if it is enforced in two places.

- **On the producer's side, in CI.** A pull request that changes the event schema runs a check against the contract. A breaking change fails the build before it ships.
- **On the consumer's side, at ingestion.** Every batch is validated against the contract. A failing batch is quarantined and the producer's owner is alerted.

The renamed column in section 9.1 would have failed the first check. If it had somehow shipped, it would have failed the second, and the 12% would never have reached a dashboard.

## 9.4 Write, audit, publish

The general pattern behind every safe pipeline is **write-audit-publish**.

1. **Write** the new data somewhere consumers cannot see: a staging table, a separate schema, or an Iceberg branch.
2. **Audit** it: run the data tests and contract checks.
3. **Publish** only if the audit passes, by swapping tables, switching a view, or fast-forwarding the main branch.

If the audit fails, consumers keep yesterday's good data and someone is alerted. Stale data with a warning is almost always better than fresh wrong data. `dbt build` approximates this by running a model's tests before building the models that depend on it.

## 9.5 Observability

Tests check known rules. Observability watches for the unknown, by tracking metrics over time and noticing change.

For every important table, record per load: freshness lag, row count, null rate of key columns, distinct counts, and a hash of the schema. For every job: duration, retries and cost. Store these as a table, which makes them queryable like any other data.

**Volume anomalies** are found by comparing today with recent history. A simple rule flags a count more than three standard deviations from the mean of the previous seven days. It needs care: weekly seasonality makes Monday look anomalous against Sunday, so compare each day with the same weekday, and require enough history before alerting.

**Service-level objectives** turn reliability into numbers people agree on: "the trips mart is complete by 07:00 IST on 99% of days". Measure against it, and you can say whether last month was acceptable, which is what a stakeholder asking "is the pipeline reliable?" actually wants.

**Lineage** answers "what does this break?" Airflow and Spark can emit lineage events in the OpenLineage format, and catalogs such as OpenMetadata collect them into a graph. In an incident, lineage tells you which dashboards to mark as suspect and whom to tell.

**Alerts** should be few, actionable and routed. Each one says what failed, what it affects, who owns it, and links to the evidence. An alert that fires daily and is ignored is worse than none.

## 9.6 CI/CD for data

Every change goes through the same path.

1. A branch and a pull request.
2. **CI** runs: linting for Python and SQL, unit tests, `dbt build` against a CI schema on a sample of data, and `terraform plan` if infrastructure changed. dbt can build only the models changed in the pull request and their descendants, reading unchanged parents from production. That keeps CI fast on large projects.
3. Review and merge.
4. **Deployment** to production: new DAG files, new job images, `terraform apply`.
5. **Rollback** is a revert followed by a rerun of the affected intervals. That is only safe because every job is idempotent.

Jobs are packaged as **container images**, so the same code and dependencies run in CI and production. On **Kubernetes**, a container runs inside a pod. A pod declares resource *requests*, which the scheduler reserves, and *limits*, which the container may not exceed. A container that exceeds its memory limit is killed. Airflow can run each task as its own pod, and Spark can run its driver and executors as pods.

## 9.7 Responding to an incident

When something does fail, the order of work matters.

1. **Stop the spread.** Pause downstream jobs. Mark affected dashboards as suspect.
2. **Tell people.** A short message to the affected teams: what is wrong, what is affected, when the next update will come.
3. **Find the cause** with evidence, not guesses.
4. **Fix and backfill.** Repair the code or the data, then rerun the affected intervals.
5. **Write the postmortem.** What happened, why, what was done, and what will prevent a repeat. Blame the system, not a person.

You have written eight short postmortems in `notes/what-broke.md` across this program. They are now the most valuable thing you own for behavioral rounds, and the evaluation set for your agent.

## 9.8 The on-call agent

Each sprint has added one capability to your agent. This sprint you assemble them into a service. It follows the design of the system Wix runs across 3,500 Airflow pipelines.

```
Airflow task fails
   │  on_failure_callback posts dag, task, run and log location
   ▼
1. Classify      cheap model, structured output            (sprint 2)
2. Gather        read_log, stage_summary, table_health,
                 lineage, search_docs                      (sprints 1, 3, 5, 7)
3. Diagnose      stronger model, structured plan with evidence
4. Report        Slack message to the owning team
5. Propose       optional fix, through approval only        (sprint 6)
```

The hook in Airflow:

```python
import requests

def notify_agent(context):
    ti = context["task_instance"]
    requests.post(AGENT_URL, timeout=5, json={
        "dag_id": ti.dag_id, "task_id": ti.task_id, "run_id": context["run_id"],
        "try_number": ti.try_number, "log_url": ti.log_url})

default_args = {"retries": 2, "on_failure_callback": notify_agent}
```

The agent's final answer is a structured plan, validated like any model output:

```python
class Diagnosis(BaseModel):
    summary: str                 # one sentence a person reads first
    root_cause: str
    evidence: list[str]          # exact lines or numbers from tool output
    confidence: Literal["high", "medium", "low"]
    next_steps: list[str]
    owner: str                   # from the table's metadata, not from the model
    needs_human: bool
```

Design decisions to be able to defend:

- **Two models.** Classification is frequent and simple, so it uses a small, cheap model. Diagnosis is rarer and harder, so it uses a stronger one. Wix reports about $0.30 per interaction with this split.
- **Evidence or nothing.** Every claim must cite tool output. A diagnosis without evidence is posted as "unknown, here is what I checked".
- **The owner comes from metadata.** Routing is a lookup, not a guess.
- **It reads, and only proposes.** Fixes go through the sprint 6 approval path. Wix found that 28 of 180 generated pull requests merged without human edits, about 15%. The agent saves the first fifteen minutes of every incident; it does not replace the engineer.
- **It is evaluated.** Your eight incidents, with their known causes, plus healthy runs where the right answer is "nothing wrong", are the test set. Run it after every prompt or tool change.
- **It has a cost and a log.** Tokens and time per incident are recorded, so you can say what it costs and whether it helps.

## SQL warm-ups: data quality queries

1. **Detect duplicates feeding a dashboard.** Asked at Meta. *Approach:* `GROUP BY` the business key `HAVING COUNT(*) > 1`; then decide whether they are exact copies or conflicting versions, which have different causes.
2. **Missing ids in a sequence.** `orders(order_id)` should be continuous. *Approach:* `LEAD(order_id)` and report gaps where the next id is more than one greater.
3. **Days with no data.** *Approach:* generate a calendar of dates for the range, left join the daily counts, and keep dates with no match. Absence never shows up in a `GROUP BY` of the data itself.

## DSA warm-ups: dynamic programming, part 2, and backtracking

1. **All unique permutations of a list with duplicates.** Asked at LinkedIn. *Approach:* sort, then backtrack, skipping an element equal to the previous one when the previous one is unused at this depth.
2. **Word break.** Can a string be split into dictionary words? *Approach:* `ok[i]` is true if some `ok[j]` is true and `s[j:i]` is a word.
3. **Longest palindromic subsequence.** Asked at Intuit. *Approach:* `dp[i][j]` over substring bounds; if the ends match, add 2 to the inner answer, otherwise take the better of dropping either end. O(n²).

## Customer drill: "your pipeline is unreliable"

A customer's head of operations tells you: *"Your pipeline is unreliable."*

What do you do in the next ten minutes? Decide, then compare.

- Ask for the last two or three occasions they have in mind, with dates. Reliability complaints are usually about specific memories.
- Ask what "reliable" means to them: on time, correct, or both? By when do they need the data?
- Propose a measurable target: data complete by a time on a share of days.
- Offer to show the last 30 days against that target, with incidents and time to recover.
- Commit to a weekly report until the number is where it should be.

A vague complaint becomes a service-level objective with a report. The conversation changes from blame to a number both sides can watch.

TITLE: Flag anomalous daily row counts
KIND: sql
MIN: 15
TAG: sql
PROBLEM:
Table `daily_counts(day, row_count)`, one row per day.

Return each `day, row_count` where the count differs from the **mean of the previous seven days** by more than **three standard deviations** of those seven days. Only evaluate days that have seven previous days. Order by day.
SOLUTION:
```sql
WITH s AS (
  SELECT day, row_count,
         AVG(row_count)         OVER w AS mean_7d,
         STDDEV_SAMP(row_count) OVER w AS sd_7d,
         COUNT(*)               OVER w AS n_prev
  FROM daily_counts
  WINDOW w AS (ORDER BY day ROWS BETWEEN 7 PRECEDING AND 1 PRECEDING)
)
SELECT day, row_count
FROM s
WHERE n_prev = 7
  AND ABS(row_count - mean_7d) > 3 * sd_7d
ORDER BY day;
```

The frame ends at `1 PRECEDING`, so a day is compared only with the days before it. Including the current day would let a large anomaly pull the mean toward itself.

The `n_prev = 7` guard stops alerts during the first week, when there is too little history.

Two refinements to mention. After an anomaly, it sits in the next seven windows and widens the band, which can hide a second problem; excluding flagged days from the baseline fixes that. And weekly patterns make weekdays and weekends look anomalous against each other, so production checks compare with the same weekday in previous weeks.

TITLE: A data quality report per load
KIND: sql
MIN: 13
TAG: sql
PROBLEM:
`trips(load_date, trip_id, driver_id)` and `drivers(driver_id)`, where `driver_id` is unique in `drivers`.

For each `load_date`, return:

- `total_rows`
- `duplicate_rows`: rows beyond the first for each `trip_id`
- `null_driver_pct`: percentage of rows with a NULL `driver_id`, rounded to one decimal
- `orphan_rows`: rows whose `driver_id` is not NULL but does not exist in `drivers`

Order by `load_date`.
SOLUTION:
```sql
SELECT t.load_date,
       COUNT(*)                                                         AS total_rows,
       COUNT(*) - COUNT(DISTINCT t.trip_id)                             AS duplicate_rows,
       ROUND(100.0 * SUM(CASE WHEN t.driver_id IS NULL THEN 1 ELSE 0 END) / COUNT(*), 1) AS null_driver_pct,
       SUM(CASE WHEN t.driver_id IS NOT NULL AND d.driver_id IS NULL THEN 1 ELSE 0 END)   AS orphan_rows
FROM trips t
LEFT JOIN drivers d ON d.driver_id = t.driver_id
GROUP BY t.load_date
ORDER BY t.load_date;
```

Four checks in one scan. The left join keeps every trip, and a trip whose driver has no match shows a NULL `d.driver_id`. Distinguishing that from a trip with no driver at all is why the orphan condition tests both columns.

The query depends on `drivers.driver_id` being unique. If it were not, the join would multiply trips and every count would be wrong. Say that assumption out loud; checking it is itself a data test.

In a real pipeline this result is written to a metrics table after each load, and the thresholds are applied to it. That is the `ops.table_health` table in this sprint's lab.

TITLE: Subset sum
KIND: dsa
MIN: 15
TAG: dsa
SRC: LinkedIn, 5 YOE
PROBLEM:
Given a list of non-negative integers and a target, return `True` if some subset of the numbers adds up exactly to the target. Each number can be used at most once.

LinkedIn asked for O(n·W) time and O(W) space, where W is the target.
SOLUTION:
```python
def can_sum(nums, target):
    reachable = [True] + [False] * target      # reachable[s]: some subset sums to s
    for x in nums:
        for s in range(target, x - 1, -1):     # go downwards so x is used at most once
            if reachable[s - x]:
                reachable[s] = True
    return reachable[target]
```

The full table would be `dp[i][s]`: whether the first i numbers can make s. Each row depends only on the row before, so one array is enough.

The direction of the inner loop is the detail interviewers check. Going down from the target means `reachable[s - x]` still holds the value from before x was considered, so x is counted once. Going upwards would let x be reused, which solves a different problem, the unbounded version used in coin change.

TITLE: Validate a batch against a contract
KIND: python
MIN: 17
TAG: cloud
SRC: LinkedIn, 5 YOE
PROBLEM:
Write `validate(rows, contract)` for a batch of records. `rows` is a list of dictionaries. `contract` looks like:

```python
{"min_rows": 2,
 "columns": {"trip_id": {"type": str},
             "fare":    {"type": float, "nullable": True},
             "zone_id": {"type": int}}}
```

Return a **sorted list of distinct violation codes**:

- `min_rows` if there are fewer rows than `min_rows`
- `missing:<col>` if any row lacks a contract column
- `null:<col>` if a non-nullable column is `None` in any row
- `type:<col>` if any non-`None` value has the wrong type. A `bool` is not an `int`.
- `unexpected:<col>` if any row has a column not in the contract

Return an empty list for a valid batch.
SOLUTION:
```python
def validate(rows, contract):
    problems = set()
    if len(rows) < contract.get("min_rows", 0):
        problems.add("min_rows")
    columns = contract["columns"]
    for row in rows:
        for extra in row.keys() - columns.keys():
            problems.add(f"unexpected:{extra}")
        for name, spec in columns.items():
            if name not in row:
                problems.add(f"missing:{name}")
                continue
            value = row[name]
            if value is None:
                if not spec.get("nullable", False):
                    problems.add(f"null:{name}")
            elif type(value) is bool and spec["type"] is not bool:
                problems.add(f"type:{name}")
            elif not isinstance(value, spec["type"]):
                problems.add(f"type:{name}")
    return sorted(problems)
```

Returning distinct codes, not one message per row, keeps a million-row batch from producing a million errors. The caller can count rows per code separately if needed.

The `bool` line exists because Python treats `True` as an integer, so `isinstance(True, int)` is true. A contract check that misses that will accept `zone_id: True`.

LinkedIn asked how this integrates with CI/CD. The same function runs in two places: in the producer's CI on sample payloads, failing the build, and at ingestion on every batch, quarantining failures.

Q: Design a task scheduler that manages execution, retries and failures, with dependencies between tasks. What changes at ten times the load?
SRC: Fanatics, 6 YOE
TAG: design
A: **Data model:** tasks with definitions and dependencies; task runs with state, attempt number, timestamps, worker and error. At ten times: partition the scheduler by workflow with leader election, put state in a scalable store with indexes on state and time, autoscale workers from queue depth, and add per-tenant limits.
