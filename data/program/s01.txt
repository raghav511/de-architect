## 1.1 Why you build everything first, badly

A walking skeleton is the thinnest version of a system that still runs end to end. This sprint you will have a generator, a message log, a processing engine, storage, a query layer, a scheduler and an LLM script. Each one will be the simplest thing that works.

The reason to start this way is that data engineering problems live in the joins between tools. Kafka on its own is easy. Kafka feeding a Spark job that writes files a query engine must read, on a schedule that sometimes retries, is where duplicates, small files and late data come from. Interviewers know this. The Uber, Flipkart and Myntra loops in your bank all ask you to walk through one pipeline from ingestion to consumption and explain what breaks.

Here is what Meridian needs by Friday: **completed trips per city, per hour**.

```
generate.py ──> Kafka topic: trip_events ──> Spark batch job ──> Parquet files in object storage
                                                                          │
                              Airflow DAG runs the job every hour         ▼
                              and checks the row count           SQL: completed trips per city
```

## 1.2 The terminal and Git you will use every day

You will inspect data from a shell far more often than from a notebook. These commands cover most of it.

```bash
head -n 3 events.jsonl | jq .                 # look at a few records before loading anything
wc -l events.jsonl                            # how many rows
cut -d, -f3 trips.csv | sort | uniq -c | sort -rn | head    # value counts for column 3
grep -c '"completed"' events.jsonl            # count matching lines
awk -F, '$5 > 1000 {n++} END {print n}' trips.csv            # rows where column 5 exceeds 1000
du -sh data/* | sort -h                       # what is taking the space
tail -f airflow/logs/latest.log               # follow a log as it is written
```

The pipe is the idea to hold on to. `sort | uniq -c | sort -rn | head` reads a file as a stream and never holds it all in memory, so the same line works on a 40 GB log. That is a standard interview question.

Distributed storage has matching commands:

```bash
hdfs dfs -ls /data/trips            # list
hdfs dfs -du -h /data/trips         # sizes
hdfs dfs -put local.csv /data/      # upload
aws s3 ls s3://lake/raw/ --recursive --human-readable --summarize
aws s3 cp local.csv s3://lake/raw/
```

For Git, know what each of these does and when you would reach for it.

| Situation | Command | Why |
|---|---|---|
| Start work | `git switch -c feature/ingest` | One branch per change |
| Bring in main | `git rebase main` on your own branch | Linear history; never rebase a branch others have pulled |
| Park half-done work | `git stash` | Clean tree without committing |
| Undo a pushed commit on main | `git revert <sha>` | Adds a new commit; history stays intact |
| Undo local commits | `git reset --soft HEAD~1` | Rewrites history; safe only before pushing |
| Find the commit that broke it | `git bisect` | Binary search over history |

## 1.3 Where the data lives: HDFS and object storage

**HDFS** splits each file into large blocks, 128 MB by default, and stores each block on three different machines. A single **NameNode** holds the metadata: the directory tree and which DataNodes hold which blocks. **DataNodes** hold the bytes. Losing a DataNode is routine, because the NameNode notices the missed heartbeat and re-replicates its blocks. The NameNode is the part that must not be lost, so production clusters run a standby.

HDFS was designed for a few very large files. Millions of tiny files hurt it, because every file and block is an object in the NameNode's memory. Keep this in mind for sprint 2, where small files become your incident.

**Object storage**, such as Amazon S3 or the MinIO container you run locally, has no directories and no blocks. It is a flat map from a key like `raw/trip_events/dt=2026-10-11/hour=09/part-0001.parquet` to an object. The slashes are only characters in the key.

Three differences matter in practice.

| | HDFS | Object storage |
|---|---|---|
| Compute and storage | On the same machines | Separate; scale independently |
| Rename a "directory" | One atomic metadata change | A copy and a delete for every object |
| Cost model | You pay for the cluster | You pay for bytes stored and requests made |

The rename row explains a great deal. Older Hadoop jobs wrote to a temporary directory and renamed it into place when finished, which made the output appear all at once. On object storage that rename is slow and not atomic, so a reader can see half a result. Table formats such as Iceberg and Delta exist largely to solve this. They commit by swapping one small metadata pointer. That is sprint 2.

Almost all new platforms use object storage. HDFS questions still appear in interviews, at Microsoft, Intuit and most services companies in your bank, so you need to explain both.

## 1.4 Kafka in ten minutes

Kafka is a distributed, append-only log.

- A **topic** is a named stream, such as `trip_events`.
- A topic is split into **partitions**. Each partition is an ordered log stored on a broker. Order is guaranteed inside a partition and nowhere else.
- Each message has a position in its partition called an **offset**.
- A **producer** chooses the partition. With a key, it hashes the key, so every message with the same key lands in the same partition for as long as the partition count stays the same.
- A **consumer group** shares the partitions among its members. Each partition is read by exactly one consumer in the group. A group records how far it has read by committing offsets.
- Messages are not deleted when read. They stay for the retention period, so another group, or the same group after a reset, can read them again.

Two consequences follow, and both come up in interviews.

**Parallelism is capped by partition count.** Six partitions means at most six consumers in a group doing useful work. A seventh sits idle.

**The key decides ordering.** Meridian keys trip events by `trip_id`, so `requested`, `accepted`, `started` and `completed` for one trip stay in order. If events were keyed randomly, a consumer could see `completed` before `started`.

Replay is the property that makes Kafka useful for data engineering. When your Spark job has a bug, you fix it and read the same offsets again.

## 1.5 Spark in ten minutes

A Spark application has one **driver** and many **executors**. The driver turns your code into a plan and schedules work. Executors run tasks on partitions of data and hold cached data.

Two kinds of operation exist.

- **Transformations** such as `select`, `filter`, `join` and `groupBy` describe a result. They are lazy, and nothing runs when you call them.
- **Actions** such as `count`, `collect`, `show` and any write trigger execution.

Laziness lets Spark see the whole query before running it, so it can push a filter down to the file reader or drop columns nobody uses.

This sprint's job reads the topic as a batch, parses the JSON, and writes Parquet partitioned by date and hour.

```python
from pyspark.sql import functions as F, types as T

schema = T.StructType([
    T.StructField("event_id", T.StringType()),
    T.StructField("event_type", T.StringType()),   # requested, accepted, started, completed, cancelled
    T.StructField("trip_id", T.StringType()),
    T.StructField("rider_id", T.StringType()),
    T.StructField("driver_id", T.StringType()),
    T.StructField("city", T.StringType()),
    T.StructField("zone_id", T.IntegerType()),
    T.StructField("fare_amount", T.DoubleType()),
    T.StructField("event_ts", T.StringType()),     # ISO 8601, UTC
])

def read_events(spark, start, end):
    raw = (spark.read.format("kafka")
           .option("kafka.bootstrap.servers", "localhost:9092")
           .option("subscribe", "trip_events")
           .option("startingOffsets", "earliest")
           .option("endingOffsets", "latest")
           .load())
    return (raw.select(F.from_json(F.col("value").cast("string"), schema).alias("e"))
               .select("e.*")
               .withColumn("event_ts", F.to_timestamp("event_ts"))
               .filter((F.col("event_ts") >= start) & (F.col("event_ts") < end))
               .withColumn("dt", F.to_date("event_ts"))
               .withColumn("hour", F.hour("event_ts")))
```

Reading from `earliest` every hour is wasteful, and you will replace it with offset ranges later. A skeleton is allowed to be wasteful. It is not allowed to be wrong, which is the subject of section 1.7.

## 1.6 Airflow in ten minutes

Airflow runs tasks in dependency order on a schedule and records what happened.

- A **DAG** is a set of tasks with dependencies and a schedule.
- A **task** is one unit of work. An **operator** is a template for a task.
- The **scheduler** decides what should run. An **executor** decides where it runs: in a local process, on Celery workers, or as a Kubernetes pod per task.
- Each run covers a **data interval**. An hourly run for 09:00 to 10:00 starts just after 10:00, when that hour is complete.
- **XCom** passes small values between tasks. It is for a row count or a file path, never for data.

```python
import pendulum
from airflow.sdk import dag, task        # Airflow 3. In Airflow 2: from airflow.decorators import dag, task

@dag(schedule="@hourly",
     start_date=pendulum.datetime(2026, 10, 1, tz="UTC"),
     catchup=False,
     default_args={"retries": 2, "retry_delay": pendulum.duration(minutes=2)})
def trip_events_hourly():

    @task
    def ingest(data_interval_start=None, data_interval_end=None) -> int:
        # run the Spark job for exactly this interval and return the row count
        ...

    @task
    def check(rows: int):
        if rows == 0:
            raise ValueError("no events for this hour")

    check(ingest())

trip_events_hourly()
```

The most important habit is in the signature of `ingest`. The task processes the interval Airflow hands it. It never calls `now()`. A task that asks the clock gives a different answer on a retry, and a backfill of last Tuesday would process today.

`catchup=True` tells the scheduler to create a run for every interval missed since `start_date`. A **backfill** is the same thing done on purpose for a chosen date range. Both only work if tasks are driven by their interval.

## 1.7 Idempotency: the idea that connects everything

Your job will be retried. Airflow retries on failure. You will rerun an hour by hand after fixing a bug. Someone will backfill a month.

A task is **idempotent** if running it twice for the same input leaves the same result as running it once. The naive write is not:

```python
events.write.mode("append").partitionBy("dt", "hour").parquet("s3a://lake/raw/trip_events")
```

Run that twice for the 09:00 hour and every row is there twice. This sprint's incident makes you find that out with real data.

There are three standard fixes. You will use all three during the program.

1. **Overwrite the partition you own.** The run for 09:00 replaces the 09:00 partition and nothing else.

```python
spark.conf.set("spark.sql.sources.partitionOverwriteMode", "dynamic")
events.write.mode("overwrite").partitionBy("dt", "hour").parquet("s3a://lake/raw/trip_events")
```

Without the `dynamic` setting, `overwrite` deletes every partition in the table. Learn that from this paragraph and not from production.

2. **Merge on a key.** `MERGE INTO target USING source ON target.event_id = source.event_id` updates rows that exist and inserts those that do not. This needs a table format, which arrives next sprint.
3. **De-duplicate on read.** Keep one row per `event_id` downstream. This hides the problem; it does not fix the write. Use it as a second line of defence.

When an interviewer asks how you make a pipeline safe to rerun, the answer has two parts: each run is bound to a fixed interval, and each write replaces or merges and never blindly appends.

## 1.8 The agent loop

A language model call is text in, text out. An **agent** is a loop around that call in which the model can ask for actions.

1. You send the conversation and a list of **tools**. Each tool has a name, a description and a JSON schema for its input.
2. The model replies with text, or with a request to call a tool with specific arguments.
3. Your code runs the tool. The model never runs anything itself.
4. You append the result to the conversation and call the model again.
5. Stop when the model answers without asking for a tool, or when you hit your own limit.

```python
import json, pathlib, anthropic

client = anthropic.Anthropic()            # reads ANTHROPIC_API_KEY from the environment
MODEL = "claude-sonnet-5-5"
LOG_ROOT = pathlib.Path("airflow/logs").resolve()

def list_failed_logs(limit: int = 5) -> list[str]:
    logs = sorted(LOG_ROOT.rglob("*.log"), key=lambda p: p.stat().st_mtime, reverse=True)
    return [str(p.relative_to(LOG_ROOT)) for p in logs if "ERROR" in p.read_text(errors="ignore")][:limit]

def read_log(path: str, tail_lines: int = 80) -> str:
    p = (LOG_ROOT / path).resolve()
    if LOG_ROOT not in p.parents:         # the model chose this path, so check it
        raise ValueError("path is outside the log folder")
    return "\n".join(p.read_text(errors="ignore").splitlines()[-tail_lines:])

TOOLS = [
    {"name": "list_failed_logs",
     "description": "List recent Airflow task log files that contain errors, newest first.",
     "input_schema": {"type": "object", "properties": {"limit": {"type": "integer"}}}},
    {"name": "read_log",
     "description": "Read the last lines of one task log. Use a path returned by list_failed_logs.",
     "input_schema": {"type": "object",
                      "properties": {"path": {"type": "string"}, "tail_lines": {"type": "integer"}},
                      "required": ["path"]}},
]
FUNCS = {"list_failed_logs": list_failed_logs, "read_log": read_log}

def explain_latest_failure(max_turns: int = 6) -> str:
    messages = [{"role": "user", "content":
        "Find the most recent failed Airflow task and explain it. Give the cause, the exact log line "
        "that shows it, and one suggested fix. If the logs do not show the cause, say so."}]
    for _ in range(max_turns):
        resp = client.messages.create(model=MODEL, max_tokens=1024, tools=TOOLS, messages=messages)
        if resp.stop_reason != "tool_use":
            return "".join(b.text for b in resp.content if b.type == "text")
        results = []
        for block in resp.content:
            if block.type == "tool_use":
                try:
                    out = FUNCS[block.name](**block.input)
                    results.append({"type": "tool_result", "tool_use_id": block.id, "content": json.dumps(out)})
                except Exception as exc:
                    results.append({"type": "tool_result", "tool_use_id": block.id,
                                    "content": str(exc), "is_error": True})
        messages.append({"role": "assistant", "content": resp.content})
        messages.append({"role": "user", "content": results})
    return "Stopped: turn limit reached."
```

Four details in that code are the difference between a demo and something you can leave running.

- **The turn limit.** Without `max_turns`, a confused model can call tools forever, and you pay for every call.
- **Errors go back to the model.** A failed tool returns `is_error` and the message. The model can then try a different path.
- **The path check.** The model supplies `path`. Anything the model supplies is untrusted input, exactly like a web form.
- **Permission to say "I don't know".** The prompt allows it. A model that must always produce a cause will invent one.

These tools only read. Every sprint adds one capability, and the first tool that can change anything arrives in sprint 6 with a human approval step in front of it.

## Incident: a rerun doubles every row (45 minutes)

Operations reports that Bengaluru shows twice as many completed trips for the 09:00 hour as the app does.

1. Reproduce it. Trigger the same DAG run twice, then count rows for that hour and count distinct `event_id` values.
2. Find the cause in your own code. It is one word.
3. Fix the write so the 09:00 run owns the 09:00 partition. Section 1.7 has the setting you need.
4. Prove it. Run the hour three times. The row count must not change.
5. Now look at the 1% of duplicates the generator sends on purpose. Your fix did not remove those. Add a second query that counts distinct `event_id`, and write down why the two kinds of duplicate have different causes.
6. Write `notes/what-broke.md` with four headings: what happened, why, the fix, how we would have caught it sooner. Keep it under 200 words.

That note is your first behavioral story. "Tell me about a data quality issue you faced in production" appears across your bank, at Adobe among others.

## SQL warm-ups: joins, aggregation, NULLs

1. **Customers and their order counts, including customers with none.** `customers(id, name)`, `orders(id, customer_id)`. *Approach:* `LEFT JOIN` and `COUNT(o.id)`. `COUNT(*)` would report 1 for a customer with no orders.
2. **Employees who earn more than their manager.** `employee(emp_id, name, manager_id, salary)`. Asked at Google and Fanatics in your bank. *Approach:* self-join the table on `e.manager_id = m.emp_id`.
3. **Average transaction amount for users who joined in 2023.** `users(user_id, join_date)`, `transactions(user_id, amount)`. Asked at Meta. *Approach:* filter on a date range, `join_date >= '2023-01-01' AND join_date < '2024-01-01'`, so an index or partition on the date can be used.

## DSA warm-ups: arrays and hash maps

1. **Two Sum.** Return the indices of two numbers that add to a target. Asked at Stripe and Meta. *Approach:* one pass with a map from value to index; look up `target - x` before inserting `x`. O(n).
2. **First unique character.** `"loveleetcode"` returns 2. Asked at Meta. *Approach:* count characters, then scan for the first with count 1.
3. **Remove duplicates from a list, keeping order.** Asked at Confluent. *Approach:* a `seen` set and an output list. `list(dict.fromkeys(xs))` does the same in one line; be ready to explain why it works.

For each one, say the time and space complexity out loud before you write code.

## Customer drill: five questions before any SQL

The city operations lead messages you: *"I need to know how many trips we did yesterday."*

Do not write a query. List five questions you would ask first. Then compare with these.

- Which trips count: requested, started, or completed? Do cancelled trips count?
- Whose yesterday? Midnight to midnight in which time zone?
- All cities, or one? Rides only, or food delivery too?
- What decision does the number feed, and how exact must it be?
- Is this a one-off, or do you need it every morning by a certain time?

The habit of asking before building is the core of forward deployed work, and it is also what design-round interviewers look for in the first five minutes.

KIND: sql

TAG: sql

PROBLEM:

`trips.rider_id` can be NULL for guest bookings. Status is one of `completed`, `cancelled`, `in_progress`.

Return the `name` of every rider who has **no completed trip**, ordered by name. Riders with no trips at all must be included.
SOLUTION:
```sql
SELECT r.name
FROM riders r
WHERE NOT EXISTS (
  SELECT 1
  FROM trips t
  WHERE t.rider_id = r.rider_id
    AND t.status = 'completed'
)
ORDER BY r.name;
```

`NOT EXISTS` is the safe form. The tempting version, `WHERE rider_id NOT IN (SELECT rider_id FROM trips WHERE status = 'completed')`, returns **no rows at all** here, because the subquery contains a NULL and `x NOT IN (..., NULL)` is never true. This trap is the reason the NULL guest booking is in the problem.

A `LEFT JOIN ... WHERE t.trip_id IS NULL` anti-join also works, with the status condition placed in the `ON` clause.

SRC: Walmart, 3 YOE

Given a list of words, group together the words that are anagrams of each other. Keep groups in order of first appearance, and words in their original order inside each group.

Input: `["mat", "tam", "cute", "beat", "eatb", "teab", "ateb"]`

Output: `[["mat", "tam"], ["cute"], ["beat", "eatb", "teab", "ateb"]]`
SOLUTION:
```python
from collections import defaultdict

def group_anagrams(words):
    groups = defaultdict(list)
    for w in words:
        groups["".join(sorted(w))].append(w)   # anagrams share the same sorted letters
    return list(groups.values())
```

The sorted letters are a canonical key. Time is O(n · k log k) for n words of length k. For long words, a 26-slot letter-count tuple as the key brings that to O(n · k). Python dictionaries keep insertion order, which gives the required group order for free.

KIND: python
MIN: 20
TAG: dsa
SRC: Amazon, 3 YOE
PROBLEM:
A log file has one event per line: timestamp, user and action, separated by spaces.

```
2026-10-11T09:00:01Z user_42 login
2026-10-11T09:00:05Z user_42 purchase
2026-10-11T09:00:09Z user_7 logout
```

Write `count_actions(path)` that returns a dictionary of action to count. The file may be far larger than memory. Skip lines that do not have exactly three fields.
SOLUTION:
```python
from collections import Counter

def count_actions(path):
    counts = Counter()
    with open(path, encoding="utf-8") as f:
        for line in f:                 # the file object yields one line at a time
            parts = line.split()
            if len(parts) != 3:
                continue               # malformed line
            counts[parts[2]] += 1
    return dict(counts)
```

Iterating over the file object streams it, so memory use depends on the number of distinct actions and not on file size. `f.read()` or `f.readlines()` would load everything.

The follow-up in the Amazon loop was "extend this to stream processing". The answer is that the loop body does not change. Only the source does: replace the file with a consumer that yields lines, and emit the counts per time window so they stay bounded.

Q: Explain the architecture of HDFS: NameNode, DataNode, block size and replication factor.
SRC: Microsoft, 4 YOE
TAG: cloud
A: Files are split into blocks, 128 MB by default, and each block is stored on three DataNodes by default. The NameNode keeps all metadata in memory: the directory tree, which blocks make up each file, and where each block lives. Clients ask the NameNode where to read or write, then talk to DataNodes directly. DataNodes send heartbeats; when one stops, the NameNode re-replicates its blocks elsewhere. Because the NameNode is a single point of failure, production clusters run an active and a standby NameNode. The design favours few large files, since every file and block costs NameNode memory.
---
Q: How does distributed storage such as HDFS or S3 differ from a traditional file system?
SRC: Capco, 6 YOE
TAG: cloud
A: A local file system stores a file on one machine and assumes the disk is reliable. Distributed storage spreads data across many machines, replicates it, and assumes hardware fails constantly. It is built for large sequential reads and writes, not small random updates: files are written once and appended or replaced. HDFS keeps a hierarchical namespace with atomic renames. Object storage such as S3 goes further and drops the hierarchy: it is a flat key-to-object map reached over HTTP, with no in-place edits and no atomic directory rename, and it scales compute and storage separately.
---
Q: HDFS or S3 for a new data platform? How does each stay available when nodes fail?
SRC: Amazon, 4 YOE
TAG: cloud
A: S3 for nearly every new platform. Storage scales independently of compute, there is no cluster to run, durability is managed for you, and clusters can be shut down without losing data. HDFS still makes sense on-premises, or where very low-latency local reads or atomic renames are needed.

On failure: HDFS re-replicates blocks from the remaining copies when a DataNode dies, and fails over to a standby NameNode. S3 stores each object redundantly across multiple facilities in a region and hides failures behind the API. The costs to mention for S3 are request charges and the lack of atomic rename, which table formats work around.

Q: Explain Kafka's architecture. What is the difference between a topic and a partition?
SRC: Databricks, 5 YOE
TAG: streaming
A: Brokers are the servers that store data. A topic is a named stream. Each topic is split into partitions, and a partition is an ordered, append-only log replicated across brokers, with one replica acting as leader. Producers write to a partition chosen by hashing the message key. Consumers read by offset and belong to consumer groups, where each partition is read by one member. Messages stay for a retention period regardless of being read.

The topic is the logical name. The partition is the unit of ordering, storage and parallelism. Order holds only within a partition.
---
Q: How do Kafka partitions, offsets and consumer groups help scale throughput?
SRC: Flipkart, 4 YOE
TAG: streaming
A: Partitions let a topic spread across brokers, so writes and reads happen in parallel. A consumer group divides the partitions among its members, so adding consumers increases read throughput up to the partition count. Offsets make this safe: each group commits how far it has read per partition, so a consumer that crashes or is replaced resumes from the last commit. Different groups keep separate offsets and read the same data independently. The limit to state: you cannot have more active consumers in a group than partitions, and a hot key puts disproportionate load on one partition.

Q: Explain Airflow fundamentals. What is a DAG, what are operators, and how do XComs work?
SRC: Delivery Hero, 7 YOE
TAG: cloud
A: A DAG is a directed acyclic graph of tasks with a schedule; it defines what runs and in which order. An operator is a template for a task, such as running a Python function, a SQL statement or a Spark job. Sensors are operators that wait for a condition. The scheduler creates a DAG run for each data interval and queues tasks whose upstream tasks have succeeded. XComs are small values a task pushes for downstream tasks to pull, stored in the metadata database, so they suit a file path or row count and not datasets. Good DAGs keep tasks idempotent and driven by the run's data interval.

Q: What are executors in Airflow?
TAG: cloud
A: The executor decides where and how task instances run. The **LocalExecutor** runs tasks as processes on the scheduler machine, which suits small installations. The **CeleryExecutor** sends tasks to a pool of long-running workers through a queue, which suits many short tasks. The **KubernetesExecutor** starts a pod per task, which gives isolation and per-task resources at the cost of start-up time. The choice is about scale and isolation. Heavy work should still run outside Airflow, in Spark or the warehouse, with Airflow only triggering and watching it.

Q: How do you handle task failures and retries in your orchestrator?
SRC: Databricks, 5 YOE
TAG: cloud

I separate failures worth retrying from those that are not: a missing input file may arrive later, but a schema error will fail identically every time and should alert at once. For long jobs, I prefer checkpoints or smaller tasks so a retry does not repeat hours of work.

Q: What is idempotency in data pipelines and why does it matter?
SRC: Expedia, 5 YOE
TAG: cloud
A: An idempotent task leaves the same result whether it runs once or several times for the same input. It matters because reruns are normal: schedulers retry, engineers rerun after a fix, and backfills replay history. Without it, each rerun duplicates or corrupts data. I get it by binding each run to a fixed data interval, then writing with partition overwrite or a merge on a business key, never a blind append. For streaming, the equivalent is committing offsets and output atomically, or de-duplicating on an event id.

Q: What is the difference between batch processing and streaming, and when would you choose each?
SRC: Fanatics, 6 YOE
TAG: streaming

Streaming fits decisions that lose value in minutes: surge pricing, fraud checks, live operations dashboards. It costs more to run and to reason about, because of ordering, late data and state. I ask what decision the data feeds and how stale it can be, and choose the simplest option that meets that.

Q: Explain lazy evaluation in Spark, and the difference between RDD, DataFrame and Dataset.

Q: What are the differences between ETL and ELT? When would you use ELT?

Q: Explain the difference between OLTP and OLAP systems, with examples of each.
SRC: LinkedIn, 5 YOE
TAG: modeling
A: OLTP systems serve the application: many small reads and writes of individual rows, with strict transactions. They are row-oriented and normalised. Examples: the Postgres database behind a ride-booking app, or a payments ledger.

OLAP systems serve analysis: few, large queries that scan many rows but few columns. They are column-oriented and often denormalised. Q: What is the difference between merge and rebase? How would you undo a bad commit that is already on main?
TAG: cloud
A: Merge joins two histories with a merge commit and keeps both as they happened. Rebase replays your commits on top of another branch, producing a linear history but new commit ids. Q: You have a 40 GB log file on a server. How do you find the ten most frequent error codes without loading it into memory?
TAG: cloud
A: Stream it through a pipeline:

```bash
grep ' ERROR ' app.log | awk '{print $5}' | sort | uniq -c | sort -rn | head -10
```

`grep` and `awk` process a line at a time. `sort` uses temporary files on disk when input exceeds memory, so it handles the size. If sorting 40 GB is too slow, `awk '{c[$5]++} END {for (k in c) print c[k], k}'` counts in a hash map sized by the number of distinct codes, then only the small result is sorted. The principle is the one behind MapReduce: stream, aggregate by key, then rank.
