## P2.1 Functions are values

In Python a function is an object like any other. You can store it in a variable, put it in a dict, pass it to another function and return it from one.

```python
def to_upper(s):
    return s.upper()

f = to_upper           # no brackets: the function itself, not a call
f("pune")              # 'PUNE'

rules = {"city": str.title, "fare": float}   # a dict of functions
rules["fare"]("12.5")  # 12.5
```

A function that takes or returns a function is called **higher-order**. You already use them: `sorted(xs, key=...)`, `map`, `filter`, and in PySpark `df.withColumn("x", F.upper("city"))`. Agent harnesses work the same way: a dict from tool name to Python function, and the loop calls `tools[name](**args)`.

## P2.2 Arguments, and the mutable default trap

```python
def load(path, fmt="parquet", *, overwrite=False, **options):
    ...
load("s3://lake/trips", "csv", overwrite=True, sep="|")
```

| Kind | Example | Notes |
|---|---|---|
| positional | `path` | must be given |
| default | `fmt="parquet"` | optional |
| `*args` | `def f(*args)` | extra positional arguments as a tuple |
| keyword-only | after `*` | must be named: `overwrite=True` |
| `**kwargs` | `**options` | extra named arguments as a dict |

Keyword-only arguments (after a bare `*`) are a good habit for flags: `load(p, True)` is unreadable; `load(p, overwrite=True)` is not.

**The trap.** Default values are evaluated **once**, when the function is defined, not on every call:

```python
def add_row(row, batch=[]):     # one list, shared by every call
    batch.append(row)
    return batch

add_row(1)   # [1]
add_row(2)   # [1, 2]   surprise
```

The fix is the `None` idiom:

```python
def add_row(row, batch=None):
    if batch is None:
        batch = []
    batch.append(row)
    return batch
```

## P2.3 Scope and closures

Python looks names up in four places, in order: **L**ocal, **E**nclosing function, **G**lobal (the module), **B**uilt-ins. That is the LEGB rule.

A function defined inside another can read the outer function's variables, and it keeps them alive after the outer function has returned. That is a **closure**:

```python
def make_multiplier(k):
    def mul(x):
        return x * k        # k comes from the enclosing scope
    return mul

double = make_multiplier(2)
double(21)                   # 42: mul still remembers k = 2
```

To **assign** to an enclosing variable (not just read it), declare it `nonlocal`; otherwise Python treats it as a new local and raises `UnboundLocalError`:

```python
def make_counter():
    n = 0
    def nxt():
        nonlocal n
        n += 1
        return n
    return nxt
```

Closures are how you configure behaviour without a class: a retry policy, a rate limiter, a connection factory. Decorators (P2.6) are built from them.

## P2.4 Comprehensions, and when not to use them

A comprehension builds a collection from an iterable in one expression:

```python
fares  = [t["fare"] for t in trips if t["status"] == "completed"]   # list
by_id  = {t["id"]: t for t in trips}                                 # dict
cities = {t["city"] for t in trips}                                  # set
total  = sum(t["fare"] for t in trips)                               # generator, no list built
```

Read it left to right as SQL: `SELECT expr FROM iterable WHERE condition`.

They are faster than the equivalent `for` + `append` loop and usually clearer. Stop when they stop being clear: two `for` clauses are fine, three are not, and anything with side effects (`[print(x) for x in xs]`) should be a plain loop. If a comprehension needs a comment to explain it, write the loop.

## P2.5 Sorting with key functions

`sorted(iterable, key=f, reverse=False)` returns a new list; `list.sort()` sorts in place and returns `None` (a common bug: `xs = xs.sort()` sets `xs` to `None`).

The key function maps each item to the value to compare. Return a **tuple** to sort by several fields; tuples compare item by item:

```python
sorted(trips, key=lambda t: (t["city"], -t["fare"], t["id"]))
#                            city A→Z,   fare high→low, id low→high
```

Negating a number flips its direction inside one ascending sort. For strings you cannot negate, sort twice using **stability** (equal items keep their order): sort by the secondary key first, then by the primary.

```python
trips.sort(key=lambda t: t["name"], reverse=True)   # secondary: name Z→A
trips.sort(key=lambda t: t["city"])                 # primary: city A→Z
```

`operator.itemgetter("city", "fare")` is a faster alternative to a lambda for plain field access.

## P2.6 Decorators

A decorator is a function that takes a function and returns a new function that wraps it. `@timed` above a `def` is shorthand for `f = timed(f)`.

```
@timed                         call f(x)
def f(x): ...          ──>     wrapper(x):  start clock
                                            result = original f(x)
                                            print time
                                            return result
```

```python
import functools, time

def timed(fn):
    @functools.wraps(fn)                 # keep fn's name and docstring
    def wrapper(*args, **kwargs):        # accept any arguments
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__} took {time.perf_counter() - t0:.3f}s")
    return wrapper
```

A decorator **with arguments**, like `@retry(3)`, needs one more layer: `retry(3)` runs first and returns the decorator.

```python
def retry(times):              # layer 1: takes the settings
    def deco(fn):              # layer 2: takes the function
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):   # layer 3: runs on every call
            ...
        return wrapper
    return deco
```

Without `functools.wraps`, every decorated function is called `wrapper` in logs, tracebacks and Airflow task names, which makes debugging miserable. Interviewers check for it.

Decorators you will meet: `@functools.lru_cache` (memoise), `@property` (P4), `@dataclass` (P4), `@contextmanager` (P5), `@pytest.fixture` (P5), `@task` and `@dag` in Airflow, and `@tool` in agent frameworks.

## P2.7 Pure functions make pipelines safe

A **pure** function returns a result that depends only on its inputs and changes nothing outside itself: no global updates, no mutating its arguments, no I/O.

```python
def clean(row):                    # pure: new dict, input untouched
    return {**row, "city": row["city"].strip().title()}

def clean_bad(row):                # impure: changes the caller's dict
    row["city"] = row["city"].strip().title()
    return row
```

Pure transformation steps give you what data engineering needs most: you can **rerun** them safely (idempotency), **test** them with a two-line assert, and run them in **parallel** (Spark ships your function to many machines). Keep I/O (reading, writing, calling APIs) at the edges of the pipeline and the logic in pure functions in the middle.

<details><summary>Answer</summary>

bump()
```
<details><summary>Answer</summary>

`UnboundLocalError`. Assigning to `n` makes it local to `bump`, and it is read before it has a value. Use `global n` (rarely a good idea) or pass and return the value.

xs = [3, 1, 2]
ys = xs.sort()
print(ys)
```

**5.**
```python
def deco(fn):
    def wrapper(*a):
        return fn(*a) * 2
    return wrapper

@deco
def three():
    return 3
print(three(), three.__name__)
```
<details><summary>Answer</summary>

`6 wrapper`. The decorator doubles the result, and without `functools.wraps` the function's name is lost.

**6.**
```python
print(sorted(["b", "A", "c"]), sorted(["b", "A", "c"], key=str.lower))
```
<details><summary>Answer</summary>

`['A', 'b', 'c'] ['A', 'b', 'c']`. Upper-case letters sort before lower-case ones by default, so `A` comes first in both. Try `["b", "a", "C"]`: the default gives `['C', 'a', 'b']`, the key gives `['a', 'b', 'C']`.

@@interview
Q: Write a retry decorator with a configurable number of attempts, and tell me what you would add for production.
TAG: py
A: Three layers: `retry(times)` returns `deco(fn)`, which returns a `wrapper(*args, **kwargs)` decorated with `functools.wraps(fn)`. The wrapper loops `times` times, returns on success, remembers the last exception and re-raises it at the end. For production I add exponential backoff with jitter so clients do not retry in lockstep, retry only on transient errors (timeouts, 429s, 5xx) rather than every exception, a cap on total time, logging of each attempt, and idempotency on the server side so a retried write does not duplicate data.
---
Q: What is a closure, and where have you used one?
TAG: py
A: A function that remembers variables from the scope where it was defined, even after that scope has returned. Python keeps those variables alive in the function's cells. I use closures for configuration without a class: a decorator that remembers its settings, a callback that knows which table it writes to, or a factory that returns a pre-configured client function. If the state grows beyond one or two values, I switch to a class.
---
Q: Explain the mutable default argument problem. Have you seen it cause a real bug?
TAG: py
A: Default values are evaluated once, when the `def` runs, so a default list or dict is shared by every call. Any call that mutates it changes it for the next call. A typical bug: a helper `def add_error(msg, errors=[])` collects errors across unrelated pipeline runs in a long-lived worker, so reports show errors from earlier jobs. The fix is `errors=None` and creating the list inside. Linters such as Ruff flag it.
---
Q: When would you not use a list comprehension?
TAG: py
A: When it stops being readable (more than two `for` clauses or complex conditions), when the body has side effects such as writing or printing, when I need error handling per item, and when the result is huge and only consumed once, where a generator expression avoids building the list. Readability wins: the reviewer should understand it in one pass.
---
Q: How would you sort a list of records by date descending and then name ascending?
TAG: py
A: If the date is a `date` or a sortable ISO string, a single key cannot simply negate it, so I use stable sorting twice: first `sort(key=name)`, then `sort(key=date, reverse=True)`. Equal dates keep the name order from the first pass. If the date is a number such as a timestamp, one pass works: `key=lambda r: (-r.ts, r.name)`. Python's sort is stable Timsort, O(n log n).
---
Q: Why do data engineers care about functions being pure?
TAG: py
A: Pipelines are rerun constantly: backfills, retries, recovery after failure. If a transformation depends only on its input and has no side effects, rerunning it gives the same output, so the pipeline is idempotent. Pure functions are also trivial to unit test and safe to run in parallel, which is what Spark does with the functions in your transformations. I keep reads and writes at the edges and the business logic pure in the middle.
