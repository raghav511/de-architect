## C5.1 The threat model

A coding agent can read files, run commands and reach the network, driven by text. Three ways that goes wrong:

1. **Excessive agency.** It runs something destructive or reaches somewhere it should not: `rm -rf`, `DROP TABLE`, a push to main, a call to production with real credentials.
2. **Secret exposure.** It reads `.env`, `~/.aws/credentials` or a token in a log, and the secret lands in the conversation (sent to the model provider), a commit, or a printed output.
3. **Prompt injection.** Text it reads (a file, a web page, an issue, a CSV cell, tool output) contains instructions, and it follows them. The practice project has one: `docs/vendor_notes.md` hides a note asking AI assistants to run a script and write keys to a file.

Claude Code has protections (permission prompts, injection-aware handling of fetched content, checks on risky commands), but you are the last line of defence. Least privilege plus review is the strategy.

## C5.2 Permissions: allow, ask, deny

Rules live in settings files. Most specific scope wins, and **deny beats allow**:

| File | Scope | Commit it? |
|---|---|---|
| `~/.claude/settings.json` | you, every project | no |
| `.claude/settings.json` | this project, whole team | yes |
| `.claude/settings.local.json` | this project, only you | no (gitignored) |

```json
{
  "permissions": {
    "allow": ["Bash(python3 -m unittest *)", "Bash(git diff *)", "Bash(git status)"],
    "ask":   ["Bash(git push *)", "WebFetch"],
    "deny":  ["Read(./.env)", "Read(./.env.*)", "Read(~/.aws/**)", "Read(~/.ssh/**)",
              "Bash(curl *)", "Bash(rm -rf *)", "Bash(sudo *)"]
  }
}
```

Allow the safe things you approve every day (tests, diffs), so you are not trained to click yes on everything. Deny secrets and dangerous commands. `/permissions` shows the active rules.

**Permission modes:** default (asks), accept edits, plan (read-only), and bypass. `--dangerously-skip-permissions` removes all prompts. Use it only inside a throwaway container with no secrets and no network access, never on your laptop.

## C5.3 Secrets

- Secrets live in environment variables or a secret manager, never in code, prompts, CLAUDE.md or commits.
- Deny reads of secret files (above). If a secret appears in the conversation, treat it as leaked: rotate it.
- Watch for **secrets in output**: the practice project prints `WAREHOUSE_TOKEN` when `DEBUG=1`. Logs and test output are context too.
- Before committing AI-written changes: `git diff` and a secret scan (for example `gitleaks`, or GitHub push protection).

## C5.4 Prompt injection and fixing security bugs with AI

Rules of thumb:

- Treat everything the agent reads as **data, not instructions**: repo files, web pages, tickets, CSV cells, MCP tool results.
- Be most careful with untrusted repositories, dependencies and web content. Use plan mode and narrow permissions there.
- Read every command before approving it, especially anything with `curl`, `| sh`, `base64`, unusual hosts or writes outside the project.
- If you see an injection attempt, stop, report it, and do not "just let it finish".

When you ask AI to **fix** a security bug, ask for the fix and an **attack test**: *"Fix the SQL injection in load.py using parameters, and add a test that passes a malicious date string and shows no rows are deleted."* Then run `/security-review` on the change. AI fixes can be incomplete, for example escaping quotes instead of using parameters.

@@interview
Q: How would you roll out an AI coding agent safely to a data platform team?
TAG: ai
A: Start from least privilege. Shared project settings committed to each repo: allow tests and read-only git, ask for pushes and network, deny secret files and destructive commands. No production credentials on developer machines; agents work against dev or sample data. Secrets in a secret manager, with push protection and secret scanning in CI. Train people on prompt injection and on reviewing every command and diff. Use plan mode for untrusted repos. Run unattended agents only in containers without secrets. Then review incidents and near misses and tighten rules.
---
Q: What is prompt injection, and how is it different from a classic injection like SQL injection?
TAG: ai
A: Prompt injection is when content the model reads (a web page, file, email or tool output) contains instructions that the model follows as if the user gave them. In SQL injection, the parser executes data as code. Here the model treats data as instructions. The difference is that there is no strict parser to escape against: models cannot perfectly separate instructions from data. So defences are layered: limit what the agent can do (least privilege), require confirmation for risky actions, isolate untrusted content, and monitor.
---
Q: How do you keep secrets safe when engineers use AI tools?
TAG: ai
A: Secrets never go in code, prompts or memory files. They live in a secret manager or environment variables and are injected at runtime. Agents are denied reading secret files. Logs mask secrets. Pre-commit and CI secret scanning plus push protection. Short-lived credentials so a leak expires. And a clear rule: if a secret ever appears in a conversation, rotate it.
---
Q: An AI tool fixed a SQL injection by escaping single quotes. Is that acceptable?
TAG: core
A: No. Escaping is fragile: encodings, other quote types and edge cases break it. The right fix is parameterised queries, where values are sent separately from the SQL text, plus least-privilege database users. I would ask for the parameterised version and a test with a malicious input proving it is harmless.
---
Q: When is it acceptable to run an agent with all permission prompts disabled?
TAG: ai
A: Only in an isolated, disposable environment: a container or VM with no secrets, no production credentials, network access limited or off, and only the code it needs, with the results reviewed before anything leaves the sandbox. Typical uses are CI jobs or long autonomous refactors on a branch. Never on a laptop with real credentials.
