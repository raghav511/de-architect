## 6.1 Why the two systems disagree

Meridian's food orders live in Postgres. An order row is inserted, then updated several times as it is paid, prepared, picked up and delivered. Some are refunded later. Test orders are deleted.

The warehouse gets orders from a nightly job that selects rows where `updated_at` is later than the last run. Finance has noticed that the warehouse total and the application total differ by a small amount every day.

There are four ways to copy a changing table. Know what each one misses.

| Method | How | What it misses or costs |
|---|---|---|
| Full extract | Copy the whole table each run | Nothing, but cost grows with the table and intermediate states are lost |
| Timestamp polling | Select rows changed since the last run | Hard deletes. Intermediate states between polls. Rows whose `updated_at` was not set. Rows committed late with an early timestamp. |
| Triggers | Database triggers write changes to an audit table | Nothing, but every write to the source becomes slower |
| Log-based capture | Read the database's own transaction log | Nothing, at low cost to the source. More parts to operate. |

Timestamp polling is why Finance's numbers drift: deleted test orders stay in the warehouse for ever. **Change data capture** from the log is the fix. CDC appears in the LinkedIn, J.P. Morgan and Duck Creek loops in your bank, each time as a design question.

## 6.2 How log-based capture works

Every relational database writes changes to a log before applying them, so it can recover from a crash. In Postgres this is the **write-ahead log**, or WAL. **Logical decoding** turns WAL entries back into row-level changes: this row was inserted with these values, that row changed from these values to those.

A **replication slot** is a bookmark in the WAL owned by one consumer. Postgres keeps all WAL after the bookmark until the consumer confirms it has read it. This guarantees nothing is missed. It also creates the most dangerous failure in CDC: if the consumer stops for days, the WAL piles up and can fill the database server's disk. Monitor slot lag from the day you create a slot.

**Debezium** is the standard open-source tool. It runs as a source connector on **Kafka Connect**, a framework for running connectors that move data into and out of Kafka and that stores their progress in Kafka itself. For each table the connector does two things.

1. **Snapshot.** It reads the existing rows once, so the lake starts complete.
2. **Stream.** It then follows the replication slot and publishes each change as a Kafka message.

One topic is created per table. Each message is keyed by the row's primary key, so all changes to one order go to one partition and stay in order.

A change event has an envelope:

```json
{
  "before": {"order_id": 9131, "status": "placed", "total": 420.00},
  "after":  {"order_id": 9131, "status": "paid",   "total": 420.00},
  "op": "u",
  "ts_ms": 1791700000000,
  "source": {"lsn": 88213904, "txId": 5521, "table": "orders"}
}
```

`op` is `c` for create, `u` for update, `d` for delete and `r` for a row read during the snapshot. For a delete, `after` is null and `before` holds the last values. Debezium follows a delete with a **tombstone**, a message with the same key and a null value, so a compacted topic can remove the key.

`source.lsn` is the position of the change in the WAL. It increases with every change, which makes it the version number you will use to put changes in order.

## 6.3 Applying changes to a table

The topic now holds a changelog. The lake needs a table showing the current state. Applying one to the other correctly takes four rules.

**Rule 1: reduce each batch to the latest change per key.** One micro-batch may hold three changes to the same order. A `MERGE` whose source has several rows for one target row is either an error or picks one arbitrarily. Keep only the change with the highest LSN for each key.

**Rule 2: never let an older change overwrite a newer one.** Replays and retries can deliver old events again. Store the LSN on the target row and update only when the incoming LSN is higher.

**Rule 3: handle deletes on purpose.** Either remove the row, or keep it with `is_deleted = true` so history and downstream incremental models can see the deletion. Most warehouses use the soft form.

**Rule 4: make it idempotent.** Rules 1 and 2 together mean the same batch can be applied twice with no effect.

```python
from pyspark.sql import functions as F, Window

def apply_cdc(batch_df, batch_id):
    w = Window.partitionBy("order_id").orderBy(F.col("lsn").desc())
    latest = (batch_df.withColumn("rn", F.row_number().over(w))
                      .filter("rn = 1").drop("rn"))
    latest.createOrReplaceTempView("changes")
    batch_df.sparkSession.sql("""
        MERGE INTO lake.silver.orders t
        USING changes s ON t.order_id = s.order_id
        WHEN MATCHED AND s.lsn > t.lsn AND s.op = 'd' THEN DELETE
        WHEN MATCHED AND s.lsn > t.lsn THEN UPDATE SET *
        WHEN NOT MATCHED AND s.op <> 'd' THEN INSERT *""")
```

The table should use merge-on-read from sprint 2, because it receives many small changes. Schedule compaction for it.

**Keep the raw changelog as well.** Write every change event, unmodified, to an append-only bronze table. The current-state table can then be rebuilt at any time, and you get a full history of every row for free, which is a Type 2 dimension waiting to be modelled.

## 6.4 The same job in Flink SQL

Flink treats a changelog as a first-class thing. A table in Flink SQL can be a stream of inserts, updates and deletes, and the `debezium-json` format tells Flink to read Debezium messages that way.

```sql
CREATE TABLE orders_cdc (
  order_id   BIGINT,
  rider_id   STRING,
  status     STRING,
  total      DECIMAL(10, 2),
  updated_at TIMESTAMP(3)
) WITH (
  'connector' = 'kafka',
  'topic' = 'meridian.public.orders',
  'properties.bootstrap.servers' = 'kafka:9092',
  'scan.startup.mode' = 'earliest-offset',
  'format' = 'debezium-json'
);

INSERT INTO lake.silver.orders_flink
SELECT order_id, rider_id, status, total, updated_at FROM orders_cdc;
```

With an Iceberg sink configured for upserts on `order_id`, that single statement is the whole pipeline.

Enough Flink to hold a conversation:

- Flink processes one event at a time and keeps **state** per key, usually in an embedded RocksDB store on local disk.
- A **checkpoint** is a periodic, consistent snapshot of all state and source positions, written to durable storage. On failure, Flink restores the last checkpoint and replays from there.
- A **savepoint** is a checkpoint you trigger by hand, to upgrade or move a job without losing state.
- Exactly-once sinks use a **two-phase commit** tied to checkpoints: data written between checkpoints becomes visible only when the checkpoint completes.

You built the Spark version in the lab and will run the Flink statement to compare. In interviews, Spark is the safer default for a team already on it, and Flink is the answer when latency or complex state is the hard part.

## 6.5 Reconciliation

A pipeline that is correct by design still needs proof. **Reconciliation** compares source and target on a schedule and alerts on a difference.

Compare in three levels, from cheap to precise.

1. **Counts** per day or per key range. Catches missing and extra rows.
2. **Sums and checksums** per bucket: the total of `total`, or a hash of the business columns. Catches values that differ while counts match.
3. **Row-level difference** for the buckets that failed, to list the exact keys.

The practical problem is that the source keeps changing while you compare. Avoid false alarms by comparing a closed window: only orders last updated more than an hour ago, on both sides. Run it nightly from Airflow, store the results in a table, and alert on any drift.

## 6.6 What goes wrong

| Failure | Symptom | Defence |
|---|---|---|
| Connector stopped | Slot lag grows; database disk fills | Alert on slot lag and connector status; a maximum retained WAL size |
| Duplicate delivery | Same event applied twice | Idempotent merge with the LSN guard |
| Out-of-order application | An old value reappears | The LSN guard; one partition per key |
| Deletes ignored | Target has rows the source does not | Handle `op = d`; reconcile counts |
| Source schema change | Parsing errors, or NULLs in a new column | Schema registry; additive changes only; schema evolution on the table |
| Very large transaction | One enormous burst of events | Batch size limits; backpressure from sprint 5 |
| Snapshot of a huge table | Hours of locks or load | Incremental snapshots in chunks while streaming continues |

One design mistake belongs here too. A service that writes to its database and then publishes a message to Kafka can crash between the two, leaving them inconsistent. This is the **dual-write problem**. The fix is the **transactional outbox**: the service writes the event to an `outbox` table in the same database transaction as the business change, and CDC publishes the outbox rows. Either both happen or neither does.

## 6.7 An agent that proposes, a person who approves

Until now your agent could only read. This sprint it finds drift between source and target and drafts the SQL to repair it. Running that SQL is an action with consequences, so the design changes.

The pattern is **propose, approve, execute**.

```python
import uuid, requests

PENDING = {}

def propose_fix(sql: str, reason: str) -> dict:
    """Propose a data repair. Nothing is executed. A person must approve it."""
    first = sql.strip().split()[0].lower()
    if first not in ("merge", "update", "delete", "insert"):
        raise ValueError("only a single data-change statement can be proposed")
    affected = count_affected_rows(sql)            # a dry run using the read-only role
    pid = uuid.uuid4().hex[:8]
    PENDING[pid] = {"sql": sql, "reason": reason, "affected": affected}
    requests.post(SLACK_WEBHOOK_URL, timeout=10, json={"text":
        f"*Proposed fix {pid}*\n{reason}\nRows affected: {affected}\n```{sql}```\n"
        f"Approve with: approve {pid}"})
    return {"proposal_id": pid, "status": "waiting_for_approval", "rows_affected": affected}

def execute_approved(pid: str, approver: str) -> None:
    proposal = PENDING.pop(pid)                    # a proposal can run only once
    run_with_write_role(proposal["sql"])
    write_audit_log(pid, approver, proposal)
```

The agent's tool list contains `propose_fix` and does not contain `execute_approved`. That one fact is the safety design. Everything else supports it.

- **Separate credentials.** The agent's connection is read-only. Only the approval path holds the write role.
- **A dry run before asking.** The message shows how many rows would change. A person approving "3 rows" and a person approving "3 million rows" are making different decisions.
- **The full statement is shown.** The approver sees exactly what will run, not a summary of it.
- **Run once.** The proposal is removed when executed, so a double click or a retry cannot apply it twice.
- **An audit log.** Who approved what, when, and what it changed.
- **No approval, no action.** A proposal that nobody answers expires.

Decide which actions need approval by asking whether the action can be undone. Reading is free. Restarting an idempotent task is low risk. Changing or deleting data needs a person. This is the same reasoning as "retry transient errors, alert on the rest" from sprint 1, applied to an agent.

## Incident: the database and the warehouse disagree (45 minutes)

Finance reports that yesterday's order total in the warehouse is ₹18,400 higher than in the application.

1. **Build the detector first.** Write the reconciliation DAG from section 6.5: counts and sums per hour for orders last updated more than an hour ago, on both sides, written to a `recon_results` table.
2. **Plant the fault.** Stop the connector, run `scripts/drift.sh`, which deletes some orders and updates others, then drop and recreate the replication slot before restarting the connector. The changes made while the slot was gone are lost.
3. **Detect.** Run the reconciliation. It should flag specific hours.
4. **Diagnose.** Go to row level for the flagged hours. Classify each bad key: missing in target, extra in target, or different values.
5. **Repair.** Trigger a targeted re-snapshot of the affected keys, or correct them with a merge from a fresh extract.
6. **Prevent.** Add an alert on replication slot lag and on connector status.

Add the incident to `notes/what-broke.md`. The interesting sentence to write is why the pipeline reported no error while losing data.

## SQL warm-ups

1. **Third-highest transaction per branch, with ties.** Branches with fewer than three distinct amounts should return NULL. Asked at Kotak Mahindra. *Approach:* `DENSE_RANK` per branch, keep rank 3, then `LEFT JOIN` from the list of branches so the short ones still appear.
2. **Customers who transacted in all twelve months of a year.** Asked at Zen. *Approach:* group by customer and `HAVING COUNT(DISTINCT month) = 12`.
3. **Consecutive duplicate transactions by the same user.** `(transaction_id, user_id, amount, transaction_date)`. Asked at Zen. *Approach:* `LAG(amount)` and `LAG(transaction_date)` per user; flag rows equal to the previous one.

## DSA warm-ups: linked lists and trees

1. **Reverse a linked list in groups of k.** The follow-up at Kotak Mahindra. *Approach:* reverse k nodes with the standard three-pointer loop, then recurse or iterate on the rest and connect the pieces.
2. **Lowest common ancestor in a binary tree.** Asked at Google. *Approach:* recurse left and right; a node is the answer when the two targets are found in different subtrees, or when it is one of them.
3. **In-order traversal of a binary search tree**, iteratively. *Approach:* a stack; push left children, pop, visit, move right. The output is sorted, which is how a BST is flattened or validated.

## Customer drill: "the refund numbers do not match"

The support lead says: *"Refund totals on your dashboard do not match the finance system."*

Break the problem down before opening a query editor. Then compare.

- **Which two numbers, for which period?** Get both figures and the exact filters.
- **Same definition?** Refund requested, approved or settled? Gross or net of fees?
- **Same boundary?** Time zone and cut-off time of each system.
- **Same moment?** Is one system showing state as of last night and the other as of now?
- **Five examples.** Ask for five specific refunds that are in one system and not the other. Examples find the cause faster than totals do.

The last step is the one to remember. A total tells you that something is wrong. A specific record tells you what.

Q: Compare three ways to extract changes from a transactional database, and say what each misses.
MODEL: **Full extract.** Copy the whole table each run. Simple and self-correcting, but cost grows with table size, and states between runs are lost.

**Timestamp polling.** Select rows whose `updated_at` is newer than the last run. Cheap, but it cannot see hard deletes, misses intermediate states, depends on every writer setting the timestamp, and can skip rows from long transactions that commit late with an early timestamp.

TAG: streaming
Q: A micro-batch of change events arrives. Describe how to apply it to an Iceberg table correctly.
MODEL: 1. **Reduce to the latest change per key**, using the source log position (LSN) to order them.
2. **Merge on the primary key** into the target.
3. **Guard with the version**: update or delete only when the incoming LSN is greater than the LSN stored on the target row, so replays and late events cannot overwrite newer data.
4. **Handle deletes explicitly**: remove the row, or set a soft-delete flag. Do not insert a row for a delete of a key that does not exist.
5. The result is **idempotent**: applying the batch again changes nothing.

Also keep the raw events in an append-only table, and compact the target regularly because it receives many small changes.

TITLE: Reconcile two tables
KIND: sql
MIN: 13
TAG: sql
PROBLEM:
`src_orders(order_id, status, total)` is the source. `tgt_orders(order_id, status, total)` is the copy. `total` can be NULL.

Return every `order_id` that is not identical in both, with an `issue` column:

- `missing_in_target` if it is only in the source,
- `extra_in_target` if it is only in the target,
- `mismatch` if it is in both but `status` or `total` differ.

Order by `order_id`.
SOLUTION:
```sql
SELECT COALESCE(s.order_id, t.order_id) AS order_id,
       CASE
         WHEN t.order_id IS NULL THEN 'missing_in_target'
         WHEN s.order_id IS NULL THEN 'extra_in_target'
         ELSE 'mismatch'
       END AS issue
FROM src_orders s
FULL OUTER JOIN tgt_orders t
  ON s.order_id = t.order_id
WHERE s.order_id IS NULL
   OR t.order_id IS NULL
   OR s.status IS DISTINCT FROM t.status
   OR s.total  IS DISTINCT FROM t.total
ORDER BY 1;
```

A full outer join keeps keys from both sides, which is the only join that can show all three kinds of difference at once.

`IS DISTINCT FROM` is a NULL-safe comparison. With `<>`, a NULL total on one side and 50 on the other compares as unknown and the row is silently passed as fine. Spark SQL writes the same idea as `NOT (a <=> b)`.

On large tables you would not join every row. Compare counts and checksums per bucket first, then run this only for the buckets that differ.

TITLE: Median order value per city
KIND: sql
MIN: 12
TAG: sql
SRC: Goldman Sachs, 4 YOE
PROBLEM:
Table `orders(order_id, city, total)`.

Return the **median** `total` for each city as `city, median_total`, ordered by city. For an even number of orders, the median is the average of the two middle values. Do not use a built-in median or percentile function.
SOLUTION:
```sql
WITH r AS (
  SELECT city, total,
         ROW_NUMBER() OVER (PARTITION BY city ORDER BY total) AS rn,
         COUNT(*)     OVER (PARTITION BY city)                AS n
  FROM orders
)
SELECT city,
       AVG(total) AS median_total
FROM r
WHERE rn IN (FLOOR((n + 1) / 2.0), FLOOR((n + 2) / 2.0))
GROUP BY city
ORDER BY city;
```

Number the rows in each city and count them. With n rows, the middle positions are `floor((n+1)/2)` and `floor((n+2)/2)`. For an odd n they are the same row. For an even n they are the two middle rows, and `AVG` averages them.

Dividing by `2.0` and applying `FLOOR` is deliberate. Integer division behaves differently across engines: `5 / 2` is 2 in Postgres and Spark SQL, and 2.5 in DuckDB and Snowflake. Writing the rounding explicitly makes the query portable.

In production you would use `PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY total)`, or an approximate percentile on very large data. Goldman asked for the median and then for how to speed it up on billions of rows, where the approximate function is the answer.

TITLE: Reverse a linked list
KIND: dsa
MIN: 12
TAG: dsa
SRC: Kotak Mahindra, 6 YOE
PROBLEM:
Given the head of a singly linked list, reverse the list in place and return the new head. Use O(1) extra space.

```python
class ListNode:
    def __init__(self, val, next=None):
        self.val = val
        self.next = next
```
SOLUTION:
```python
class ListNode:
    def __init__(self, val, next=None):
        self.val = val
        self.next = next

def reverse_list(head):
    prev = None
    node = head
    while node:
        nxt = node.next      # remember the rest of the list
        node.next = prev     # point this node backwards
        prev = node          # advance prev
        node = nxt           # advance node
    return prev
```

Three pointers walk the list once: time O(n), space O(1). The order of the four lines in the loop is the entire problem. Save `next` before overwriting it, or the rest of the list is lost.

The follow-up at Kotak was reversing in groups of k. Reuse this loop for k nodes at a time, and connect each reversed group's tail to the head of the next reversed group. Leave a final group shorter than k as it is.

TITLE: Apply a batch of change events
KIND: pyspark
MIN: 23
TAG: streaming
PROBLEM:
`target` holds the current state of orders: `order_id, status, total`.

`changes` is a batch of change events: `order_id, op, status, total, lsn`. `op` is `c`, `u` or `d`. For a delete, `status` and `total` are null. A key can appear several times, in any order. A higher `lsn` is a later change.

Write `apply_changes(target, changes)` returning the new state of the table.
SOLUTION:
```python
from pyspark.sql import functions as F, Window

def apply_changes(target, changes):
    w = Window.partitionBy("order_id").orderBy(F.col("lsn").desc())
    latest = (changes.withColumn("rn", F.row_number().over(w))
                     .filter(F.col("rn") == 1)
                     .drop("rn"))
    untouched = target.join(latest.select("order_id"), "order_id", "left_anti")
    upserts = (latest.filter(F.col("op") != "d")
                     .select("order_id", "status", "total"))
    return untouched.unionByName(upserts)
```

Only the last change to each key matters for current state, so the batch is first reduced to one row per key by highest `lsn`. Rows of the target that the batch does not mention pass through with an anti-join. Rows whose last change is not a delete are added. Keys whose last change is a delete are in neither part, so they vanish.

An order created and deleted in the same batch never appears, which is correct. This is the DataFrame form of the `MERGE` in section 6.3. On a real table you would use the merge, so only affected files are rewritten. A production version would also carry `lsn` on the target and refuse changes older than what is already stored.

Q: Does Delta Lake support upserts?

TAG: spark

Q: Compare full load and incremental load. What are the trade-offs?
SRC: Barclays, 5 YOE
TAG: modeling
A: A full load rebuilds the target from the whole source each run. It is simple, always consistent with the source, picks up deletes and corrections automatically, and needs no change tracking. Its cost and run time grow with the table. An incremental load processes only what changed. It is fast and cheap at scale, and it is the only option for large or frequently refreshed data. Its costs are complexity and risk: change detection, late data, deletes, schema changes, and drift over time. I use full loads for small tables and as a periodic reset, and incremental loads with reconciliation for large ones.

Q: What is the difference between a checkpoint and a savepoint in Flink, and how does Flink achieve exactly-once?
TAG: streaming
A: A checkpoint is an automatic, periodic snapshot of all operator state and source offsets, owned by Flink and used for failure recovery. A savepoint is the same kind of snapshot triggered manually and kept until you delete it, used for planned operations: upgrading job code, changing parallelism, migrating clusters.

For exactly-once, Flink injects barriers into the streams so every operator snapshots its state at a consistent point. On failure it restores state and rewinds sources to the checkpointed offsets, so each event affects state once. For external sinks it uses two-phase commit: writes are pre-committed during the checkpoint interval and committed when the checkpoint completes.

TAG: streaming

Q: What is the outbox pattern and what problem does it solve?
TAG: design
A: It solves the dual-write problem. A service that updates its database and separately publishes a message can fail between the two, leaving the database and the message stream inconsistent. No ordering or retry of the two writes makes them atomic. With the outbox pattern, the service inserts the event into an outbox table in the same database transaction as the business change. A relay, usually CDC on the outbox table, publishes those rows to Kafka. The event exists if and only if the transaction committed. Consumers must still be idempotent, since the relay delivers at least once.

Q: Write a producer-consumer program using multithreading. When would you use threads, processes or async IO in a data pipeline?
SRC: Goldman Sachs, 4 YOE
TAG: dsa
A: Use a thread-safe bounded queue:

```python
import threading, queue

q = queue.Queue(maxsize=100)

def producer():
    for i in range(1000):
        q.put(i)            # blocks when the queue is full
    q.put(None)             # signal the end

def consumer():
    while (item := q.get()) is not None:
        handle(item)

threading.Thread(target=producer).start()
threading.Thread(target=consumer).start()
```

The bounded queue gives backpressure. **Threads** suit I/O-bound work such as API calls and file transfers, since the interpreter lock is released while waiting. **Processes** suit CPU-bound work such as parsing or compression. **Async IO** suits very many concurrent network calls in one thread.
