## O2.1 What a golden path is

Every data team keeps solving the same problems: how to start a new pipeline, where to put the contract, how to test it, how to deploy it, how to get alerts. Left alone, 30 teams solve them 30 ways. Each way works, until someone else has to run it.

A **golden path** (also called a paved road) is the opinionated, supported way to do a common job, end to end. It bundles the decisions most teams should not have to make: the layout, the tools, the tests, the deployment, the monitoring, the ownership metadata.

Three properties make it golden:

1. **It is the easiest way.** A team gets a working, production-ready result in an hour, not a month.
2. **It is supported.** The platform team owns the template, fixes it, upgrades it and answers questions about it.
3. **It is optional.** Teams may leave the path for a good reason, but off the path they own what they build. Paths win by being better, not by being mandatory.

In O1 the self-serve platform was what makes domain ownership affordable. Golden paths are how that platform is used day to day.

## O2.2 Which journeys to pave

Pave the journeys that are frequent and painful. List what teams actually do, how often, and how long it takes today:

| Journey | How often | Time today | Pave first? |
|---|---|---|---|
| Publish a new data product (batch) | 20 a quarter | 6 weeks | Yes |
| Add a new source by CDC | 10 a quarter | 3 weeks | Yes |
| Create a streaming job | 4 a quarter | 8 weeks | Later |
| Request access to a dataset | 300 a quarter | 4 days | Yes (self-service with approval) |
| Build a one-off ML feature table | 2 a quarter | 2 weeks | No |

Start with one or two journeys, done well, rather than ten done badly. Talk to the teams that will use them: shadow two of them doing the journey the hard way and write down every wait, every question, every copy-paste. That list is the backlog for the path.

## O2.3 Anatomy of a template

A template for a new data product creates a working repository in one step. A good one contains:

| Part | What it gives |
|---|---|
| Layout | A standard repository structure every engineer recognises |
| Contract | `contract.yaml` with owner, grain, schema and SLOs, pre-filled from the questions asked |
| Transformation project | A dbt or Spark project with one example model that runs |
| Tests | Contract tests, data quality tests and a unit test example |
| CI | Lint, tests, contract checks and policy checks on every pull request |
| Deployment | The orchestrator job (schedule, retries, alerts) defined as code |
| Observability | Freshness and volume monitors wired to the owner's channel |
| Catalog | Registration of the product, its owner and lineage on first deploy |
| Docs | A README that explains how to change, run and debug it |

The scaffolder asks only what it cannot infer: the product name, the domain, the owning team, the schedule. Names are checked (snake_case, unique in the domain) before anything is created. Everything else has a safe default, such as a dead-letter table, schema checks and retries, because the defaults are what most teams will keep.

## O2.4 Keeping templates alive

A template is copied once and then drifts. A year later, 80 repositories were made from six versions of it, and the security fix you made last month reached none of them.

Treat templates as products with versions:

- **Semantic versions.** Patch for fixes, minor for new optional pieces, major for changes users must act on.
- **Record the version** each repository was created from, in a file the platform can read.
- **Automated upgrade pull requests.** A bot proposes the change in every repository, with the diff and release notes; owners review and merge. For shared pieces (CI steps, deployment), prefer libraries or shared workflows that update in one place over copied files.
- **A drift report.** For each repository: how many versions behind, which files differ from the template. Chase the major-behind first.
- **Deprecate old versions** with a date, like any product.

The rule of thumb: copy as little as possible into each repository. Every copied file is a file you will have to upgrade 80 times.

## O2.5 The developer portal

Golden paths need a front door. A **developer portal** (Backstage is the common open-source choice) brings together:

- **A catalog** of everything: services, pipelines, data products, owners, and how they connect.
- **Templates** that create new components through a short form.
- **Docs** next to the components they describe.
- **Scorecards** that show each component against the standards: has an owner, has a contract, tests pass, on a supported template version, SLOs met.

For data, the portal and the data catalog should not compete: either one links to the other, or the portal shows data products from the catalog. One place to start beats two half-complete ones.

## O2.6 Guardrails, not gates

A **gate** is a person who must approve: a review board, a ticket to the platform team. Gates make teams wait and teach them to route around you. A **guardrail** is an automatic check that stops a mistake and explains how to fix it.

Good guardrails for data:

- The contract exists and the data matches it.
- Personal data columns are tagged and masked.
- Every product has an owner and an on-call channel.
- Tests exist and pass; quality checks run in production.
- Costs stay within the team's quota, or the job is flagged.

Every guardrail needs an **escape hatch**: a waiver with a reason, an owner and an expiry date, recorded where the check can read it. A waiver that never expires is a hole; one that expires turns a shortcut into a dated decision someone must revisit.

## O2.7 Measuring a golden path

You cannot claim a path works because it exists. Measure it like a product:

- **Adoption:** share of new pipelines or products created on the path.
- **Time to first production run** on the path compared with off it.
- **Lead time for changes** and **change failure rate** for repositories on the path.
- **Support load:** tickets and questions per project.
- **Satisfaction:** a short survey each quarter; ask what made people leave the path.
- **Drift:** share of repositories on a supported template version.

If adoption is low, ask why before mandating anything. The usual answers are that the path does not cover a real need, or that it is slower than the old way.

## O2.8 Failure modes

| Failure | What it looks like | Prevention |
|---|---|---|
| Golden cage | The path is mandatory and cannot bend; teams fight it | Keep it optional with escape hatches; earn adoption |
| Too many paths | Ten templates, none maintained | One or two journeys, done well |
| Stale templates | Repositories stuck on old versions with known bugs | Versions, upgrade bots, drift reports, shared libraries |
| Built without users | A beautiful template nobody asked for | Shadow real teams first; measure adoption |
| Gates disguised as paths | The template still ends in a ticket to the platform team | Self-service with automatic guardrails |
| Defaults nobody understands | Teams cannot debug what the template generated | Docs, examples and a clear "how it works" |

## O2.9 Architect's lens: golden paths and self-serve templates

The questions an architect is asked about golden paths: what to pave, how to keep it alive, and how to know it works.

| Question | Short answer for golden paths |
|---|---|
| **What problem does it solve?** | Fragmentation and slow starts: every team solves the same setup problems differently, new pipelines take weeks, and the platform team becomes a ticket queue. A golden path makes the right way the fastest way for common journeys. |
| **Why it over the alternatives?** | Against tickets to a platform team: self-service scales and removes waiting. Against a written standards document: a template produces a working, compliant result instead of asking teams to read and follow rules. Against a mandatory framework: an optional path keeps teams able to handle real exceptions. |
| **When not to use it?** | Journeys that happen once or twice a year; teams too few to justify the upkeep; areas still changing so fast that a template would be out of date in a month (write a guide first, pave later). |
| **Who owns and pays for it?** | The platform team owns the templates, the scaffolder, shared CI and the upgrade process as products, with a roadmap and support. Teams own what they create from a template, including keeping it upgraded. |
| **Where does it sit?** | In the developer portal and the platform: templates and the scaffolder create repositories; shared workflows, policy checks and monitors run in CI and production; the catalog registers the result. |
| **How does it fail and scale?** | It scales with reuse: shared libraries and workflows update everyone at once, copied files do not. It fails as a golden cage, template drift, too many paths, paths built without users, and gates disguised as self-service. |
| **When do you move off it?** | When a journey disappears or changes completely, retire the path with a notice; when a managed service covers the journey better, make the path a thin wrapper around it. |

### Under the hood

**1. What goes into a template for a new data product, and what stays out of it?**
<details><summary>Model answer</summary>

In: a standard layout, a pre-filled contract (owner, grain, schema, SLOs), a transformation project with one working example, contract and quality tests, the orchestrator job as code with retries and alerts, freshness and volume monitors, catalog registration and a README. Out of the copied files: anything that should change for everyone at once, such as CI steps, deployment logic and policy checks; those come from shared workflows or libraries the template references by version. The less is copied, the less drifts.

</details>

**2. How do you get a fix to 80 repositories created from old template versions?**
<details><summary>Model answer</summary>

Know where every repository stands: each records the template version it came from, and a drift report compares it with the latest. Ship the fix as a new template version with release notes, and let a bot open an upgrade pull request in every affected repository, with the diff and tests running in CI. Owners merge; the report tracks who has not, starting with those a major version behind. For the future, move the fixed part into a shared workflow or library so the next fix reaches everyone without 80 pull requests.

</details>

**3. What makes a guardrail better than a review gate, and how do exceptions work?**
<details><summary>Model answer</summary>

A guardrail is an automatic check that runs on every change, fails fast with a message that says how to fix it, and needs no human to wait for, so it scales and is applied the same way to everyone. A gate is a person or board that must approve, which adds waiting and inconsistency. Exceptions go through a waiver recorded next to the code: the policy it skips, the reason, the owner and an expiry date. The check reads the waiver and passes until it expires, then fails again, so every exception is a dated decision rather than a permanent hole.

</details>

**4. Which defaults would you put in a pipeline template, and why do defaults matter so much?**
<details><summary>Model answer</summary>

Most teams keep the defaults, so defaults decide how most pipelines behave in production. Good ones: retries with backoff, idempotent writes (overwrite a partition or MERGE by key), a dead-letter table for bad records, schema checks against the contract, freshness and volume alerts to the owner, cost tags, and sensible resources. The simulator shows what missing defaults cost: the [dead-letter challenge](#/sim/sc/dlq) stalls on one bad record and the [schema challenge](#/sim/sc/schema) breaks readers, failures a template prevents by shipping a DLQ and a registry check from day one.

</details>

**5. How do you know a golden path is working, and what do you do if adoption is low?**
<details><summary>Model answer</summary>

Measure adoption (share of new projects on the path), time to first production run on and off the path, lead time and change failure rate for repositories on it, support tickets per project, satisfaction, and the share of repositories on a supported template version. If adoption is low, find out why before mandating: interview teams who left the path. Usually the path misses a real need or is slower than the old way; fix that, and adoption follows.

</details>

**6. A director wants every team to use the golden path by next quarter. What do you say?**
<details><summary>Model answer</summary>

Agree with the goal, not the mandate. A mandate turns a path into a cage: teams with real exceptions will work around it, and the platform team loses the signal that tells it what to fix. Instead: set an adoption target for new projects, make the path the default in the portal, measure why teams leave it and fix those reasons, require the guardrails (owner, contract, masking) for everyone on or off the path, and make the old ways more expensive by retiring their support with a date.

</details>

## In the app: templates, drift and guardrails in the browser (1.75 hours)

Four exercises run real tests in your browser:

1. **Render a template.** Check the parameters (required, pattern, defaults), fill every `{{placeholder}}` in file names and contents, and refuse to render when anything is missing or invalid.
2. **Template drift.** For each repository, say how many versions behind the latest template it is, and which files are missing or changed.
3. **Guardrails with waivers.** Run policy checks on a project and honour waivers until their expiry date.
4. **Is the path working?** From project records, compute adoption and median time to first production run on and off the golden path.

Pick one journey your teams repeat (a new batch product, a new CDC source, an access request). Write: the steps today and how long each takes; the template and what it creates; the defaults; the guardrails in CI; the escape hatch; and the one number you would track to know it worked.

## Customer drill: "nobody uses our templates" (10 minutes)

A platform lead says: "We built templates for pipelines six months ago. Only 15% of new pipelines use them. Leadership wants to make them mandatory." Answer out loud in three minutes: what do you find out first, and what do you do?

<details><summary>A strong answer</summary>

First find out why: interview teams who did not use the templates and look at what they built instead. Typical reasons are that the template does not cover their case (streaming, a source type), that it is slower than copying an old repository, or that what it generates is hard to debug. Fix the top two reasons, make the template the default in the portal, and measure time to first production run on and off the path. Mandate only the guardrails (owner, contract, masking, tests), which apply to everyone; keep the path itself optional and earn adoption with speed. Report adoption monthly.

</details>

@@interview
Q: What is a golden path, and how would you build one for data pipelines?
TAG: arch
A: A golden path is the opinionated, supported, fastest way to do a common job end to end, which teams may leave if they own the result. For data pipelines I would start by measuring the journeys: how often teams start a new pipeline, how long it takes, where they wait. I would shadow two teams, then build one template: standard layout, a pre-filled contract, a dbt or Spark project with a working example, tests, CI with contract and policy checks from a shared workflow, the orchestrator job as code with retries and alerts, monitors, and catalog registration. I would offer it through the developer portal and measure adoption and time to first production run.

Q: How do you stop templates from drifting once 100 repositories have been created from them?
TAG: arch
A: Copy as little as possible: CI, deployment and policy checks come from versioned shared workflows and libraries that update everyone at once. Version the template, record the version in each repository, and publish a drift report of how far behind each one is and which files differ. Ship fixes as new versions with release notes and let a bot open upgrade pull requests that run tests in CI. Chase major-behind repositories first, and deprecate old versions with a date.

Q: Our platform team is a ticket queue. How would you turn it into self-service?
TAG: arch
A: Count the tickets by type; most are repetitive (new pipeline, new source, access, environment). Pick the top one or two and turn each into a self-service flow: a form in the developer portal, a template or automation behind it, and automatic guardrails instead of manual review, with waivers for exceptions. Keep humans for genuinely new problems. Measure lead time per request type before and after, and the share of requests handled without a person.

TAG: arch
A: Almost never the path itself; I make the guardrails mandatory. Owner, contract, personal data masking, tests and cost tags apply to everyone on or off the path, enforced by checks in CI and production. The path stays optional so teams with real exceptions are not blocked, and their reasons for leaving tell the platform team what to improve. I raise adoption by making the path the fastest way and by retiring support for old ways with a date.
