- **Reading note: Generators.** A function with yield returns a generator that pauses after each value and resumes on the next call. yield from delegates to another iterable. Chaining generators builds a pipeline that processes one record at a time.

## P3.1 What a for loop really does

Every `for` loop runs the **iteration protocol**:

```python
for row in rows:          # what Python actually does:
    handle(row)           #   it = iter(rows)
                          #   while True:
                          #       try: row = next(it)
                          #       except StopIteration: break
                          #       handle(row)
```

- An **iterable** is anything you can loop over: lists, dicts, strings, files, generators. `iter(x)` gives an iterator.
- An **iterator** produces values one at a time with `next()` and raises `StopIteration` when it runs out. It remembers where it is.

A list is an iterable but not an iterator: you can loop over it many times. A file object and a generator *are* iterators: once consumed, they are empty.

```python
it = iter([10, 20])
next(it)   # 10
next(it)   # 20
next(it)   # StopIteration
```

## P3.2 Generators: functions that pause

A function containing `yield` is a **generator function**. Calling it runs nothing; it returns a generator object. Each `next()` runs the body until the next `yield`, hands out that value, and **pauses** with all local variables intact.

```python
def read_lines(path):
    print("opening")
    with open(path) as f:
        for line in f:
            yield line.rstrip("\n")
    print("closed")

g = read_lines("trips.log")   # prints nothing yet
next(g)                       # prints "opening", returns line 1
next(g)                       # returns line 2: no reopening, no re-reading
```

```
caller          generator
next(g)  ─────> runs until yield ──┐
         <───── value 1 ───────────┘   (paused here, locals kept)
next(g)  ─────> resumes after yield, runs to the next yield
         <───── value 2
```

Memory is the point: a generator holds one value at a time, so it can describe a billion rows, or an endless stream, in a few hundred bytes.

**Generator expressions** are the lazy twin of list comprehensions: round brackets instead of square ones.

```python
squares = [x * x for x in range(10**8)]   # builds a huge list: gigabytes
squares = (x * x for x in range(10**8))   # builds nothing until consumed
total = sum(x * x for x in range(10**8))  # constant memory
```

## P3.3 The "used once" trap

Generators can be consumed only once. This bites in real code:

```python
rows = (parse(l) for l in open("trips.csv"))
n = sum(1 for _ in rows)        # consumes everything
fares = [r["fare"] for r in rows]   # [] : nothing left
```

Rules of thumb:

- If you need the data twice, either materialise it once (`list(...)`, if it fits) or restart from the source.
- Never call `len()` on a generator; it has none.
- Functions that receive "an iterable" should loop over it **once**. If a function needs two passes, it should say so, or take a list.

## P3.4 Generator pipelines

Chain small generators, each doing one job, like Unix pipes. Nothing runs until the last stage pulls a value; then each row flows through every stage before the next row is read.

```
file ──> read_lines ──> parse ──> only_completed ──> chunked(1000) ──> write_batch
         (one line)    (dict)    (filter)            (list of 1000)    (database)
```

```python
def parse(lines):
    for line in lines:
        trip_id, city, status, fare = line.split(",")
        yield {"id": int(trip_id), "city": city, "status": status, "fare": float(fare)}

def only_completed(trips):
    return (t for t in trips if t["status"] == "completed")

pipeline = only_completed(parse(read_lines("trips.csv")))
for batch in chunked(pipeline, 1000):
    write_batch(batch)
```

Memory stays flat no matter how big the file is: at most one line plus one batch is in memory. This is the shape of Spark's **lazy evaluation** too: transformations build a plan, and nothing runs until an action (`count`, `write`) pulls data through it. A Kafka consumer loop is the same pattern with an endless source.

`yield from other_generator()` hands out everything another generator produces; useful for reading several files as one stream.

## P3.5 itertools you will actually use

```python
from itertools import islice, chain, groupby, accumulate, count

list(islice(rows, 5))                 # first 5 items: LIMIT 5
chain(file_a_rows, file_b_rows)       # one stream from many: UNION ALL
accumulate([1, 2, 3])                 # 1, 3, 6: running total
count(1)                              # 1, 2, 3, ... forever

for city, grp in groupby(sorted_rows, key=lambda r: r["city"]):
    print(city, sum(1 for _ in grp))  # groups CONSECUTIVE equal keys only
```

The `groupby` warning matters: it groups **consecutive** equal keys, so unsorted input gives repeated groups. That is a feature when you want runs (online/offline streaks, sessions), and a bug when you wanted SQL's `GROUP BY`. For a true group-by, sort first or use a dict.

Python 3.12 added `itertools.batched(iterable, n)`, which yields tuples of n. Exercise 2 has you write it yourself, because interviewers ask.

## P3.6 Batching and chunking

Almost every external system is faster in batches: one database insert of 1,000 rows instead of 1,000 inserts; one API call with 100 ids; one Parquet file of 128 MB instead of 10,000 tiny ones.

```python
def chunked(iterable, size):
    buf = []
    for x in iterable:
        buf.append(x)
        if len(buf) == size:
            yield buf
            buf = []
    if buf:
        yield buf          # the last, smaller batch: easy to forget
```

Choosing the size is a trade-off: bigger batches mean fewer round trips but more memory and a bigger retry when one fails. Start with 500–5,000 rows or a few MB, and measure.

## On your Mac (optional, 20 minutes)

See the memory difference. Save as `lazy.py` and run it:

```python
import tracemalloc

def eager(n):
    return sum([x * x for x in range(n)])

def lazy(n):
    return sum(x * x for x in range(n))

for f in (eager, lazy):
    tracemalloc.start()
    f(2_000_000)
    _, peak = tracemalloc.get_traced_memory()
    tracemalloc.stop()
    print(f"{f.__name__}: peak {peak / 1e6:.1f} MB")
```

The eager version's peak grows with n; the lazy one stays near zero.

**2.**

def gen():
    print("start")
    yield 1
    print("end")
g = gen()
print("made")
print(next(g))
```
<details><summary>Answer</summary>

`made`, then `start`, then `1`. Calling a generator function runs nothing. "end" is never printed because nobody asked for a second value.

data = ["a", "a", "b", "a"]
print([(k, len(list(g))) for k, g in groupby(data)])
```
<details><summary>Answer</summary>

`[('a', 2), ('b', 1), ('a', 1)]`. groupby groups consecutive equal items only.

**4.**
```python
it = iter([1, 2, 3])
for x in it:
    if x == 1:
        next(it)
    print(x)
```
<details><summary>Answer</summary>

`1` then `3`. The `next(it)` inside the loop consumes 2, so the loop's next value is 3.

</details>

**5.**
```python
def chunks(xs, n):
    for i in range(0, len(xs), n):
        yield xs[i:i + n]
print(list(chunks([1, 2, 3, 4, 5], 2)))
```
<details><summary>Answer</summary>

`[[1, 2], [3, 4], [5]]`. This version needs `len` and slicing, so it works on lists but not on generators. Exercise 2 asks for one that works on any iterable.

</details>

**6.**
```python
nums = [1, 2, 3]
sq = (n * n for n in nums)
nums.append(4)
print(list(sq))
```
<details><summary>Answer</summary>

`[1, 4, 9, 16]`. The generator reads `nums` lazily, so it sees the item appended before it was consumed.

Q: Explain the difference between an iterable and an iterator, with one example of each.
MODEL: An iterable can produce an iterator through `iter()`; you can loop over it again and again (a list, a dict, a string). An iterator produces values with `next()`, remembers its position and is used up after one pass (a generator, a file object, `iter([1, 2])`). Every iterator is iterable, but a list is not an iterator.

TYPE: short
TAG: py
Q: Your streaming dedupe keeps a set of every event id it has seen. What goes wrong in production, and how do you fix it?
MODEL: The set grows forever and the process eventually runs out of memory. Bound it: keep ids only for a time window (for example the last hour, based on event time, evicting older ids), use a TTL cache or an external store such as Redis with expiry, or rely on idempotent writes (MERGE on the key) downstream. Streaming engines do this with watermarks and state TTL.

@@interview
Q: How would you process a file that is larger than memory in Python?
TAG: py
A: Stream it. Iterate the file object line by line (or use `csv.DictReader`, or pandas with `chunksize`, or pyarrow's batch reader for Parquet), process each row or chunk with generator stages, and write results in batches. Only aggregates or a bounded window stay in memory. If the work needs global sorting or joins on data that does not fit, I would push it to a tool built for that: DuckDB, Spark or a database, rather than reinvent external sorting.
---
Q: What is a generator, and how is it different from returning a list?
TAG: py
A: A generator function uses `yield` to produce values one at a time, pausing between them with its local state kept. Returning a list computes and stores everything up front. A generator uses constant memory, starts producing immediately, and can represent endless streams, but it can be consumed only once and has no length or random access. I use generators for pipelines and streams, lists when I need several passes or indexing.
---
Q: Implement a function that yields fixed-size batches from any iterable.
TAG: py
A: Keep a buffer list; append each item; when the buffer reaches the batch size, yield it and start a new list; after the loop, yield the remainder if it is not empty. Validate that the size is at least 1. It works on generators because it never uses `len` or slicing. On Python 3.12+ `itertools.batched` does this, returning tuples. The classic mistakes are forgetting the final partial batch and clearing the yielded list in place instead of creating a new one.
---
Q: How does Python's laziness relate to Spark's lazy evaluation?
TAG: py
A: Both separate describing the work from doing it. A generator pipeline only runs when the consumer calls `next()`, and data flows through each stage one item at a time. Spark transformations build a logical plan; an action triggers the optimiser and execution. The difference is that Spark optimises the whole plan first (predicate pushdown, column pruning, join strategy) and runs it in parallel across partitions, while a Python generator chain runs exactly as written on one core.
---
Q: When is `itertools.groupby` the right tool and when is it a trap?
TAG: py
A: It groups consecutive items with equal keys. That is exactly right for runs and sessions on time-ordered data: online streaks, consecutive failures, sessionisation after sorting by user and time. It is a trap when people expect SQL `GROUP BY` on unsorted data, because each change of key starts a new group. For a true group-by, sort by the key first (O(n log n)) or accumulate into a dict (O(n)).
---
Q: A teammate's job reads a generator twice and the second result is always empty. Explain and fix.
TAG: py
A: Generators are single-use iterators; the first pass consumes it, so the second loop gets nothing. Fixes: compute everything in one pass, materialise once with `list()` if it fits, recreate the generator from its source for the second pass, or use `itertools.tee` for small look-aheads. I would also add a type hint (`Iterable` versus `Sequence`) so the function says whether it needs multiple passes.
