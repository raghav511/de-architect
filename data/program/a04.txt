- **Reading note: semantic layer versus raw text-to-SQL.** Public 2026 benchmarks, including one from dbt Labs, report that a model asked to write SQL against raw tables answers fewer business questions correctly than the same model asking a semantic layer for a defined metric. Treat a database MCP server like any service that holds credentials: least privilege, read-only by default, audit every call, and assume text coming back from the data can contain instructions.

They bill per token or per call on top of compute, so cost control is your job.

## A4.1 The AI data stack in one picture

An AI feature that answers questions about your business is a data product first. Six layers, bottom to top:

1. **Sources and pipelines.** The same ingestion, CDC and quality checks you built in earlier modules. Bad data in means confident wrong answers out.
2. **Storage.** Lakehouse tables and the warehouse, plus embeddings for text (module A5).
3. **Context layer.** The semantic layer (metrics, dimensions, joins), a glossary of business terms, table and column descriptions, example questions with correct SQL, and access rules. This is what the model reads to understand your data.
4. **Access paths.** Four ways a model reaches data: generated SQL, defined metrics, retrieval over documents, and tools (an MCP server).
5. **The model and the agent loop.** Prompting, tool calls, retries, budgets.
6. **Evals, governance and cost.** Gold questions with known answers, logs of every query, PII rules, and a bill you can explain.

Most failures you will debug live in layers 1 and 3, not in the model.

**Say it:** "Six layers: data, storage, context, access, model, evals and governance. The context layer is the part we own."

## A4.2 Text-to-SQL you can trust

Text-to-SQL means the model writes a query from a question. It is fast to demo and easy to get wrong. The production version has five parts:

- **Schema linking.** Send only the tables and columns the question needs, with descriptions. Hundreds of tables in the prompt lower accuracy and raise cost.
- **Context.** Business definitions ("active rider = at least one completed trip in 28 days"), allowed joins, and three to five example questions with correct SQL.
- **Guardrails before running.** Read-only: one statement that starts with SELECT or WITH, no write keywords. An allow list of tables. A row limit and a timeout. A read-only database role, so the guard is not the only line of defence.
- **Self-correction.** If the database returns an error, send the error back once or twice. Cap the tries.
- **Checks after running.** Empty result, a total that does not match a known metric, or a suspicious row count: say so instead of answering.

Show the SQL with the answer. A person can check a query; nobody can check a number with no source.

**Say it:** "Link the schema, ground it in definitions and examples, guard the SQL, retry on errors with a cap, and show the query."

## A4.3 Semantic and context layers

A **semantic layer** defines metrics once, in code: what "revenue", "completed trip" and "active rider" mean, which tables they come from, and which dimensions they can be cut by. Dashboards, notebooks and now models all ask it for `revenue by city last week` instead of writing their own SQL.

Why it matters more with AI: when ten people write "revenue" ten ways, you get ten numbers. When a model writes it, you get a new number every time the wording changes. A metric call is deterministic: same question, same SQL.

Use both, on purpose:

- **Known metrics** (the questions in your top 50): route through the semantic layer. The model picks the metric, the dimensions and the filters; the layer writes the SQL.
- **Exploration** (one-off questions): allow guarded raw SQL, label the answer as exploratory, and log the question. Repeated questions become new metrics.

The wider **context layer** adds descriptions, owners, freshness and access rules, so the model also knows what not to use (a deprecated table, a column with PII).

**Say it:** "Metrics through the semantic layer for consistency; guarded SQL for exploration; repeated exploration becomes a metric."

## A4.4 MCP for databases: tools, not passwords

An agent should never hold a database password and run whatever it likes. It should call a small set of **tools**, each one doing one safe thing. The Model Context Protocol (MCP) is the common standard for describing those tools to any model. A database MCP server usually offers:

- `list_tables` and `describe_table`: discovery, with descriptions from the context layer.
- `run_query`: read-only, guarded, row-capped, with a timeout.
- `get_metric`: ask the semantic layer for a defined metric.

Security rules:

- **Least privilege.** The server connects with a read-only role limited to approved schemas. Row and column security still apply.
- **Audit.** Log every call: who, which tool, the SQL, rows returned, cost.
- **Prompt injection from data.** A customer note in a table can say "ignore your instructions". Tool results are data, never instructions. Keep write tools out, or behind human approval.
- **Errors the model can read.** Return a clear error ("table not allowed: riders") so the agent can correct itself instead of guessing.

**Say it:** "The agent calls narrow read-only tools through MCP; credentials, limits and audit live in the server, not in the prompt."

## A4.5 AI functions inside SQL

Warehouses can now call a model from a SELECT: classify every support ticket, extract fields from every email, summarise every review. Examples are Snowflake Cortex AI functions, Databricks `ai_query` and BigQuery's generative functions. This is ETL with a model as a transform, so treat it like one:

- **Cost.** Calls x tokens per call x price. A 50 million row backfill at 300 tokens a row is 15 billion tokens. Estimate before you run; try 1,000 rows first.
- **Cache by input hash.** Do not pay twice for the same text. Store `label, model, prompt_version, input_hash` next to the row.
- **Incremental, not full refresh.** Only new or changed rows are classified each run. A change of model or prompt version is a deliberate backfill.
- **Determinism.** Temperature 0 and a fixed model version; still expect some drift, so sample and review.
- **Quality.** Constrained outputs (a fixed label list or a JSON schema), a dead-letter table for invalid replies, and a labelled sample to measure accuracy.

**Say it:** "AI functions are transforms that bill per call: estimate, cache by hash, run incrementally, version the prompt and model, and measure on a labelled sample."

## A4.6 Evaluating data agents

You cannot ship "ask your data" on demos. Build an eval set:

- **30 to 100 real questions** from the people who will use it, each with a reviewed gold SQL or metric call.
- **Execution accuracy:** run the gold and the generated query and compare the results, ignoring row order and column names. Comparing SQL text fails correct answers written differently.
- **Also track:** refusals that should have been answers, answers that should have been refusals, retries, latency and cost per question.
- **Run it on every change:** new model, new prompt, new tables, renamed columns. Schema changes break agents silently.
- **Split by difficulty:** single table, joins, time windows, ambiguous wording. Report per group.

A release rule is simple: no drop in execution accuracy on the eval set, and no new write or permission failures in the logs.

**Say it:** "Gold questions with reviewed answers, scored by running both queries, rerun on every model, prompt or schema change."

## Ask-your-data design drills (30 minutes)

Answer each out loud, then check the model answers.

1. The finance team asks "what was revenue last quarter?" Raw SQL or semantic layer?
2. A generated query joins `trips` to `riders` on the wrong key and returns a number 3 times too big. What catches it?
3. The agent's MCP server uses the analytics admin user. What do you change?
4. You need sentiment for 40 million reviews. What do you do before running the AI function?
5. A column is renamed from `fare` to `fare_amount`. What breaks and how do you find out?

**Model answers:** 1, semantic layer: it is a defined metric and the number must match finance's report. 2, an execution check against the metric (revenue by quarter from the semantic layer) and a sanity rule on row counts after joins; the eval set should contain a join question like it. 3, a read-only role limited to approved schemas, row and column security, a statement timeout, and an audit log. 4, estimate tokens and cost, run 1,000 rows, measure accuracy on a labelled sample, cache by input hash, then run incrementally. 5, the context layer and any example SQL that mention `fare`; run the eval set on schema changes and alert on the drop.

@@interview
Q: Design an "ask your data" assistant for the operations team.
TAG: ai
A: Start from the top 50 questions they ask. Known metrics go through the semantic layer; exploration uses guarded text-to-SQL. Context: metric definitions, table descriptions, a glossary and example SQL, with schema linking so each prompt carries only relevant tables. Access through an MCP server with read-only tools on a read-only role, row limits and timeouts, every call logged. Answers show the SQL and the source tables. An eval set of 60 real questions scored by execution accuracy gates every change, and repeated exploratory questions become new metrics.
---
Q: Text-to-SQL or a semantic layer?
TAG: ai
A: Both, for different questions. Defined metrics through the semantic layer, because the answer must match the official number and the SQL is the same every time. Exploration through guarded text-to-SQL, labelled as exploratory and logged. I watch the logs and promote repeated questions into metrics.

Q: How do you stop an agent with database access from doing damage?
TAG: ai
A: It never gets a password, only narrow tools: list, describe, read-only query, get metric. The server uses a read-only role on approved schemas with row and column security, enforces one statement, an allow list, a row cap and a timeout, and logs every call. Tool results are treated as data so injected instructions in a row do nothing. Anything that writes or sends goes through human approval.

Q: How do you evaluate a text-to-SQL system?
TAG: ai
A: A gold set of real questions with reviewed SQL, split by difficulty. I run both gold and generated queries on a fixture or a read-only replica and compare results ignoring order and column names. I also track wrong refusals, wrong answers that should have been refusals, retries, latency and cost. It runs on every change of model, prompt or schema, and a release must not lower accuracy.
---
Q: We want sentiment on 40 million reviews using a warehouse AI function. Walk me through it.
TAG: ai
A: Estimate first: rows times tokens times price, then a 1,000-row trial to check cost and accuracy against a labelled sample. Constrain the output to a fixed label set, send invalid replies to a dead-letter table, and cache by input hash with model and prompt version stored next to the label. Run incrementally on new and changed reviews. A new prompt or model is a planned backfill with a before-and-after accuracy report.
---
Q: What is MCP and why would a data team care?
TAG: ai
A: The Model Context Protocol is a standard way to describe tools to any model or agent. A data team can publish one governed server, with read-only query, describe and metric tools, credentials, limits and audit, and every assistant in the company uses it, instead of each team wiring its own database access into prompts.
