## C1.1 What Claude Code actually is

Claude Code is an **agent in your terminal**. You already met agents in AI 1: a model in a loop with tools. Claude Code is that loop, built for software work:

```
you: a task in plain English
loop:
  Claude reads files, searches, runs commands (tools)
  you approve the risky ones (permissions)
  Claude edits files and checks its work
until: it answers, or you stop it (Esc)
```

Three things make it different from pasting code into a chat window:

1. **It sees your real project.** It can open any file, grep the codebase and run your tests, so its answer is based on your code, not a guess.
2. **It acts.** It edits files and runs commands. That is the power and the risk: every lesson in this track is partly about controlling what it may do.
3. **It remembers the project, not you.** Each session starts fresh. Durable knowledge goes in a `CLAUDE.md` file in the repo (lesson C7), not in your head.

For a data engineer this means: "why does this dbt model double count", "add a test for late-arriving rows", "write the backfill script and dry-run it" become tasks you hand over and **review**, instead of tasks you type out.

## C1.2 Install and sign in

On your Mac (one of these):

```bash
curl -fsSL https://claude.ai/install.sh | bash     # native installer (recommended)
brew install --cask claude-code                    # or Homebrew
```

Then in any project folder run `claude`. The first run asks you to sign in: either your Claude subscription (Pro or Max) or an Anthropic Console account billed per token. Run `/doctor` inside a session if anything looks wrong.

On iPad or iPhone use the **Codespace** linked from the test page: a real Linux terminal in Safari with Claude Code already installed and the practice project open.

## C1.3 The keys and commands you use every day

| You want to | Do this |
|---|---|
| Point at a file | type `@` and pick it, e.g. `explain @pipeline/ingest.py` |
| Run a shell command yourself | start the line with `!`, e.g. `! python3 -m unittest -q` (the output goes into the conversation) |
| Stop Claude mid-step | `Esc` (it stops and waits; nothing is lost) |
| Go back to an earlier point | `Esc` twice, or `/rewind`, then pick the message to return to |
| Plan before any edit | `Shift+Tab` until the footer says **plan mode** |
| Accept edits without asking each time | `Shift+Tab` to **accept edits** (only once you trust the plan) |
| Start a clean conversation | `/clear` (do this between unrelated tasks) |
| See what fills the context | `/context` |
| Pick up yesterday's session | `claude -c` (continue) or `claude -r` (choose one) |
| Change model | `/model` |

When Claude wants to run a command or edit a file, you see a **permission prompt**: allow once, allow always for this kind of command in this project, or no. Say no freely; tell it why, and it adapts.

## C1.4 The workflow that works: explore, plan, code, commit

Most bad AI changes come from skipping straight to "fix it". A senior pattern:

1. **Explore.** "Read @pipeline/ingest.py and @tests/test_ingest.py. Do not change anything yet. Which tests fail and why?"
2. **Plan.** In plan mode: "Propose the smallest fix for the date-window bug. List files you would touch and how you will prove it works."
3. **Code.** Approve the plan, let it edit, and let it **run the tests**.
4. **Review and commit.** Read the diff yourself (`! git diff`). Ask "what could this break?" Then "commit with a message that explains the bug".

The review step is not optional. You are accountable for every line Claude writes, in the same way you are for a junior engineer's pull request you approve.

## Lab: your first change (35 minutes)

1. In plan mode (`Shift+Tab`), ask: *"Explain this project in 6 lines: what it reads, what it writes, and how to run the tests. Do not edit anything."* Check the answer against the README.
2. Run the tests yourself: `! python3 -m unittest -q`. Two tests fail.
3. Ask: *"Look only at test_end_day_included. Explain why it fails, then propose the smallest fix. Wait for my go-ahead."*
4. Approve, let Claude edit and re-run the tests. Exactly one fewer test should fail.
5. Read `! git diff`. Is the change one line? Did it touch anything else?
6. Ask Claude to commit with a clear message. Check with `! git log --oneline -2`.
7. Press `Esc` twice and look at the rewind menu. You do not need to use it, but know it is there.

Write down three things you noticed (for example: it asked before running the tests; plan mode refused to edit). You need them for task 1.

@@interview
Q: How do you use AI coding assistants in your day-to-day data engineering work?
TAG: ai
A: I use Claude Code as a pair that does the typing while I keep the judgment. For a bug, I make it reproduce the failure first, explore the relevant files in plan mode, and propose the smallest fix with a test. Then it edits and runs the tests, and I review the diff the way I would review a teammate's pull request. Where it saves the most time: boilerplate such as tests, backfill scripts and dbt model scaffolding, explaining unfamiliar code, and first drafts of design docs. Where I stay hands-on: data contracts, anything touching production data or credentials, and performance decisions, where I want the numbers myself.
---
Q: What risks do AI coding agents bring to a data platform team, and how do you manage them?
TAG: ai
A: Four risks. Wrong but plausible code, so every change goes through tests and human review. Over-broad actions such as deleting files or running against production, so permissions are least-privilege and production credentials are never on the machine. Leaks of secrets or customer data in prompts, so we deny reads of secret files and use synthetic data. Skill atrophy, so engineers still own the design and can explain every line. I treat the agent like a fast junior engineer with no production access.
---
Q: A teammate says "the AI wrote it, the tests pass, ship it". How do you respond?
TAG: behavioral
A: I agree tests are necessary, but they only prove what they cover. I would ask three questions: does the diff do only what we intended, what inputs are not tested (nulls, late data, duplicates, volume), and can the author explain the change? If the answer to the last is no, it is not ready. I would frame it as our normal review bar, not a special rule for AI code.
---
Q: When would you not use an AI agent for a task?
TAG: ai
A: When the cost of a subtle error is high and hard to detect: changing financial calculations without a strong test suite, schema migrations on production tables, or security-sensitive code, unless I can verify the result independently. Also when the task is mostly judgment, like choosing between two architectures for my team's constraints: AI can list options, but the decision and its trade-offs are mine.
---
Q: How do you make sure AI-assisted changes are reviewable?
TAG: ai
A: Small, focused changes: one bug or feature per session and per commit. I ask for a plan first, so the reviewer can compare the plan with the diff. The commit message explains why, not just what. And the change includes the test that proves it, ideally written to fail before the fix.
