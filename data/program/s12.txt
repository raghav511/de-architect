## 12.1 What this sprint is for

You have built a platform, broken it nine ways, written eight design documents, and taken two mock loops. Studying more now has less value than performing under interview conditions. This sprint is almost entirely practice in the format you will face.

## 12.3 Order your interviews

Interviewing is a skill that improves with repetition, so sequence it.

1. **Practice tier, first two weeks.** Two or three companies you would accept but are not your first choice. Real interviews with lower stakes.
2. **Target tier, next.** The companies you most want, once your timing and nerves have settled.
3. **Stretch tier, alongside.** Roles slightly above your level, including forward deployed roles if they interest you.

Try to bring final rounds together within two or three weeks, so offers arrive close to each other.

**Questions for every recruiter:**

- How many rounds, and what is each one?
- Is AI assistance allowed, required or banned in each technical round?
- Which language may I use for coding: Python, Scala or either?
- What level is the role, and what does it pay in fixed salary, variable pay and equity?
- Is there a take-home, and how is it reviewed?

## 12.4 The capstone, presented

A repository that interviewers can open does more than any claim on a resume. Yours should contain:

- **A README** that starts with one paragraph on what the platform does, then an architecture diagram, then how to run it.
- **Design decisions** as short records: why Iceberg, why update mode for demand, why the agent only proposes fixes. Your sprint notes contain all of them.
- **The incident log**, cleaned up. It shows you have operated what you built.
- **The agent's evaluation table**: incidents, scores, cost per incident.
- **Honest scope.** Say it is a personal platform on synthetic data, built to learn and demonstrate.

Prepare a **five-minute demo**: thirty seconds on the problem, one minute on the architecture, two minutes on a live failure being diagnosed by the agent and posted to Slack, one minute on the evaluation numbers, thirty seconds on what you would build next. Rehearse it three times. Use it when an interviewer says "tell me about a project".

## 12.5 Your resume

- **Headline:** "Senior Data Engineer", followed by your strongest specialities. Lead with data engineering, since that is the role, and keep AI as the differentiator in the second line.
- **Each role** opens with the largest system you worked on and its scale.
- **Every number** must be one you can explain for five minutes: how it was measured, what you did, what others did.
- **Add the project**: the platform and on-call agent, with the repository link.
- **Order skills** by what you can defend under questioning, not by what you have heard of.

## 12.6 Offers

Get offers close together, because a competing offer is the strongest negotiation evidence. Compare total compensation over four years, including how equity vests. Ask for the number that would make you accept, with a reason. Be pleasant and specific. Get the final offer in writing before resigning.

TITLE: Teams with more than two consecutive wins
KIND: sql
MIN: 12
TAG: sql
SRC: Flipkart, 4 YOE
PROBLEM:
Table `matches(team, match_date, result)`, where `result` is `W` or `L`. Each team plays at most once per date.

Return every team that had **a run of three or more consecutive wins** in its own sequence of matches. Order by team.
SOLUTION:
```sql
WITH r AS (
  SELECT team, match_date, result,
         ROW_NUMBER() OVER (PARTITION BY team ORDER BY match_date)         AS rn_all,
         ROW_NUMBER() OVER (PARTITION BY team, result ORDER BY match_date) AS rn_result
  FROM matches
)
SELECT DISTINCT team
FROM r
WHERE result = 'W'
GROUP BY team, rn_all - rn_result
HAVING COUNT(*) >= 3
ORDER BY team;
```

Gaps and islands, in its second form. Within a run of wins, both row numbers rise by one per match, so their difference is constant; a loss interrupts the run and changes the difference. Grouping by team and that difference gives each run, and `HAVING` keeps runs of three or more.

"Consecutive" here means consecutive matches, not consecutive dates, which is why row numbers are used and not dates. In the diagnostic, the same idea used dates because the question was about calendar days. Read which one the question asks for.

TITLE: Top K most frequent words
KIND: dsa
MIN: 12
TAG: dsa
SRC: Salesforce, 4 YOE
PROBLEM:
Given a list of words and an integer `k`, return the `k` most frequent words, most frequent first. Words with equal counts are ordered alphabetically.

`["the","day","is","sunny","the","the","sunny","is","is"]`, `k = 4` returns `["is","the","sunny","day"]`.
SOLUTION:
```python
import heapq
from collections import Counter

def top_k_words(words, k):
    counts = Counter(words)
    return heapq.nsmallest(k, counts, key=lambda w: (-counts[w], w))
```

Count in O(n). Then select k items with a heap in O(m log k) for m distinct words, which beats sorting all of them when k is small. The key orders by count descending and then by the word itself, which handles ties.

Salesforce asked for a scalable version using a Count-Min Sketch. When the vocabulary is too large to count exactly, a Count-Min Sketch estimates counts in fixed memory with small overestimates, and a heap of size k holds the current top candidates. In a distributed setting, count per partition, then merge counts by word and take the top k, which is a `groupBy` followed by a limit in Spark.

TITLE: The most queried table in an audit log
KIND: pyspark
MIN: 12
TAG: spark
SRC: Walmart, 3 YOE
PROBLEM:
A DataFrame `df` was read from `audit.txt` with columns `userid, timestamp, tablename, query_text`.

Write `most_queried(df)` returning a Python list of the table name or names with the highest number of queries, sorted alphabetically. Return all names if several tie.
SOLUTION:
```python
from pyspark.sql import functions as F

def most_queried(df):
    counts = df.groupBy("tablename").count()
    top = counts.agg(F.max("count")).first()[0]
    return [r.tablename for r in counts.filter(F.col("count") == top)
                                       .orderBy("tablename").collect()]
```

Count per table, find the maximum, and return every table at the maximum. Ties are the usual follow-up, which is why the result is a list.

Only the small result is collected to the driver. Walmart also asked for a plain Python version; it is a `Counter` over the third field of each line, read as a stream, as in sprint 1.

Q: Read a text file into Spark and count words, using `map`, `flatMap` and `reduceByKey`.
SRC: Databricks, 5 YOE
TAG: spark
A: With the RDD API:

```python
counts = (spark.sparkContext.textFile("s3://bucket/book.txt")
          .flatMap(lambda line: line.lower().split())
          .map(lambda word: (word, 1))
          .reduceByKey(lambda a, b: a + b))
```
`flatMap` turns each line into many words. `map` pairs each word with 1. `reduceByKey` combines counts per word, first within each partition and then after the shuffle, which sends less data than `groupByKey`. With DataFrames: `split`, `explode`, then `groupBy("word").count()`, which goes through the optimiser and is what I would use in practice.

Q: How would you use MapReduce to solve Two Sum over a very large dataset?
SRC: Amazon, 4 YOE
TAG: dsa
A: For each number x, the pair partner is target − x. In the map phase, emit each number keyed by a canonical pair key: the smaller of x and target − x. Both members of a valid pair then arrive at the same reducer. In the reduce phase, check whether both x and target − x are present, counting duplicates when x equals target − x, and emit the pairs. That is one shuffle, and it parallelises across keys. In Spark this is a self-join on `value = target - value`, or the keyed grouping above.
---
Q: What happens when multiple consumers in one group read from a single partition?
SRC: Databricks, 5 YOE
TAG: streaming
A: They cannot. Within a consumer group, each partition is assigned to exactly one consumer, so only one of them reads it and the others receive nothing from that partition. They act as standbys and take over after a rebalance if the active consumer fails. Consumers in different groups can each read the same partition independently, each tracking its own offset. To read faster, you add partitions and then consumers, not consumers alone.
---
Q: Explain clustered and non-clustered indexes, and when to use each.
SRC: Adobe, 4–6 YOE
TAG: sql
A: A clustered index determines the physical order of rows in the table, so there can be only one; range scans on its key are very efficient. A non-clustered index is a separate structure holding the key and a pointer to the row, so a table can have several, at the cost of extra lookups and slower writes. I put the clustered index on the column used for range queries or the primary access path, often a date or the primary key, and non-clustered indexes on selective lookup columns. In columnar warehouses the equivalents are sort and clustering keys plus metadata pruning, not indexes.
---
Q: Explain horizontal and vertical partitioning, and how partition pruning works.
SRC: Adobe, 4–6 YOE
TAG: spark
A: Horizontal partitioning splits rows into groups, by date or region for example, with the same columns in each. Vertical partitioning splits columns into separate tables, such as moving rarely used or sensitive columns out of a hot table; columnar storage gives a similar effect automatically. Partition pruning uses a filter on the partition column to skip partitions entirely at planning time, using directory names or table metadata, so only matching partitions are read. It fails if the filter wraps the column in a function the planner cannot map to partitions.
---
Q: What is the difference between `COUNT(*)`, `COUNT(1)` and `COUNT(column)`?
SRC: Meta, 3 YOE
TAG: sql
A: `COUNT(*)` counts rows. `COUNT(1)` also counts rows; the constant is never NULL, and modern optimisers treat both identically, so there is no performance difference. `COUNT(column)` counts rows where that column is not NULL. `COUNT(DISTINCT column)` counts distinct non-NULL values. The practical use: in a left join, count a column from the right-hand table to get zero for rows with no match, where `COUNT(*)` would return one.
---
Q: When would you use `HAVING` instead of `WHERE`?
SRC: Meta, 3 YOE
TAG: sql
A: `WHERE` filters rows before grouping; `HAVING` filters groups after aggregation, so it can use aggregate results. For example, customers with more than three orders: `GROUP BY customer_id HAVING COUNT(*) > 3`. Conditions on raw columns belong in `WHERE`, because filtering early reduces the rows grouped. Window function results can be filtered by neither, which is why `QUALIFY` exists in some engines, or a subquery is used.
---
Q: Explain when to use `RANK`, `DENSE_RANK` and `ROW_NUMBER`.
SRC: Stripe, 4 YOE
TAG: sql
A: All three number rows within a partition by an ordering. `ROW_NUMBER` gives unique consecutive numbers, breaking ties arbitrarily unless the ordering is complete; use it to pick exactly one row per group, as in de-duplication. `RANK` gives ties the same number and leaves gaps after them, as in a competition: 1, 1, 3. `DENSE_RANK` gives ties the same number with no gaps: 1, 1, 2; use it for "the second-highest distinct value". Choosing between them is a statement about how ties should be treated, so say it aloud.
---
Q: What is the difference between a list and a tuple, and between `append` and `extend`?
SRC: Meta, 3 YOE
TAG: dsa
A: A list is mutable; a tuple is immutable. Tuples can be dictionary keys and set members because they are hashable when their contents are, they signal fixed structure such as a record, and they are slightly lighter. Lists suit collections that change. `append(x)` adds x as a single element, so appending a list nests it. `extend(iterable)` adds each element of the iterable. `[1, 2].append([3, 4])` gives `[1, 2, [3, 4]]`; `extend` gives `[1, 2, 3, 4]`.
---
Q: What are decorators in Python, and when would you use them?
SRC: Capgemini, 5 YOE
TAG: dsa
A: A decorator is a function that takes a function and returns a new one, usually wrapping the original with extra behaviour, applied with `@name` above a definition. Uses in data engineering: retrying a call with backoff, timing and logging a pipeline step, caching results, checking inputs, and registering functions, as Airflow's `@task`, MCP's `@mcp.tool()` and pytest fixtures do. A wrapper should use `functools.wraps` so the wrapped function keeps its name and docstring.
---
Q: What are generators in Python, and why are they memory-efficient?
SRC: Fractal, 7.5 YOE
TAG: dsa
A: A generator is a function that uses `yield` to produce values one at a time, pausing between them. It returns an iterator, and nothing is computed until the next value is requested. Only the current state is held in memory, not the full sequence, so a generator can stream a file of any size, read records page by page from an API, or chain transformations lazily. Generator expressions, written with parentheses, give the same behaviour inline. The trade-off: a generator can be consumed only once.
---
Q: What is data locality in Hadoop, and why is it important?
SRC: J.P. Morgan, 6 YOE
TAG: spark
A: Data locality means running a task on the node that already holds its input block, or on the same rack, so data is read from local disk instead of over the network. Hadoop and Spark schedulers prefer local placement and wait briefly for it before falling back. It mattered greatly when compute and storage shared machines in HDFS clusters, because the network was the bottleneck. With object storage, all reads are remote, so locality matters less and the gains come instead from reading fewer bytes and from caching.

Q: How does YARN schedule applications and allocate resources?
SRC: Microsoft, 4 YOE
TAG: spark
A: YARN separates resource management from job logic. The ResourceManager holds the cluster's resources and a scheduler, usually capacity or fair, that divides them among queues. Each node runs a NodeManager that launches and monitors containers. When an application is submitted, the ResourceManager starts its ApplicationMaster in a container, and the ApplicationMaster requests further containers with stated memory and cores, preferring nodes that hold its data. For Spark, those containers run the executors. Memory limits are enforced per container, which is where "container killed for exceeding memory limits" comes from.

Q: Compare MapReduce and Spark. When is each preferable?
SRC: Microsoft, 4 YOE
TAG: spark
A: MapReduce writes intermediate results to disk between every map and reduce step, so multi-step jobs are slow but very robust with little memory. Spark keeps data in memory across steps where it can, optimises whole query plans, and offers SQL, streaming and machine learning on one engine, so it is much faster for iterative and multi-stage work. Spark is the default today. MapReduce survives in legacy jobs that work and are not worth rewriting, or in clusters where memory is very constrained.

Q: How do you make sure NULL values do not distort aggregations such as `AVG()`?
SRC: Zen, 7 YOE
TAG: sql
A: First decide what NULL means. `AVG(column)` ignores NULLs, which is correct if NULL means "not applicable" and wrong if it means zero. If NULL means zero, use `AVG(COALESCE(column, 0))`. If it means unknown, report the share of NULLs beside the average, because a mean over 40% of the rows is misleading. Also watch `COUNT(column)` against `COUNT(*)` in denominators, and NULLs in join keys, which silently fail to match.
