# Data Architect: working notes for Claude

A single-user interview-prep PWA for a senior data engineer (the learner; who they are lives only in `~/.data-architect/profile.txt`, never in this public repo). Static files, served by GitHub Pages at https://raghav511.github.io/de-architect/. Used on a MacBook (Chrome), iPad and iPhone (Safari). Keep this file short and current: update it with every PR, and delete anything that is no longer true.

## How we work

- **Ship first, check after.** Build the feature with its own tests, open a PR, merge it at once, then run the long checks in the background (7 simulated users, accessibility, journeys, red team, speed, offline) and ship a fix for anything they find. Never hold a merge for the full suite.
- **Merge PRs yourself; never wait for the user.** If GitHub blocks a merge (a required review on `main`), do not bypass it with `--admin` or change branch protection: tell the user and keep working on the next thing.
- **Decide and continue.** If the user has not answered in 10–15 minutes, pick the recommended option and keep going.
- **The user's feedback mid-task comes first:** do it, ship it, then return to the plan.
- **Fewest taps:** one task per screen, the main action visible without scrolling on a phone, nested tabs instead of long pages, autosave instead of Save buttons.
- **Self-contained:** everything is learned and practised inside the app. Outside sources appear only as small ⓘ/▶ links next to an in-app note, opening in a new tab. No pirated or paywalled copies.
- **Progress is never lost.** Content changes go through the update tracker (below); never delete learner data.
- Show progress as a live checklist (the desktop app's task list) and plain status lines while working.
- Never print or commit the sync URL or its key (`~/.data-architect/config.json`), API keys, or learner data. Tests never reach the real grader on 127.0.0.1:8765.
- **Security review 11–13 (hardening):** grading through the sync script checks on a back-off (5, 10, 20, 40 s then each minute, `GRADE_BACKOFF`), at most 8 checks per answer (`g.checks`, then one per 10 minutes on reopen) and none while the tab is hidden (`waitVisible`); `sync/Code.gs` refuses every request when `KEY` is empty unless a valid session comes with it (`NO_KEY`, the app explains it), and has `authorize()` for the one-time UrlFetch permission; CSP `connect-src` lists only self, script.google.com, script.googleusercontent.com, accounts.google.com, api.anthropic.com, cdn.jsdelivr.net and the Mac grader; Settings accepts only `https://script.google.com/macros/s/…/exec` sync URLs (or localhost). Test browsers use `bypassCSP` for stub hosts such as https://sync.test; Q24 and Q35 run with the policy enforced. Tests Q33–Q35.
- **Public repo security:** `tools/secret_scan.py` runs in the pre-commit hook, `../qa/ship.sh` and `tools/refresh/ship.sh` and blocks keys, sync URLs, emails, home paths and the words in `~/.data-architect/private_terms.txt`. Who the learner is lives only in `~/.data-architect/profile.txt` (grader and coach read it). Commits use the GitHub noreply email. `index.html` has a Content-Security-Policy (scripts only from the app and cdn.jsdelivr.net, nothing inline, no frames); keep new code free of inline scripts and `eval`. Grader practice runs may read only inside their sandbox copy (`RUN_ALLOW`).

## Shipping a change

- Version strings: `VERSION` in `js/app.js`, `CACHE` and `?v=` in `sw.js`, `?v=` in `index.html`, and `version.json` (`notes` are shown to the learner as release notes, in plain words).
- The local helper `../qa/ship.sh NEWVER "title" "note" ...` bumps all of them, commits, opens the PR and merges it (it prints `NEEDS YOUR MERGE` if GitHub blocks it). PR descriptions end with the Claude Code line; commits with the Co-Authored-By line.
- `../qa/ship.sh` always works in the main checkout; from a worktree or another clone use `tools/refresh/ship.sh` (same steps, in its own checkout).
- Rebuilding the terminal: bump `VMV` in `js/term.js` (the service worker keeps `vm/` in its own cache across app updates).

## Tests

- `node tools/smoke.js BASE [filter] [--engine chromium|webkit]`: every feature once, as the learner uses it, on Chromium (Mac) and WebKit (iPhone 13): reel sound and moving on, Python output, quiz score, live mock score, simulator grade, sync merge, every section opening, figures, search, warm-up, profile, offline, terminal. - `node tools/crawl.js BASE [--engine chromium|webkit] [--state fresh|mid] [--quick] [--only REGEX]`: the button crawler. Visits every screen (NAV, NAV_GROUPS, every module tab, practice tabs, a problem of each kind, quiz, live mock, reels, simulator and its modes, warm-up, Profile, terminal) on Chromium (Mac) and WebKit (iPhone 13), first run and five weeks in, clicks every control once from the same starting state and records what happened, errors, CSP violations, dead controls, tap targets under 44 px, overflowing text and unnamed controls; destructive controls are skipped and listed. Regression checks for the bugs it found are in `REGRESS`. All four runs write `tools/crawl/REPORT.md`; `tools/crawl/UX.md` is the Mobbin benchmark.
- `node tools/personas/run.js BASE OUT [id]`: 7 simulated users rated 1–10 with P0/P1/P2 issues (needs fake sync and the stub grader; `../qa/round.sh OUT [id]` starts them).
- `python3 tools/build_bank.py`, `python3 tools/validate.py`: banks and content (need duckdb 1.5.x; 2.0 breaks minispark).
- `node tools/vm/labs_test.mjs`: boots the in-app Linux headless and passes all 16 Git labs.
- `../qa/checks.js BASE`: red team, broken-state recovery, offline, speed and size budget against `../qa/perf_baseline.json` (use the gzip server on 8812 for realistic sizes).

## Key mechanisms

- **Today:** one box called Today with sections Reading and labs, Quiz, Coding track, Interview practice and Coaching, plus a summary row. Each group has its own daily minutes (`budgets()`: reading `capWd/capWe` 60/120, coding `codeWd/codeWe` 50/80, interview and coaching `ivWd/ivWe` 30/45, all in Profile › Plan), filled by `fill()`, so carried work never lengthens a day. Reading keeps program order; an unfinished earlier module shows first in its own "Finish … first" block; a step carried from an earlier day is tagged "from Mon" (`S.planned`). Coding: reviews due, today's set, then this week's leftovers; an earlier week's unsolved problems wait for the weekend catch-up block (`codingItems`). Interview: the mock (its blanks carry into the next mock only on the same module, `mockQuestions`), coach items, then company questions with this module's first (`interviewItems`). Manual ticks live in `S.xdone[date]`; company questions tick on `#/recent`.
- **Daily refresh:** `tools/refresh/ROUTINE.md` (run every evening at 9 PM by the scheduled task `data-architect-weekly-refresh`, renamed Data Architect daily refresh; it adds interview questions, news, coding problems, design questions and module edits, then writes and records reels for new or changed sections in `~/.data-architect/refresh-repo`; companies in `tools/refresh/companies.txt`; ships with `tools/refresh/ship.sh`).
- **Recent interview questions:** `data/recent.json` (items: id, mid, company, level, asked, found, TAG, Q, A, src, url), written by the weekly scheduled task `data-architect-weekly-refresh` (also refreshes `data/news.json` and module content). Shown at `#/recent`, on the module's interview page, as one Today row (until every new one is ticked in `S.rq`) and in What is new. They are part of the interview step's fingerprint, so a finished interview step goes back to not done when its module gets new questions. Got it on What is new only hides the note; nothing is ever marked done for the learner.
- **Module tabs:** a tab is finished when `S.tabs[m:tab]` is set (with the text's hash; a changed tab is not finished) ("Done, next") or all plan steps that open it are ticked (`tabDone`); `#/learn/m` opens the first unfinished tab.
- **Scheduler:** units are packed day by day from today; nothing is skipped. Days since `S.since` (first use or "Make this week 1") with nothing done count as missed and show a "Catching up" note. Main-path steps come before Claude Code steps on the same day.
- **Update tracker:** each step, exercise and quiz has a content fingerprint (`S.cv`). When content you finished changes, the step goes back to not done with an "Updated" tag, and the old completion, score and code move to `S.archive`. New modules and steps are listed in the one-line "What is new" note on Today. `repairTracker()` fixes damaged tracker data.
- **Udemy links:** `udemyLinks()` shows a folded "Watch on Udemy" list under D1's chapter sections (`modules.d01.sections`, keyed by chapter h2 index), one row at the top of P1–P5's chapter (`modules.pX.lectures`), and on DSA problems by week (`dsa.weeks`). The lessons themselves are written for the app; never copy course material. No separate Udemy modules: content goes into the module and week already in the schedule.
- **Architect's lens:** a chapter h2 containing "Architect's lens" is wrapped in a `.lens` card by `mdEl()`: a 7-row table (what problem, why over others, when not, who owns and pays, where it sits, how it fails and scales, when to move off) and "Under the hood" internals questions with `<details>` model answers; matching questions join the module's `@@interview`.
